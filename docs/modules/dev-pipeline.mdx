# Dev Pipeline

## 结论

`ops/dev-pipeline/` 是一个**内部研发流水线**:在 Linear 里以 app 身份(`proactive-ai-dev`)接需求 → 读代码出 plan → 等人确认 → 委派 Codex 实现 → 人按需起一个 Fly preview 环境看效果 → 关 PR / 说「拆」自动销毁。全程**人在 Linear 里主动驱动**,没有后台轮询或自动收敛循环。

它**不进**产品代码:dev-pipeline 服务(Python/FastAPI)在自己的目录、跑在本地常驻进程;只有 preview 的 3 个 GitHub workflow 进 `main`(纯 CI/infra)。定位同 [Internal Reward Dashboard](./internal-reward-dashboard)——内部工具。

## 核心链路

```
Linear issue @proactive-ai-dev
  → planner 读代码出 plan(贴回 AgentSession，停下等人）
  → 人回「ok」 → 服务把 plan 当 spec、issueUpdate(delegateId=Codex) 委派
  → Codex 实现 → 人在 Codex 页面点 "Create PR" → GitHub 出 PR（自动挂到 issue）
  → 人回「部署/preview」 → 服务按 PR 改动范围起 Fly preview，回贴 URL
  → 看效果 → 关 PR 或回「拆 preview」 → 临时环境自动销毁
```

- 需求级对话主场 = Linear AgentSession;代码级对话主场 = GitHub PR。
- 触发 Codex 的唯一可靠方式 = `issueUpdate(delegateId=<codex_user>)`(实测 assigneeId / 纯文本 @mention 都不行)。
- 护栏:Codex 只在 `dev-pipeline/*`/`codex/*` 分支开 PR,**绝不 auto-merge**;人去 GitHub merge。

## 怎么用（Linear 里的指令）

在 EDG issue 的 agent 对话里说这些关键词(**新 @ 或在已有对话里回复都行**):

| 意图 | 关键词 | 行为 |
|---|---|---|
| 出方案 | (首次 @ 带需求) | planner 出 plan,等你回 ok |
| 确认 | `ok` / `确认` / `可以` / `go` | 委派 Codex 实现 |
| 起 preview | `部署` / `preview` / `看看` / `看效果` / `起服务` | 按改动范围起临时环境,回 URL |
| 拆 preview | `拆` / `关掉` / `停掉` / `销毁` | 销毁该 PR 的临时环境 |

找 PR 靠 Linear issue 上自动挂的 **GitHub PR attachment**(Codex 开 PR 时 Linear 自动关联),比按 issue 标识搜 GitHub 文本可靠。

## Preview 架构（scope-aware，按需最省）

`detect` job 用 `gh pr diff --name-only` 判 PR 改了哪些范围,**只起被改到的副本**:

| PR 改了什么 | `pinai-pr-N`（前端） | `pinai-pr-N-api`（后端 cluster） |
|---|:---:|:---:|
| 只前端 | ✅ → 指共享 dev 后端 | — |
| 后端逻辑（没动 migration） | ✅ → 指 ↘ | ✅ web+chat，**共用 dev 库** |
| 还动了 `db/migrations/` | ✅ → 指 ↘ | ✅ web+chat+**db 机器**（独立库，dev 零影响） |

- **A 档 cluster**:独立库不是单独的 Fly app,而是后端 app 内的一台 `pgvector` 机器(6PN 内网)。后端 app = web+chat+db 一锅,一次 destroy、一套 secret。**每 PR ≤ 2 个 Fly app**。
- **前端并行**:前端 job 用确定的后端 URL(`pinai-pr-N-api.fly.dev`),与后端 job 同时跑,不串行等待。
- **auth 一律复用共享 dev Supabase**(登录不随 PR 变);后端副本注入整套 dev secret(含 Composio/Stripe/LiteLLM——前期保留,验证完整环境)。
- workflow:`.github/workflows/preview.yml`(起)、`preview-down.yml`(手动拆)、`preview-cleanup.yml`(关 PR 自动拆)。

## 时延与成本（实测）

| 指标 | 实测 |
|---|---|
| 最大启动(前端+后端+独立库全 serving) | **~208s（~3.5 分钟）** |
| 纯前端 preview | ~1 分钟 |
| 停止(关 PR / @拆 → 全销毁) | **~22s** |
| 后端副本规格 | web×1 + chat×1（`--ha=false`），各 2 vCPU/2GB + db 机器 1GB |

⚠️ **后端副本不缩零**,跑着就花钱(~4 vCPU+4GB+db),靠关 PR / `@拆` 及时收。前端是静态站、空闲缩零、基本不花钱。

## 运维 / 验证

- **本地服务**:`cd ops/dev-pipeline && uv run uvicorn dev_pipeline.app:app --port 8200`,经 cloudflare 隧道收 Linear webhook。OAuth app token 存 SQLite kv,`/healthz` 看 `installed`。
- **手动起/拆 preview**(不经 Linear):`gh workflow run preview.yml -f pr=<N>` / `gh workflow run preview-down.yml -f pr=<N>`。
- **彻底清残留**:`flyctl apps destroy pinai-pr-<N>-api`(连 db 机器一起拆)+ `pinai-pr-<N>`。
- **服务单测**:`cd ops/dev-pipeline && uv run ruff check . && uv run mypy && uv run pytest`。
- **workflow 改动**:`workflow_dispatch` 只能从 `main` 触发;迭代时用 `gh workflow run preview.yml --ref <branch>` 跑分支版,验通再 merge `main`。

## 踩坑

1. **Linear OAuth token 失效**:`installed:true` 只代表 token 存在不代表有效。失效后 @ agent 仍建 session,但回写 Linear 报 401。Linear 因 "already installed" 不重发 token——必须先 **Settings → Agents → proactive-ai-dev → Revoke access** 再重新授权。详见 [[dev-pipeline-linear-oauth-token]]。
2. **Codex 出 PR 要手动点**:Codex-for-Linear 跑完任务只在沙箱 commit,**真开 GitHub PR 要在 Codex 页面手动点 "Create PR"**(Codex Cloud 设计,不是 bug)。前提:Codex 的 GitHub environment 必须连了本 repo(否则它环境里没 `origin` remote,只给 chatgpt task 链接、不出 PR)。
3. **后端副本 secret 用 stage 不用 no-stage**:A 档里 app 内先有了 pg 机器,`sync_fly_secrets --no-stage`(立即应用)会因「无 release 镜像」失败;暂存即可,随 `flyctl deploy` 生效。
4. **Fly 新 app 的 DNS 传播 ~40s**:preview 部署完到能 `curl` 通有几十秒延迟,不是 bug。
5. **第三方服务跨 preview 打架**:多个 preview 用同一 dev 测试账号时,Composio 游标 / LiteLLM key / Stripe 客户会互相干扰(数据库各自隔离,第三方共享状态不隔离)。前期接受,后续可给 per-PR 测试身份。
