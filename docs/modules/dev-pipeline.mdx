# Dev Pipeline

## Summary

`ops/dev-pipeline/` is an **internal dev pipeline**: it takes requests in Linear as an app identity (`proactive-ai-dev`) → reads the code and produces a plan → waits for human confirmation → delegates implementation to Codex → a human spins up a Fly preview environment on demand to see the result → closing the PR / saying "teardown" destroys it automatically. The whole process is **driven actively by humans in Linear**; there is no background polling or automatic convergence loop.

It does **not** go into product code: the dev-pipeline service (Python/FastAPI) lives in its own directory and runs as a local long-lived process; only the 3 preview GitHub workflows go into `main` (pure CI/infra). Same positioning as [Internal Reward Dashboard](./internal-reward-dashboard) — an internal tool.

## Core Flow

```
Linear issue @proactive-ai-dev
  → planner reads the code and produces a plan (posts it back to the AgentSession, stops and waits for a human)
  → human replies "ok" → service treats the plan as the spec and delegates via issueUpdate(delegateId=Codex)
  → Codex implements → human clicks "Create PR" on the Codex page → GitHub opens a PR (auto-attached to the issue)
  → human replies "deploy/preview" → service spins up a Fly preview based on the PR's change scope, replies with the URL
  → check the result → close the PR or reply "teardown preview" → the temporary environment is destroyed automatically
```

- Main venue for requirement-level conversation = Linear AgentSession; main venue for code-level conversation = GitHub PR.
- The only reliable way to trigger Codex = `issueUpdate(delegateId=<codex_user>)` (tested: neither assigneeId nor a plain-text @mention works).
- Guardrail: Codex only opens PRs on `dev-pipeline/*`/`codex/*` branches and **never auto-merges**; a human merges on GitHub.

## How to Use (Commands in Linear)

Just say it naturally in the agent conversation on an EDG issue (**either a new @ or a reply in an existing conversation works**). The main intent routing is LLM classification (`intent.py` IntentRouter, claude-haiku-4-5; the intent set includes new_request / refine_plan / confirm / deploy / teardown / forward / clarify / chitchat); the keywords in the table below are only the fallback set used when there is no `ANTHROPIC_API_KEY` or the LLM errors:

| Intent | Fallback keywords | Behavior |
|---|---|---|
| Produce a plan | (first @ with the request) | planner produces a plan and waits for you to reply ok |
| Confirm | `ok` / `approve` / `yes` / `go` (Chinese equivalents also match) | delegates implementation to Codex |
| Start preview | `deploy` / `preview` (Chinese words for "take a look" / "see the result" / "start the service" also match) | spins up a temporary environment based on the change scope, replies with the URL |
| Tear down preview | `teardown` / `destroy` (Chinese words for "turn off" / "stop" also match) | destroys the temporary environment for that PR |

PRs are found via the **GitHub PR attachment** auto-attached to the Linear issue (Linear links it automatically when Codex opens the PR), which is more reliable than searching GitHub text by issue identifier.

## Preview Architecture (scope-aware, cheapest on demand)

The `detect` job uses `gh pr diff --name-only` to determine which scopes the PR changed, and **only spins up the copies that were changed**:

| What the PR changed | `pinai-pr-N` (frontend) | `pinai-pr-N-api` (backend cluster) |
|---|:---:|:---:|
| Frontend only | ✅ → points at the shared dev backend | — |
| Backend logic (no migration touched) | ✅ → points at ↘ | ✅ web+chat, **shares the dev DB** |
| Also touched `db/migrations/` | ✅ → points at ↘ | ✅ web+chat+**db machine** (separate DB, zero impact on dev) |

- **Tier A cluster**: the separate DB is not a separate Fly app but a `pgvector` machine inside the backend app (6PN private network). Backend app = web+chat+db in one, one destroy, one set of secrets. **≤ 2 Fly apps per PR**.
- **Frontend in parallel**: the frontend job uses the known backend URL (`pinai-pr-N-api.fly.dev`) and runs at the same time as the backend job, with no serial waiting.
- **auth always reuses the shared dev Supabase** (login doesn't change per PR); the backend copy is injected with the full set of dev secrets (including Composio/Stripe/LiteLLM — kept for now, to verify the full environment).
- workflow: `.github/workflows/preview.yml` (bring up), `preview-down.yml` (manual teardown), `preview-cleanup.yml` (automatic teardown on PR close).

## Latency and Cost (measured)

| Metric | Measured |
|---|---|
| Max startup (frontend+backend+separate DB all serving) | **~208s (~3.5 minutes)** |
| Frontend-only preview | ~1 minute |
| Stop (close PR / @teardown → everything destroyed) | **~22s** |
| Backend copy size | web×1 + chat×1 (`--ha=false`), 2 vCPU/2GB each + db machine 1GB |

⚠️ **The backend copy doesn't scale to zero**; it costs money while running (~4 vCPU+4GB+db), so tear it down promptly by closing the PR / `@teardown`. The frontend is a static site that scales to zero when idle and costs almost nothing.

## Operations / How to Verify

- **Local service**: `cd ops/dev-pipeline && uv run uvicorn dev_pipeline.app:app --port 8200`, receives Linear webhooks through a cloudflare tunnel. The OAuth app token is stored in a SQLite kv; check `installed` at `/healthz`.
- **Manually start/tear down a preview** (bypassing Linear): `gh workflow run preview.yml -f pr=<N>` / `gh workflow run preview-down.yml -f pr=<N>`.
- **Fully clean up leftovers**: `flyctl apps destroy pinai-pr-<N>-api` (tears down the db machine with it) + `pinai-pr-<N>`.
- **Service unit tests**: `cd ops/dev-pipeline && uv run ruff check . && uv run mypy && uv run pytest`.
- **Workflow changes**: `workflow_dispatch` can only be triggered from `main`; while iterating, use `gh workflow run preview.yml --ref <branch>` to run the branch version, and merge into `main` once it is verified.

## Gotchas

1. **Linear OAuth token expired**: `installed:true` only means the token exists, not that it is valid. After it expires, @-ing the agent still creates a session, but writing back to Linear returns 401. Linear won't reissue the token because it is "already installed" — you must first **Settings → Agents → proactive-ai-dev → Revoke access** and then re-authorize. Details in [[dev-pipeline-linear-oauth-token]].
2. **Codex PRs need a manual click**: when Codex-for-Linear finishes a task it only commits in the sandbox; **actually opening the GitHub PR requires manually clicking "Create PR" on the Codex page** (Codex Cloud design, not a bug). Prerequisite: Codex's GitHub environment must be connected to this repo (otherwise its environment has no `origin` remote, and it only gives a chatgpt task link without opening a PR).
3. **Use stage, not no-stage, for backend copy secrets**: in tier A the app already has a pg machine first, so `sync_fly_secrets --no-stage` (apply immediately) fails with "no release image"; staging is enough, and the secrets take effect with `flyctl deploy`.
4. **DNS propagation for a new Fly app takes ~40s**: there is a delay of tens of seconds between the preview deploy finishing and `curl` succeeding; not a bug.
5. **Third-party services conflict across previews**: when multiple previews use the same dev test account, Composio cursors / LiteLLM keys / Stripe customers interfere with each other (databases are isolated per preview, but shared third-party state is not). Accepted for now; per-PR test identities can be added later.
