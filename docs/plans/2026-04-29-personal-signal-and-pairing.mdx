# PersonalSignal 范式 + 配对设计

承接 [2026-04-28-device-ingest-unification](./2026-04-28-device-ingest-unification.mdx)。
那一份把"所有 device 走一个 ingest 接口"的骨架搭完了,这一份定**字段范式**、**配对流程**、**本地/远程切换**。

## 一、目标

1. **PersonalSignal envelope 范式**:wire format 字段名跟 DB 列名 1:1 对齐,没有翻译层。
2. **手机 / Web App**:复用 Supabase Google 登录,登录后 SDK 自动注册自己作 device,**用户从不点"添加设备"**。
3. **无屏 / 第三方硬件**:走 6 位 Pair Code(OAuth Device Flow 简化版)。Web 端"Add Hardware" 按钮的真正用途。
4. **BLE 子设备(omi 项链 / 戒指)**:挂在手机 App 这台 device 之下,不在 user_devices 表独立成行。
5. **本地 dev 兼容**:同一份手机 App 既能连本地 ngrok 也能连 Fly,Supabase URL 共享。

## 二、PersonalSignal envelope

### 字段三层

**必填(4 个 envelope 骨架)**

| 字段 | 类型 | 例子 |
|---|---|---|
| `id` | string (UUID) | 客户端生成,幂等键 |
| `source` | string | `device:omi-7a2b` / `mobile:iphone-15` / `connector:gmail` / `web:browser-x` |
| `kind` | string | `ambient.image` / `ring.heart_rate` / `gmail.received` |
| `occurred_at` | ISO 8601 | 端侧时间(不是 server time) |

**Should-have(3 个,业务判断需要)**

| 字段 | 用途 |
|---|---|
| `title` | 一行人 / LLM 都看得懂的标题 |
| `summary` | 一句话摘要 |
| `payload` | 自由 JSON,`kind` 决定内部 schema |

**自由(没有 nice-to-have)**

`payload` 是 schemaless JSON。要塞什么塞什么。但有一个约定:

- **二进制**:`payload.binary_b64` (base64 字符串) + `payload.mime` (`image/jpeg` / `audio/opus` / `video/mp4` / ...)。后端按 `kind` 是否在媒体白名单决定要不要把 base64 解码落盘。

(决策:**不引入 nice-to-have 一层**。`salience` / `confidence` / `dedupe_key` 等当前都进 envelope 顶层,但**不强制端侧填**。后端给默认值。)

### Wire format

```
POST /api/proactive/devices/ingest
X-Device-Id:    <uuid>
X-Device-Token: <psk-from-register>
Content-Type:   application/json

[
  {
    "id":          "uuid",
    "source":      "device:omi-7a2b",
    "kind":        "ambient.image",
    "occurred_at": "2026-04-29T10:30:00Z",
    "title":       "frame #12",
    "summary":     "桌前工作中",
    "payload":     { "width":640, "height":480, "binary_b64":"...", "mime":"image/jpeg" }
  },
  ...
]
```

顶层就是数组。`source` 在每条 signal 里(不在 envelope 外)——一台手机可代理多个 BLE 子设备,每条来源可不同。

### 命名规范(强约束)

- 字段名 **snake_case**(跟 SQL 列对齐)
- `kind`:`<source_class>.<event_name>`,例如 `ambient.image` / `gmail.received` / `ring.heart_rate`
- `source`:`<scheme>:<stable_id>`,scheme 限定四种:`device` / `mobile` / `connector` / `web`

### 跟 personal_signals 表对齐

| Wire field | DB column | 备注 |
|---|---|---|
| `id` | `id` | TEXT PK |
| `source` | `source` (拆) + `device_id`(派生) | scheme 进 source,id 部分进 device_id |
| `kind` | `kind` | TEXT |
| `occurred_at` | `occurred_at` | TIMESTAMPTZ |
| `title` | `title` | |
| `summary` | `summary` | |
| `payload` | `payload_json` | JSONB |

PersonalSignal in-flight ≡ personal_signals row at-rest。ingest handler 几乎是 passthrough。

## 三、配对流程(三类设备分轨)

### Class A:能登 Supabase 的 App(手机 / Web / 桌面)

**用户从不操作"添加设备"**。SDK 启动时调一次 `ensureDevice()`,本地 keychain 缓存 token。

```
App 启动
  ↓ 用户已登录 Supabase ?
     否 → 引导 Google login → access_token
     是 → 复用 access_token
  ↓ keychain 有 device_token ?
     有 → 直接用,return
     无 → POST /api/proactive/devices/register (Bearer access_token)
          ← {device_id, device_token}
          ↓ 写 keychain / EncryptedSharedPrefs / localStorage
  ↓ ingest 时带 X-Device-Id + X-Device-Token
```

Web 端代码已存在(`proactive-ai-frontend/src/lib/devices.ts:ensureDevice`)。手机 App SDK 复用同一逻辑。

### Class B:无 Supabase 但有屏的硬件(智能眼镜 / 智能音箱 / 屏幕设备)

**Pair Code 模式**(简化版 RFC 8628)。

```
设备启动 → POST /api/proactive/devices/pair-code/request
            { device_class:"wearable", model?:"..." }
            (无需 auth)
          ← { code:"482915", poll_interval:3, expires_in:300 }

设备屏显示 "Pair: 482915"
设备每 3s 轮询: GET /api/proactive/devices/pair-code/poll?code=482915
                ← { status:"pending" }    (继续等)

   |
   v   用户在 Web (已登 Supabase)
       Add Hardware → 输入 482915
       POST /api/proactive/devices/pair-code/claim
         { code:"482915", display_name:"客厅眼镜", model:"xreal_v3" }
         (Bearer Supabase JWT)
       ← Server: 验证 code 有效 + 把当前 user_id 写进去 +
                 创建 user_devices 行 + 生成 device_token + status='claimed'
   |
   v
设备下次 poll → { status:"claimed", device_id, device_token }
设备存 token,开始 ingest。Server 立即作废 pairing_codes 行。
```

#### 新表

```sql
-- migration 005
CREATE TABLE pairing_codes (
  code         TEXT PRIMARY KEY,        -- 6 位,字符集 23456789ABCDEFGHJKLMNPQRSTUVWXYZ(去 0/O/1/I/L)
  status       TEXT NOT NULL,           -- 'pending' | 'claimed' | 'expired'
  device_class TEXT NOT NULL,           -- 'wearable' / 'sensor' / 'embedded'
  model        TEXT,                    -- 客户端自报
  user_id      BIGINT REFERENCES users(id),  -- claim 后填
  device_id    TEXT,                    -- claim 后填
  expires_at   TIMESTAMPTZ NOT NULL,
  created_at   TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX idx_pairing_codes_pending ON pairing_codes(expires_at) WHERE status='pending';
```

#### 新接口(4 个)

| 方法 | 路径 | Auth | 说明 |
|---|---|---|---|
| POST | `/api/proactive/devices/pair-code/request` | 无 | 设备申请 code |
| GET | `/api/proactive/devices/pair-code/poll?code=xxx` | 无(code 即凭据) | 设备轮询状态 |
| POST | `/api/proactive/devices/pair-code/claim` | Supabase JWT | 用户输 code 完成关联 |
| POST | `/api/proactive/devices/pair-code/cancel` | code 持有者 | 撤销(可选) |

#### 安全

- 6 位 code = 32^6 ≈ 10^9 组合,可控但要防穷举。
- **Per IP rate limit**:request / poll 各 10/min。
- **单 user 最多 1 个 active code**:防屏霸 / 防误操作。
- **5 分钟过期**:scheduler tick 每分钟 sweep `status='pending' AND expires_at < now() → status='expired'`。
- **claim 立即作废**:删行或 `status='claimed'` 留 audit。
- **Constant-time compare**:`crypto.timingSafeEqual`,防侧信道。

### Class C:无屏 BLE(omi 项链 / 智能戒指 / 心率胸带)

**Sub-device under 手机 App**。云端不存它的独立 token,挂在手机 App 这条 user_devices 行下面:

```
omi ↔ 手机 App: 操作系统级 BLE pairing(蓝牙 PIN / passkey,与 server 无关)
手机 App ↔ Server: 走 Class A 的 token
手机 App ingest 时: payload.source_hardware = "omi-7a2b"
                    或者 envelope source = "device:omi-7a2b"(手机 App 代填)
                    user_devices.metadata.attached_hardware += {id, model, paired_at}
```

云端永远只信任手机 App。omi 物理上断电、丢失、被偷,不影响 token——因为 token 在手机里。

**这一档不需要新接口、不需要新表。** 手机 App SDK 在本地 BLE pairing 后,把 attached_hardware 通过 ingest payload 带上来即可。

## 四、心跳

**没有单独的心跳协议**。`user_devices.last_seen_at` 在每次 ingest / register / poll 时由后端 fire-and-forget 更新。

UI 在线判断:`now() - last_seen_at < 5min`。

## 五、本地开发 vs Fly 后端兼容

### 痛点

手机 App 装到 iPhone 上之后,得知道往哪个 server 发数据:
- 开发:本地 docker compose 在 MacBook 的 `localhost:3000`,iPhone 不能直连 localhost
- 生产:Fly app `proactive-ai-api-prod.fly.dev`

Supabase URL 在两种 case 下**始终是云端**(共享),不切换。切换的只是 `API_BASE`。

### 三种本地路径(选其一)

#### 1. LAN IP(Makefile 当前默认)
- `ipconfig getifaddr en0` 拿 MacBook 在路由器上的 IP(如 `192.168.1.42`)
- iPhone 连同一 WiFi → `API_BASE=http://192.168.1.42:3000`
- 优点:零额外组件
- 缺点:换 WiFi / 不同网段就废,iPhone 上没法离开家测试

#### 2. ngrok 公网隧道
- `ngrok http 3000` → 拿到 `https://xxx.ngrok-free.app`
- iPhone 上 `API_BASE=https://xxx.ngrok-free.app`
- 优点:任何网络都能连,跟生产环境最像
- 缺点:免费版 URL 每次重启变;ngrok 进程要常驻
- **首选这个,符合用户提到的工作流**

#### 3. 部署到 Fly dev
- 改 `apis/.env.dev` + push,等 GitHub Actions 部完
- iPhone 始终用 `https://proactive-ai-api-dev.fly.dev`
- 优点:不需要本地运行任何东西
- 缺点:迭代慢(每次改代码要部署)

### SDK 怎么切换 API_BASE

在手机 App 里做成 build-time 注入(类似前端 vite 的 `VITE_API_BASE_URL`):

```
DEV build:    API_BASE = process.env.API_BASE_DEV (ngrok / LAN)
STAGING build: API_BASE = "https://proactive-ai-api-dev.fly.dev"
PROD build:    API_BASE = "https://proactive-ai-api-prod.fly.dev"
```

或者 runtime override:App 内塞一个隐藏的 dev menu,粘贴 ngrok URL 即可切换。**本地测试推荐 runtime override**,不需要重新打包。

### Supabase URL

**始终用云端 Supabase**(同一个 URL + key),不要在本地起 Supabase 实例。理由:
- Google OAuth callback 必须 HTTPS,本地起没意义
- 用同一个 Supabase 后端,user 在 Web 登录的就是手机上看到的
- `apis/.env.dev` 和 `apis/.env.production` 当前已经是同一个 Supabase 项目还是不同?需要确认(写时观察)。建议:**dev / prod 用不同 Supabase 项目**,避免 dev 的脏数据污染 prod auth。

### Makefile 加目标

```bash
make ngrok            # 起 ngrok http 3000,打印出 URL
make ios DEV=ngrok    # iOS build 时把 ngrok URL 注入 VITE_API_BASE_URL
```

## 六、跟现状的兼容性

### 改动总览

| 层 | 改动 | 兼容办法 |
|---|---|---|
| DB | 新增 `pairing_codes` 表(migration 005) | 加表,不动现有 |
| `personal_signals` schema | **不动** | 列名已是 snake_case,跟 wire 对齐 |
| ingest handler | 接受新字段 + 老字段 fallback | `kind` ✓、`occurredAt`→`occurred_at`、`dedupeKey`→`dedupe_key`、新增 `source` 顶层 |
| ingest body 形态 | 顶层数组 + envelope 旧 `{deviceId, items}` | handler 同时接受两种 |
| 4 个 pair-code 接口 | 全新 | 加,无破坏 |
| Web Hardware Devices | "Add Hardware" 改成 Pair Code 输入框 | 保留 manual register tab 给 dev |
| 手机 App SDK | 新增(另仓库) | 复用 Web 端 `ensureDevice` 逻辑 |

### 不动的东西

- `personal_signals` / `raw.db.device_*_snapshot` 表 schema
- Composio / mobile_proxy / 其它 connector 路径
- timeline cursor pagination / DeviceTimeline UI
- 现有 device register / revoke / list 路径

## 八、决策记录

- **不叫 CloudEvents**:用户决定,因为我们是"个人 context 数据",不是通用云事件,不希望被 CE spec 锁。但精神同源(envelope + schemaless data + 必填骨架)。
- **没有 specversion**:加版本字段是 over-engineering 的开端。等真有不兼容改动再说。
- **没有 datacontenttype**:mime 在 payload 里足够。
- **没有 nice-to-have 层**:`salience`/`confidence`/`dedupe_key` 直接进 envelope 顶层,但端侧不强制填。
- **顶层数组而非 `{items:[...]}`**:跟工业界 batch 习惯一致。
- **6 位 code 而非 8 位**:用户体验优先;rate limit 抵消穷举风险。
- **Pair Code 不复用 OAuth Device Flow 完整规范**:full RFC 8628 引入 user_code/device_code 双层,我们简化成单 code,因为我们的设备和 server 之间没有 OAuth client 概念。
- **Supabase 始终用云端**:本地起 Supabase 不值得,Google OAuth callback 是硬性 HTTPS 要求。
