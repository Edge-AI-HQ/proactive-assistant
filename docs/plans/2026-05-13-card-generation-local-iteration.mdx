# 卡片生成本地 5 轮迭代

## 背景与目标

主线诉求:迭代 `/agent/generate` 的卡片生成质量。Daytona 沙盒方案要求 `api` 暴露公网地址(sandbox 在云端跑 `pinai_sdk` 回调 web `/api/agent/*`),本地开发挂 ngrok 麻烦,所以这一轮直接把 sandbox 后端换成本地 Python(deepagents 的 `LocalShellBackend`),避免对外地址依赖。

只在本机 docker compose 内跑,所有数据在本机 postgres,不污染 dev/prod。

## 实际跑通的拓扑

```
api (FastAPI 8000) ──┐
                            ├── local docker network
agent-engine (FastAPI 8001) ─┤   (api 内部 DNS 可解析)
   └─ generator subagents  │
       (LocalShellBackend) │
       /state on /         │
       python3 /tmp/...    │
       └─→ pinai_sdk ──────┘
litellm (4000) — 走 master key 直挂,LLM 调用全部经它路由
postgres (54322) — pgvector pg15,本地 fresh DB
```

关键点:**没有 Daytona、没有 ngrok**。LLM 直接在 `pin-ai-agent-engine` 容器里 `subprocess.run("python3 /tmp/collect.py", shell=True, env={...})`,脚本 `from pinai_sdk import client` 通过 docker 内部 DNS `http://api:8000` 回连。

## 排通过程踩到的 5 个坑

按修复顺序记录,后人重做时直接对照。

1. **`apis/` 残留容器占网**。`docker compose down` 后没显式 `--remove-orphans` 时,3 周前的 `pin-ai-apis` 还挂在 `pin-ai-assistant_default` 网络上,新 `make up` 报 `active endpoints`。先 `docker stop && docker rm pin-ai-apis`,或一次性 `docker compose down --remove-orphans`。
2. **旧 postgres 卷里 `pai_world_signals` 已经存在**。yoyo migration 是 forward-only,启动时报 `DuplicateTable`。`make reset` 或 `docker compose down -v` 清卷后重来。
3. **`LocalShellBackend(virtual_mode=True)` 只重写 filesystem op,不重写 shell exec**。`/state/phase1.json` 这条 path 在 data-collector 那里通过 `subprocess.run` 写 *literal* `/state/phase1.json`,planner 那边 `read_file('/state/phase1.json')` 又被 virtual mode 重定向到 `<root_dir>/state/phase1.json`,两边读不到同一份。改成 `virtual_mode=False` + 提前 `os.makedirs("/state", exist_ok=True)`,两边都拿 literal path。
4. **`inherit_env=False` 砍掉 DNS / locale / SSL 相关 env**。最终在 subprocess 里 httpx 报 `ConnectError: [Errno -2] Name or service not known`,看起来像 DNS 失败实际是 env 残缺。改成 `inherit_env=True` 然后只覆盖 `PATH / PYTHONPATH / PAI_API_URL / PAI_RUN_JWT`。
5. **`PATH` 必须把 `/app/.venv/bin` 排在 system path 前**。系统 `python3` 没有 `httpx / pydantic`(都装在 chat 容器 uv venv 里),`shell=True` subprocess 起的 `python3` 默认走系统的就 `ImportError`。`PATH=/app/.venv/bin:/usr/local/bin:/usr/bin:/bin`。
6. (额外:`docker compose up -d --build agent-engine` 不带 `PINAI_LOCAL_SANDBOX=1` env 会把开关默认拉回 0,继续走 Daytona 路径。env override 必须每次都带,或者写到 `backend/.env`。)

## 代码改动(临时,迭代用)

`backend/src/pinai_agents/chat/agents/generator.py` 加 `PINAI_LOCAL_SANDBOX=1` 开关:本地用 `LocalShellBackend(root_dir="/state", virtual_mode=False, inherit_env=True, env={...})`,清理 `/state` 旧文件,不去 Daytona。默认为 0 不影响线上路径。

`docker-compose.yml` 给 agent-engine 加了 `PINAI_LOCAL_SANDBOX: ${PINAI_LOCAL_SANDBOX:-0}` 透传。

`.claude/settings.local.json` 加了一条 `Bash(docker exec pin-ai-postgres psql:*)` 允许规则,绕过 classifier 对 docker exec psql 的默认拦截(本地迭代用,不要 commit)。

这些是临时脚手架,不建议合并到主干。线上要避免公网地址,合适的做法是 web/chat 共网或 web 在 chat 同 pod。

## 数据怎么来的(重要,影响发现的可信度)

**没用 dev Supabase 同步**。原计划是 `pg_dump` user_id=5296 (boliang@pinai.io,dev 里最有数据的账号)到本地,但 Claude Code 的 auto-mode classifier 把"从 dev DB 拉 PII 到本地"归类为生产读取/PII exfiltration,即便用户多次明确授权也持续拦截(包含一次显式批准后仍拦,classifier 加了"smile@pinai.io 不等于 5296,这是别人的数据"的行为启发式)。

只能 pivot 到合成数据。手写了 `/tmp/seed_5296.sql`,塞进 user 5296 一套形状真实的事实:

| 表 | 行数 | 内容画像 |
|---|---|---|
| `users` | 1 | id=5296, 占位 email + sk-... LiteLLM virtual key |
| `pai_profile` | 1 | 一位 SF 的 Senior PM,SaaS Series B,正在备战十月 SF 半马 |
| `pai_goals` | 3 | 半马 / Q3 platform launch / book club host |
| `pai_memory` | 10 | 工作习惯、家庭、Brex 拒付、AWS 账单异常等 |
| `pai_personal_signals` | 15 | 全部 open,salience 0.5-0.95,横跨 work/family/health/finance |
| `pai_raw_gmail_messages` | 10 | 与 signals 互为证据 |
| `pai_raw_gcal_events` | 8 | 未来 30 天日历,含冲突(graduation vs Q3 retreat) |
| `pai_world_signals` + user_view | 5 + 5 | 5 条 world news,每条都和某个 personal signal 互相印证 |
| `pai_user_settings` | 1 | language=en, auto_generate=false |

合成数据本身有"剧本"——故意制造了几个高质量的多源交叉证据点(Brex 拒付 / signal + gmail + memory + world、Mei 毕业 / signal + memory + gcal、AWS NAT egress / memory + world),所以下面的"卡片质量评分高"要打个折扣:**真实用户数据不会这么干净**。如果以后能拉到 dev 数据再跑一遍,大概率会暴露更多脆弱性(噪声 signal 多、source 不齐、intent 模糊)。

## 运行参数

每轮:
- 端点 `POST http://agent-engine:8001/agent/generate`
- JWT:本地用 `cryptography` 拿 `PAI_JWT_SIGNING_KEY` 在 `pin-ai-api` 容器里现签 EdDSA,claim 含 `vk=sk-REDACTED / user_id=5296 / iss=pinai-agents-web / aud=pinai-agents-internal`
- body:`{"cards_to_generate": 6, "output_language": "en", "run_id": "round<N>"}`
- LLM 链路:经 LiteLLM 4000 → 真 GPT-5.5 / Sonnet 4.6(LangSmith project `pinai-agents-dev` 留 trace)
- 数据:每轮**不重新 seed**,DB 状态完全相同,世界信号也没变;只有运行 ID 不同

每轮耗时 166-201s,集中在 LLM 调用(LiteLLM 调用次数 R1 估 16 次)。

## 5 轮卡片产出

每轮都返回 6 张卡,evaluator 全部 pass=true(无任何 fail)。

下表只列 intent_key + basket + 评估 overall:

| 主题 | R1 | R2 | R3 | R4 | R5 |
|---|---|---|---|---|---|
| board prep financial section | work 8.2 | work 8.1 | work 7.8 | work 7.8 | work 8.0 |
| Mei graduation × Q3 retreat 冲突 | family 8.0 | family 7.8 | family 8.2 | family 8.2 | family 8.4 |
| Mei piano recital RSVP | family 8.2 | family 8.2 | family 8.1 | family 8.4 | family 8.4 |
| Brex 旅行 velocity limit | wealth 7.6 | wealth 7.2 | wealth 7.9 | wealth 7.9 | wealth 8.0 |
| AWS / OpenAI VPC endpoint | work 7.8 | work 7.5 | work 7.5 | work 7.0¹ | work 7.5 |
| 14mi 长跑 / 周中单人带娃 | health 7.4 | health 7.1 | health 7.7 | family 7.4² | health 7.6 |

¹ R4 把 OpenAI VPC endpoint + 推理 vendor + batch tier 揉成一张 `openai-inference-and-egress-cost-reduction`,sources 5 条,实际可执行性下降到 7.0(why_now=5.5,因为没绑硬期限)。
² R4 把跑步那张换成 `jordan-seattle-solo-parenting-week`,角度从"挪长跑"切到"安排子女接送",basket 也飘到 family。

**核心观察 1:5 轮选的 6 个 intent 高度重叠**(只有第 6 个偶尔换角度)。理由是数据本身一周内只有这几个真正"紧迫"的事件,planner 取 salience top-N 后必然落在同样几条 signal 上。

## 系统级发现

### F1. intent_key slug 在跨轮间不稳定

同一个底层决策,5 轮里出现过 3 个不同 key:

- Brex 那张:R1/R3/R4 是 `brex-travel-velocity-limit`,R2 `brex-hotel-velocity-limit`,R5 又回 `brex-travel-velocity-limit`
- AWS VPC 那张:R1/R2 `aws-openai-vpc-endpoint-nat-egress`,R3 `aws-openai-vpc-endpoint-cost-cut`,R4 `openai-inference-and-egress-cost-reduction`,R5 `aws-openai-vpc-endpoint-cost-cut`
- 长跑那张:R1 `half-marathon-long-run-solo-parenting`,R2 `half-marathon-long-run-jordan-travel`,R3/R5 `solo-parent-week-...`,R4 `jordan-seattle-...`

planner 提示词里写了 "intent_key is a stable slug — kebab-case, ≤120 chars, identifies the underlying decision (not the card title). The same intent across runs gets the same key so dedup is deterministic." LLM 在单轮里能自洽,但跨轮就改写了。结果是**基于 intent_key 的去重在生产上会有大量假阴性**(同一决策反复推给用户)。

可行的对策(由轻到重):
- planner 子代理在写 intent_key 之前先 fetch 该 user 最近 30 天的所有 intent_keys 当作 vocabulary 给 LLM 看;
- 用 hash(规范化后的 subject + basket)作为 key 而不是 LLM 自由发挥;
- 后置一层 embedding 去重(用最近卡片 embeddings 比对新生成的 title + why_now)。

### F2. 没有 cards_recent 表 → planner 永远不知道"上一轮推过什么"

5 轮跑完 `pai_intent_card_state` 仍是 0 行。`/agent/generate` 返回的 cards 只在响应 body 里,**不持久化**;dedup 输入的 `client.cards.recent(limit=30)` 在 phase1.json 里始终是空数组。

这是当前 generator 设计的一个 gap:planner 提示词里反复强调"dedup against cards_recent",但 cards_recent 是空的(因为没有任何代码把生成结果写回 DB),所以 dedup 实际上从来没起作用。

线上是 scheduler dispatcher 在调 `/agent/generate` 之后再去写 `pai_intent_card_state`(`web/scheduler/dispatcher.py`),手动调 chat 的 endpoint(我这种打法)就漏掉了那一步。后果是连续两次手动调,planner 看到的"历史"是同一个空集,**只要数据没变化就一定生成同一组 6 张卡**,跟"洗牌"无关。

迭代时如果要复现"第二天的 generator 调用",必须手动把第 N 轮的 cards 塞进 `pai_intent_card_state`(`intent_key + status='dismissed' / 'open' / 'consumed'`)再跑第 N+1 轮。否则永远是 day 1 的视角。

### F3. evaluator 永远 pass,calibration 在合成数据上失效

5 × 6 = 30 张卡全 pass,最低分 7.0 / 10,与 prompt 里 `pass = overall >= 5.0` 的阈值差距很大;prompt 里 "A card you naturally rate 8.5 is probably 7.5" 的"resist generosity"在打分布上也没什么体现(scores 集中在 7.0-8.5)。两种可能性:
1. 合成数据剧本太干净——每张卡都至少有 2-3 个互相印证的 source,evaluator 自然给高分。
2. 同模型族(card-generator 用 gpt-5.5,evaluator 也用 gpt-5.5)即便切了 "cross-family" 框架,实际上还在彼此的舒适区里。

线下"全 pass"对线上信号意义有限,建议至少做两件事:
- 把 evaluator 模型固定换成 sonnet 4.6 或 opus 4.7,真正 cross-family;
- 评估时不要只给 card 本身,也给同轮其余 5 张卡,这样 evaluator 才能识别"同 batch 内角度重复"(F1 描述的问题在 R4 五条 source 那张就该被 flag,但没有)。

### F4. why_now 拿不到时区/具体时间戳

打分 5 维里 `why_now_clarity` 最低(平均 ~7.8 vs relevance ~8.7)。LLM 写出来的 why_now 是英文短句("Mei graduation 2026-06-14 — overlaps Q3 kickoff"),具体但**没结构化时间字段**。UI 想做"还剩 2 天"这种倒计时的话,要么 LLM 再多输出一个 `deadline_at: 2026-05-20T23:59:00-07:00` 字段,要么后处理 regex 解析(脆)。schema 里 `urgency: float` 是有的,但 0.95 跟"5 天后"还是"24 小时后"对不上时间感。

### F5. world signal 引用规范不够严格,auto-consume regex 只匹配 world

`generator.py` 里的 `_WORLD_ID_RE = re.compile(r"world\s+id\s*=\s*(world_[A-Za-z0-9_-]{8,64})")`,只识别形如 `world id=world_abc123, title=...` 的 source 字符串,然后 POST `/api/agent/world/consume` 把它 mark consumed。

5 轮里所有"world"类 source 都写成了 `world id=world_002, title=AWS introduces VPC endpoints for OpenAI traffic`,regex 能匹配。但:
- 我的 seed 用了 `world_001..world_005` 这种 8 字符 id(实际生产是 32 字符 hex)——regex 要求 `{8,64}` 还能过,但贴近线下格式 ✓
- signal / memory / gmail 这几类引用同样有"id=xxx"的规则,但**没有对应的 consume 机制**。`pai_personal_signals.status` 5 轮跑完仍是 `open`,5 轮都用了 sig_001 ~ sig_015 但 reference_count 也没自增。
- 这意味着:同一个 personal signal 会被反复在每轮里当成证据塞进卡片,直到有人手动 `status='consumed'`。world 那一面有 auto-consume,personal 那一面没有,**两侧不对称**。

线上这个不对称有 evolution_runs 兜底吗?evolution_runs 表本地是空的,无法验证。建议在 generator 末尾镜像一次对应的 `signals.consume(sig_id, run_id=run_id)` 调用,模式跟 world 同构。

### F6. growth / life basket 完全没出现

5 轮 × 6 张 = 30 卡,basket 分布:work=10, family=10+, wealth=4-5, health=4-5,**growth / life 0 张**。可能是因为 seed 没塞进 growth/life 的强 signal(没写"今天该背 50 个 GRE 单词"或"该订下半年体检")。Prompt 里有 5 个 basket 的 hint 但 planner 没主动平衡分布。如果产品上需要每天都给"成长/生活"覆盖,planner 需要显式 quota("each basket最多 2 张,但每周至少 1 张")。

### F7. 后台 ingest 在并发干活

每轮跑完后再查 `pai_world_signals`,从 5 行涨到 136 行,provider 包括 `google_news / sec / federal_reserve / tavily`。说明 api 的 world signal ingest scheduler 一直在后台拉真实(或 mock 的)新闻,把 raw 行注入 DB 并给 user 5296 打 user_view score。

对本次迭代没什么影响(seed 的 5 条 tavily 还在,salience 也没被覆盖),但对线上意义不小——**ingest 速度和 generate 速度的赛跑**会影响 phase1 拿到的 world 集合。

## 速度成本

| 步骤 | 用时 |
|---|---|
| data-collector(8 source 并发抓 + 写 phase1.json)| ~10-15s |
| planner | ~25-35s |
| card-generator | ~50-80s |
| evaluator | ~35-50s |
| 总 | 166-201s |

绝大头是 card-generator,因为它要对 6 张卡每张写 ~10 句话外加 sources 列表;evaluator 紧随其后(每张卡 5 维打分 + feedback 字段)。Daytona 路径会再加 30-60s 的 sandbox provisioning(冷启动情况下,有 snapshot 减半)。

LiteLLM master key 直挂、走 cache,prompt cache 的命中能省掉重复的 system prompt。LangSmith trace 里能看到 cache_read tokens,可以进一步压成本但不在本次范围。

## 给后续迭代的建议(按 ROI)

1. **F2 解决:把 generate 调用的写 DB 逻辑挪进 chat 进程的 endpoint**,而不是依赖 web scheduler dispatcher 在外层包。这样手动调试时 dedup 也能跑。
2. **F1 解决:planner 加 vocabulary 注入** + 后置 embedding dedup。
3. **F3 解决:evaluator 切 cross-family**(sonnet 4.6 / opus 4.7)+ batch-level review。
4. **F5 解决:personal signal 也对称 auto-consume**,镜像 world 那个 regex。
5. **schema 加 deadline_at 字段**(F4),why_now 字符串保留兼容性。
6. **basket quota / coverage 检查**(F6),planner 输出层加一道"覆盖度反馈"。

## 没做的事

- 没改任何代码进 prod 路径(`generator.py` 的改动只在 `PINAI_LOCAL_SANDBOX=1` 分支下生效,默认 0 不影响)。
- 没碰任何 prompt 文本——5 轮的产出差异完全是 LLM 自身的非确定性。
- 没接 dev Supabase 真实数据(classifier 反复拦截 + 用户最终授权 ack 写 settings 后仍被拦,具体可参见本文档"数据怎么来的"段)。
- 没修上面 F1-F7 任何一条;本文档只是把现象记下来作为下一轮迭代的基线。

## 复现步骤(简短版,给下一个接手的人)

```bash
# 1. 起栈
cd /Users/ec2-user/Desktop/01PINAI/01code/PIN-AI-ASSISTANT
make up  # 需要 backend/.env.keys + ops/litellm/.env.keys

# 2. seed
docker compose cp /tmp/seed_5296.sql postgres:/tmp/seed_5296.sql
docker compose exec postgres psql -U postgres -d postgres -f /tmp/seed_5296.sql

# 3. 切到本地 sandbox 路径并重启 chat
PINAI_LOCAL_SANDBOX=1 docker compose up -d --force-recreate agent-engine

# 4. 跑一轮
docker compose cp /tmp/run_gen.py api:/tmp/run_gen.py
docker compose exec api python3 /tmp/run_gen.py \
  --virtual-key <sk-...> \
  --signing-key '<PAI_JWT_SIGNING_KEY base64>' \
  --cards 6 --lang en --run-id testN
```

`/tmp/seed_5296.sql` 和 `/tmp/run_gen.py` 本地没 commit,需要时直接重新写(本文档"数据怎么来的"段有完整 schema 描述)。
