# Sunset 本地 LLM + Ambient 语音端侧化(RN 单端版)

状态:**PR1(删端侧 LLM)已实施**(2026-07-11,见文末「实施状态」);PR2(语音端侧化)待决策 E/F 确认后开工。本文是该项工作的设计 + 实施 SSOT。

版本历史:v1(2026-06-21)基于 Capacitor + RN 双端基线;v2(2026-07-07)加入语音隐私反转(端侧转文本);**v3(2026-07-11)Capacitor 已 sunset(#256 删 proactive-ai-frontend + capacitor-plugins,RN 接管 iOS 交付),按 RN 单端 repo 重新定标——删除范围收敛到一套 native module + 一个 app,且删 LLM 变成零功能损失**。

## 动机(为什么)

**① 删掉「端上跑大模型」的死重。** RN 迁移(#221/#251 等)把 Capacitor 时代的端侧 LLM 栈整套搬进了 `apps/mobile/modules/ambient-models/`(ModelManifest/Downloader/Store/Verifier + LlamaTextGenerationEngine + 下载管理 UI + onboarding 下载步),**但 llama.swift SPM 从未接线**——`AmbientModels.podspec:17-19` 注释明说推理接线留给「Milestone C」,`#if canImport(LlamaSwift)` 恒 false。后果:**当前生产 RN 里用户能下载 0.6–2.6GB GGUF,但 LLM 推理永远不可用**——下载功能是纯死重(白占用户存储),本地 summary 桥是显式 `native_unavailable` stub(`apps/mobile/src/ambient/summary-bridges.ts:6-19`)。删除 = 零功能损失 + 用户存储回收。

**② 反转 ambient 语音隐私(2026-06-21 用户需求,方向不变)。** 用户要求:被动 ambient 录音不允许上云,必须端侧转文本、只有文本上云。当前 RN 现状仍相反:ambient 整段 WAV 上传 → 云端 `gpt-4o-transcribe(-diarize)`(`apps/mobile/src/ambient/sources/sound-classifier.ts:317,334,344`)。休眠的 SFSpeech 端侧转写(含 `requiresOnDeviceRecognition` 硬保证)是激活目标。

**核心约束:不影响当前功能形态。** 采集 / Silero VAD / SoundAnalysis / 录音存盘 / `captureReady` / 云端 summary / 主聊天语音全部保留。

### 保留 Silero VAD 的依据(不变)

唯一消费者 `AudioStreamManager.swift:35`,被动录音语音门控;~2MB 运行时自动缓存,无 UI 无管理;删它退化 RMS 门控 → 误触发/垃圾录音上涨。**语音端侧化后更重要**:它决定 SFSpeech 的工作量与耗电。

## 关键技术事实(行号为 2026-07-11 RN 代码)

1. **ambient-models 自包含**:JS 消费者仅 5 个文件(`summary-bridges.ts` / `models-selection.ts` / `timeline/models.ts` / `AmbientModelSetupStep.tsx` / `AmbientModelsPanel.tsx`),全在删除/改造范围;native 侧是独立 Expo module(pod `AmbientModels`),无其它模块 import。删后编译无悬空引用。
2. **core pipeline 的 modelBridge 机器现在只有 RN 一个消费者**(`apps/mobile/src/ambient/timeline/pipeline.ts`;Capacitor 消费者已随 #256 消失),且该路径在 RN 从未成功产出(LLM 不可用 → `!result.ok` 分支)。因此 v3 不再用 v2 的「注入 Noop」最小方案,**直接删 core 的 modelBridge 机器**:`pipeline.ts:59,66` bridge 参数、`:158-244` LLM 生成分支、`pipeline-models.ts` 的 LLM bridge 类型;窗口记账(attempt/backoff)与 LLM 解耦的部分实施时以代码为准决定去留。`pipeline.test.ts`(1401 行)随之重写(最大测试改动面)。
3. **SFSpeech 休眠实现具备硬隐私保证**:`modules/ambient-audio/ios/AudioStreamManager.swift:872` `request.requiresOnDeviceRecognition = requireOnDevice`;激活时恒 true——locale 不支持端侧就不出转写,**绝不回退云端**。多 locale(zh/en)候选、置信度、分块(`:747` 起)齐备。
4. **端侧转写复活管线 native 侧现成**:`AmbientAudioModule.swift:41` 已暴露 `transcriptReady` 事件、`:104` `drainPendingTranscripts`;facade 类型 `TranscriptProvider` 含 `local_speech`(`modules/ambient-audio/index.ts:113` 事件已注册)。PR2 只需 JS 侧消费 + 掐断 WAV 上传,信号 schema(`session_summary`)不变。
5. **`local_llm` 枚举值保留**:历史卡片(Capacitor 时代真产出过并已上云)用它,下游读取/映射不动,只删产出路径。
6. **VoicePcmStream 与 ambient 物理隔离**(文件头注释:chat dictation 持 external-mic lease 时 ambient 被抑制,独立 AVAudioEngine,never writes WAV captures)——决策 E 的「主聊天保留云端流式」不与 ambient 隐私目标冲突。
7. **质量代价(不变,诚实声明)**:中英混说 SFSpeech < `gpt-4o-transcribe`;Phase 2 切 iOS 26 SpeechAnalyzer/SpeechTranscriber 缓解;隐私 > 质量是明确取舍。
8. **成本收益**:ambient 每个 speech burst 省一次 `gpt-4o-transcribe(-diarize)`;下载死重回收(用户侧最多 2.6GB/模型)。

## 影响分析

**零功能损失(v3 比 v2 更干净)**:RN 里 LLM 推理从未可用——timeline 本就全靠云端 summary 出卡,action candidate 从未产出,隐私锁本就无本地兜底。删除只回收死重。

**变好的**:① ambient 录音不再出设备(PR2,Apple API 硬保证);② 隐私锁期间转写照常本地进行,文本排队解锁补传;③ 省 `gpt-4o-transcribe(-diarize)` 持续成本;④ 用户不再被引导下载几 GB 永远跑不起来的模型。

**变差的(接受)**:① 中英混说转写质量下降(PR2 起,Phase 2 SpeechAnalyzer 缓解);② ambient 暂无 speaker 标签(决策 F,Phase 2 补)。
