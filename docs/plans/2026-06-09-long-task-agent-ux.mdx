# 长任务 / 多 Agent 对话体验优化实施计划

> **实施状态（2026-06-10）**：P0 / P1a / P1b / P2 / P3 已全部实现于 PR#75（checkbox 不逐项回填，以 PR 为准）；其中"报告回执行"实施时砍掉（见 P3 节标注）、归属字段收窄到只在 start 帧（见 P1a.1 标注）。P3 的 summarization 产品化提示（可选项）与 P4 未做。

**Goal:** main chat 跑长任务（deep research 类，4 个并行 subagent、200+ 工具调用、30-60 分钟）时，用户能看懂"现在在干嘛"：内部机制输出（summarization）不再泄漏成回复；assistant turn 渲染为 Claude.ai 式的 **text 叙事主线 + work group（thinking/工具/task 卡合流的垂直 rail，AI 生成组标题，完成后坍缩成一行）**；200+ 子工具调用被 4 张 task 卡吸收；TodoPanel 按 turn 生命周期管理，不被 subagent 内部 todos 覆盖、不跨对话残留。

**Architecture:** 不动 actor kernel / RedisFrameBus / resumable SSE 底座（已是业界正确形态）。改动集中在三层：`chat/transport/sse.py`（langgraph 事件 → SSE 帧的过滤、归属标注、组标题生成）、`web/services/chat_turn_recorder.py`（归属/标题/链接字段持久化）、前端 `components/chat/conversation/`（WorkGroup/rail 新渲染体系 + TaskCard + TodoPanel 生命周期）。三条设计纪律贯穿全部任务：

1. **帧协议只加可选字段**；归属、组标题、结构化链接都是 best-effort 增强——任何环节拿不到时帧不带新字段 / 用确定性 fallback，前端回落平铺渲染，不引入新失败模式（progressive enhancement）。
2. **数据层保持平铺**（parts 数组形态不变，直播帧与落库 parts 同构，注解经回填字段挂在既有 part 上），分组/嵌套只发生在渲染层重组（React derived view）。
3. **异步注解绝不阻塞主流**：组标题（Haiku）异步生成、淡入替换 fallback；text 流式渲染永远不等任何注解。

**Tech Stack:** deepagents 0.6.7 / langchain 1.3.2 / langgraph 1.2.2、FastAPI SSE、LiteLLM（标题用 Haiku 档 alias）、React + Vite + framer-motion、vitest + pytest。

## Decisions Locked（2026-06-09/10 拍板）

- **前端信息架构采用 Claude.ai work group 模式**：text 段是叙事主线；text 之间连续的 reasoning + 工具调用 + task 卡合流为一个 work group，左侧垂直 rail 串联，完成后整组坍缩成一行 AI 标题 + Done。原"ChatToolGroup 降噪 + 独立 ReasoningBlock"方案废弃。
- **组标题用小模型生成**（Haiku 档，经 LiteLLM，本 run 的 virtual key 计费）：组封口时异步调用，确定性 fallback 兜底；小组（parts < 3 且无 task 卡）不调用。
- **task 卡是 rail 上的一等节点**：subagent 的 200+ 子工具按归属收进各自 task 卡（折叠态一行：description + spinner + 计数 + 当前动作），点开看子 rail。task 卡标题用 `args.description`，不调 Haiku。
- **thinking 展示**：流式时 rail 节点滚动窗口显示最新 1-2 行；该段结束折叠成首句一行；点开看全文。
- **进度叙事 prompt 要做**（输出风格层，非行为约束）：引导 agent 在长任务阶段之间输出一两句进度文本——这是组粒度成立的前提。plan-first（先报计划等用户确认）仍暂不做。
- **todos 是 turn 级计划**：随 turn 结束收尾，不做跨 turn 任务清单。TodoPanel（composer 上方全任务进度）与组标题（已完成段落概括）并存、不重复。
- **Tavily 配额已修**（2026-06-09）；代码侧失败语义修复仍要做。
- **实现层细节（2026-06-10 定）**：① task 子 rail 移动端**内联展开** + max-height 内部滚动（复用 TodoPanel `max-h-[200px]` 模式），不做 bottom sheet（不引入 portal/手势体系）；② Haiku 标题的语言锚 = **用户本 turn 消息原文（截断 ~200 字）带进标题 prompt**，要求"用与用户消息相同的语言"（不做语言检测库，不信 thinking 语言——prod 实证 thinking 会漂英文）；③ 坍缩动画：text 渲染不等任何动画，组坍缩 250ms height 过渡（现有缓动 `[0.32, 0.72, 0, 1]`），fallback 标题即时显示、Haiku 标题到达后 200ms cross-fade 替换，滚动跟随沿用现有"贴底才自动滚"逻辑。
- **实施顺序 P0 → P1a → P1b → P2 → P3**；P4（astream_events v3）等 beta 稳定再评估。
- summarization 泄漏用 **SSE 层过滤**修复，不替换 deepagents 内置 middleware（替换需 `HarnessProfile.excluded_middleware` 全局注册 + 子类注入，副作用面大，收益为零）。

## 背景：prod 实证（为什么要做）

2026-06-10 03:26 UTC，prod main chat（`pai_chat_messages` id=114，user 113 "deepreearch一下上面这个内容"）一个 turn 跑了约 1 小时，落库 213 个 parts / 196KB：

| parts 顺序 | 内容 |
|---|---|
| 1-2 | reasoning + `write_todos`（主 agent 写 4 项调研计划） |
| 3-4 | reasoning + **text(3687字)**：开头是 summarization 内部输出的 "## SESSION INTENT / ## SUMMARY / ## ARTIFACTS / ## NEXT STEPS" 全文，结尾拼着主 agent 真实回复"并行调研所有主题：" |
| 5-8 | 4 个 `task` 调用（general-purpose subagent 并行：Google 全家桶 / ASR refine / agent 权限 / credit 定价），4 个全部返回完整 research summary |
| 9-210 | 202 个工具调用 = 4 个 subagent 内部调用混流：88 browser_tool + 54 execute + 30 tavily_search + 17 write_todos + 6 world_search + 6 tavily_extract + 2 grep + 1 read_file |
| 211 | **text(4349字)**：主 agent 综合的 Deep Research 报告 |
| 212-213 | write_todos（全部 completed）+ text(364字) 补充 insight |

暴露的问题：

1. **summarization 泄漏**：thread 超 170k tokens 触发 deepagents 内置 SummarizationMiddleware，其内部 summary LLM 调用被 `sse.py` 当成主 agent 输出流给用户（`chat:delta`）并持久化。
2. **工具混流**：4 个 subagent 的 202 个工具调用平铺成一个 "Used 206 tools" 组，无归属，前端 200+ chip 全量渲染（stagger `delay: index*0.06`，第 200 个 chip 延迟 12 秒）。
3. **task 结果显示成 repr**：task 的 tool result 是 `Command` 对象，`sse.py:340` 的 `getattr(output, "content")` 拿不到 → meta 存成 `Command(update={...})` repr 截断 300 字符。subagent 的产出对用户几乎不可见（实际结果已正常回传主 agent）。
4. **Tavily 静默全挂**：30 次 tavily_search 全部返回 `{'error': Exception('Error 432: ')}`（配额），UI 30 个绿勾，agent 无明确失败信号，被迫 88 次 browser_tool + 54 次 sandbox execute 硬爬，turn 时长爆炸。根因：`langchain_tavily/tavily_search.py:434-435` 把 API 异常吞成 `return {"error": e}` 正常返回值（空结果才 raise ToolException），永远走不到 error 路径。
5. **TodoPanel 横跳**：17 次 write_todos 来自主 agent + 4 个 subagent（各有独立 TodoListMiddleware），前端不分来源全部 `setTodos` → 主计划被 subagent 内部 todos 轮番覆盖，进度数字横跳；turn 结束后 panel 永久挂着，下一次普通对话还在。
6. **过程叙事缺失**：整个 turn 中间只有一处 text，工作过程对用户是 200+ chip 的黑盒滚屏（最终报告其实生成了，但被工具流淹没）。

## 目标体验（work group + rail）

> 用户发"deepresearch 一下"→ 主 agent 简短回复研究计划（text）→ **work group 出生**：rail 上 thinking 滚动窗口 → write_todos → 4 张 task 卡并列（各自 description + spinner + 子工具计数跳动 + 当前动作行），组顶部状态行实时显示"4 个子任务进行中" → agent 阶段间输出进度 text，**组封口坍缩成一行 AI 标题**（"完成四个主题的并行调研"）+ Done → 下一组… → 最终报告全宽呈现 → composer 上方 TodoPanel 全程显示总进度，turn 结束自动收起 → 全程刷新/断线无损（replayFrom 重放重建组状态），SESSION INTENT 这类内部输出永不再现。
>
> 完成后回看（history）：text 叙事主线 + 若干行坍缩的组标题，点开任意组看 rail 全景，点开 task 卡看子 rail，web 搜索结果是 favicon + title 可点击列表。

### work group 流式状态机（设计 SSOT）

`streaming → settling → done`：

- **streaming**（组出生：第一个非 text part 到达）：整组展开，rail 逐节点生长。主 rail 每组通常 <10 节点（200+ 子工具被 task 卡吸收，这是"流式可全展开"成立的前提）。标题区显示**确定性状态行** = 当前活跃节点的人话动作（原 P3"状态行"吸收于此）。thinking 节点滚动窗口 1-2 行；task 卡折叠态实时跳计数/动作；普通工具单行打 ✓；web 搜索类完成显示 "N results"。
- **settling**（text 开始流入 = 组封口）：组坍缩成一行标题 + Done；**异步**发起 Haiku 标题调用（输入 = 组内 thinking 首尾截断 + 工具清单 + task 结论 meta，输出 ≤20 字用户语言完成时态概括）；返回前显示确定性 fallback 标题（"完成 6 个步骤 · 搜索网页 · 4 个子任务"），返回后淡入替换。text 流式渲染不等标题。
- **done / 异常**：组级红标来自组内工具的 `isError`（turn 级 `chat:error` 已有独立错误文本渲染，不重复染组徽标——实现时收窄）；HITL interrupt → 组不封口，resume 后继续生长；断线重连 → replayFrom 全帧重放，组状态纯由帧序列推导，自然重建；最后一组标题赶不上 `chat:done`（见 P1a flush 机制）→ 永久 fallback 标题，history 一致。

## 机制依据（deepagents/langgraph 源码实证）

源码路径根：`pinai-agents/.venv/lib/python3.12/site-packages/`。以下结论均经 probe 脚本在真实 `create_deep_agent` 图上实证（2026-06-09）。

### summarization

- prompt 模板（`## SESSION INTENT` 等四个标题）硬编码在 `langchain/agents/middleware/summarization.py:34` `DEFAULT_SUMMARY_PROMPT`；deepagents `create_deep_agent` 默认装配（`deepagents/graph.py:740`，subagent stack 也有，graph.py:595）。
- 我们的 model 经 LiteLLM `ChatOpenAI` 无 profile → 默认 `trigger=("tokens", 170000)`、`keep=("messages", 6)`（`deepagents/middleware/summarization.py:202-209` `compute_summarization_defaults`）。触发判定是"近似计数 OR 最后一条 AIMessage 的 `usage_metadata.total_tokens` ≥ 阈值"双路（langchain 版 389-437）。
- **库已打标**：summary LLM 调用传 `config={"metadata": {"lc_source": "summarization"}}`（`langchain/agents/middleware/summarization.py:656-659`）。astream_events 里该调用的 start/stream/end 事件 `metadata.lc_source == "summarization"`——这是过滤依据。
- **为什么是"流式打字"泄漏**：astream_events 注册 streaming callback handler 后，`BaseChatModel._should_stream` 返回 True，`ainvoke` 内部转成流式逐 token 跑（`langchain_core/language_models/chat_models.py:2072-2106`）→ 产生 on_chat_model_stream 事件序列。
- **不能用 namespace 区分**：summary 调用发生在主 model node 的 `wrap_model_call` 里，checkpoint_ns / langgraph_node 与主 model 调用完全相同（实证）。
- deepagents 包装版是 **non-mutating**：`request.override(messages=...)` 只改本次模型输入，state["messages"] 不动，压缩进度记在 state 私有字段 `_summarization_event`（跨触发复用 cutoff，链式压缩）；被压缩历史 offload 到 backend `/conversation_history/{thread_id}.md`。
- **与 PR#71 `compact_thread` 的分工**（2026-06-10 main 已合入，`chat/harness/compaction.py`）：compact_thread 是 **turn 后**跑的 mutating 压缩（150k tokens / 200 messages 触发、keep 12 turns、`RemoveMessage(REMOVE_ALL)` 物理重写 state），调用点在 `chat/transport/routes/chat.py` 的 `langgraph_to_sse` 流**结束之后**——其 `_summarize` LLM 调用（非流式 ainvoke）不经过事件流，**不会泄漏进 SSE**，无需过滤。内置 SummarizationMiddleware 退为 **turn 中途的 170k backstop**（main_chat.py:284 注释）——单 turn 内 200+ 工具结果冲过 170k 时（prod msg114 正是此场景）仍会触发，**P0.1 的过滤防的就是这个 backstop 的泄漏**。两者都打 `lc_source=summarization` 标（compact 的 summary message 复用该标避免内置 middleware 二次 offload）。

### subagent / task 归属

- deepagents 自动注册 `general-purpose` subagent（`deepagents/middleware/subagents.py:425`，工具 = 主 agent 全集）；我们 `main_chat.py:288` 传的 `subagents=[_ECHO_PROBE_SUBAGENT]` 是叠加。
- task 工具 args schema 只有 `{description, subagent_type}`（subagents.py:267-277）；返回 `Command(update={..., "messages": [ToolMessage(content=<subagent 最终文本>, tool_call_id=...)]})`（subagents.py:527-532）；`on_tool_end` 的 `data["output"]` 是**原始 Command 对象**。
- 并行语义：每个 task tool_call 一个 `Send("tools", [tool_call])`（`langchain/agents/factory.py:1763`）→ 同 superstep 的多个 Pregel task **asyncio 真并发**。
- **归属字段**（事件 `event["metadata"]`）：
  - `langgraph_checkpoint_ns`：全路径，段格式 `<node>:<task_id>`、分隔符 `|`（`langgraph/_internal/_constants.py:87,89`）。subagent 子图内所有事件首段 = `tools:<task_id>`。
  - `lc_agent_name`：subagent 名（declarative 经 `create_agent(name=...)` 注入，`langchain/agents/factory.py:1663-1666`；主 agent 未传 `name` 时为 None）。
  - **ns → task toolCallId 的关联点（2026-06-10 实测修正）**：`task` 自身的 `on_tool_start` 事件 ns 就是子图根 ns（单段 `tools:<pregel_task_id>`，且先于所有 nested 事件）——映射记**该帧的 run_id（= 帧 toolCallId）**。⚠️ 教训：最初用 on_chain_start Send 载荷里的 **LLM call id** 做 parentTaskId，与帧 toolCallId（langgraph run id）是**两个 id 命名空间**，前端配对永远 miss（prod 实测 task 卡 0 tools 全平铺）；单测当时与实现一致地错——真不变量是"parentTaskId 必须等于某个已发出 task 帧的 toolCallId"，现有测试与 E2E probe 已锁住。
  - `parent_ids` **不可用**（子图 run 与 task 的 tool run 是兄弟不是父子，实证推翻直觉）；`ls_agent_type` 不在 metadata allowlist（`langchain_core/runnables/config.py:289-300` 只复制 `model` 和 `checkpoint_ns`）。
- **嵌套判定**：`len(ns.split("|")) >= 2`。注意主 agent 自己的工具事件 ns 也是单段 `tools:<id>`——现有 `_is_subagent_model_event`（sse.py:237-250）的 `"tools:" in ns` 只对 model 事件碰巧正确（主 model ns 是 `model:<id>`），**复用到 tool 事件会误杀主 agent 工具**。

### 工具错误语义（P0.2 依据）

- `langchain_tavily` 的 `TavilySearch` / `TavilyExtract` 自带 `handle_tool_error: bool = True`（tavily_search.py:240）；空结果 raise `ToolException`（:429）走 error 路径，但**其它异常被吞成 `return {"error": e}`**（:434-435）。
- LangChain convention：`raise ToolException` + `handle_tool_error=True` → BaseTool 层捕获 → ToolMessage `status = "error"`（`langchain_core/tools/base.py:1120-1125`），**不会**冒泡炸 turn（不经过 ToolNode 的 handle_tool_errors 层）。

### todos

- 主 agent + 每个 subagent 各有独立 `TodoListMiddleware`（graph.py:713/660/589）；state 字段 `todos`，`write_todos` 返回整表替换的 Command。
- **双向隔离**：task 入口剔除父 todos、出口剔除子 todos（subagents.py:534-540, 504）——subagent 的 todos 不污染主图 state；**但其 write_todos 工具事件照常出现在主事件流**（前端混流根因）。
- 主图 todos 随 checkpointer **跨 turn 持久**，库无任何清理（todo.py 全文件）→ 残留是确定行为。

### turn 重建（P2 简化依据）

- `/api/conversation/history` 对 in-flight run 返回 `active.replayFrom` = 该 run 第一帧**之前**的 stream entry id（`web/routes/ui/conversation.py:366-378`）；前端把它设为 lastEventId（`useConversationRuntime.ts:802-803`）→ XREAD 重放**整个 turn 的全部帧**（thinking / deltas / tools / 注解帧）。即：进行中 turn 的 write_todos / 组标题等状态由帧重放经正常路径自动恢复，**不需要独立的 history 回填通道**。

### 业界 UX 模式（要点）

完整调研含来源 URL 见本 plan 末尾"调研来源"。可移植结论：

- **没有头部产品给用户看 agent 树或全量工具流水**。Claude.ai Research 后端 3-5 并行 subagent，前端聚合为单一研究叙事；Claude Code 每个 subagent 一行折叠卡（描述 + 实时工具计数 + 完成后 "Done (17 tool uses · 56.6k tokens)"）。
- **Claude.ai work group 解剖**（用户提供截图，2026-06-10）：text 叙事主线之间，连续的 thinking + 工具调用合并为可折叠组——AI 生成的概括性组标题（与 thinking 原文语言无关，跟随用户语言）+ 左侧垂直 rail 串联 thinking 段（时钟 icon）/ 工具卡 / Done（✓）+ web 搜索展示 query + "9 results" + favicon/title/domain 可点击列表。真实运行完成后组是坍缩态。
- **三层披露**：默认人话状态行 → 点开看步骤 → 再点开看原始调用（Perplexity 原则："信息在用户好奇之前不上屏"；其案例研究实证"看得见进度，用户就愿意等"）。
- **长任务三件套**：开跑声明预期时长 → 可离开（服务端继续 + 推送拉回）→ 报告与过程物理分离，过程坍缩为一行回执。
- **todo 模型**（Claude Code）：`pending/in_progress/completed` + 单一 in_progress + 进行时文案；对话型产品把 plan 放消息流内/composer 上方 sticky，**任务结束自动收起**。
- 移动端：砍常驻侧栏，状态一眼可见 + 完成推送；明细用 bottom sheet。

## 风险与待确认

- `lc_source` metadata 是 langchain 私有约定（非公开 API），升级 langchain 时需要 grep 确认仍存在（`summarization.py` 搜 `lc_source`）；Task 0.1 的单测同时是回归门。
- `on_chain_start name=="tools"` 的 Send 载荷形态依赖 langchain create_agent 的 per-tool-call Send 实现（factory.py:1763），升级时同样需要回归（Task 1a.1 的"降级回归门"单测覆盖：载荷变形 → 帧回落现状形态，不报错）。
- 组标题质量依赖 Haiku 对中英混合上下文的概括；上线后观察实际标题质量，不满意再调 prompt / 换档（配置项已留）。
- 进度叙事 prompt 是软引导，模型不一定每个阶段都输出 text——组粒度退化为大组时 rail 仍可用（task 卡吸收主要体量），不算失败模式。
- checkpoint 体积已由 PR#71 `compact_thread`（turn 后 mutating 压缩）治理；内置 SummarizationMiddleware 仅剩 turn 中途 170k backstop 角色，P0.1 防其泄漏。两套 summarization 的分工见机制依据节。
