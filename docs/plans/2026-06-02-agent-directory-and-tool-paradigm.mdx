# Agent 目录结构 + 工具范式重构

> **状态**：实施计划（已拍板，全套一起做，分 4 个 PR 有序推进）。
> **范围**：chat agent 的**目录结构**（框架/业务分层）+ **工具范式**（native @tool / Code Mode / pinai_sdk codegen）+ 相关 **prompt 更新**。不动 context/白屏（已在 PR #22 修复）、不动 Composio 副作用门（搁置）。
> **关联**：[2026-06-01 agent 架构重构研究](./2026-06-01-agent-architecture-redesign) 的 **§13 facade 四层** —— 本文是它的**目录化落地**；[工具调用范式选型](./2026-05-04-tool-calling-paradigms) —— 本文修正其「chat 纯 native / 离线 code mode」的分工为「两个场景都开放双范式、模型自选」。
> **对标**：Claude Code（工具自包含 + 核心抽象顶层）、Anthropic「Code execution with MCP」(2025-11)、Cloudflare Code Mode、smolagents CodeAgent。

## 一、动机 + 已拍板的三个决策

**动机**：当前 `chat/` 按「技术类型」分目录（agents/runtime/tools/routes/browser），**框架适配（deepagents/langgraph）和业务逻辑混在一起**；一个能力「三处手写」（`/api/agent/*` SSOT + native @tool + pinai_sdk）要同步维护；目录没体现「框架 vs 业务」这条 pinai 独有的边界。

**已拍板**：
1. **codegen SDK** —— `pinai_sdk` 改成从 `/api/agent/*` 的 OpenAPI 自动生成，消除三处手写同步。
2. **Code Mode 进 main/card 双范式** —— native tool 和 Code Mode 都开放给对话场景，**让模型自己选**；prompt 更新讲清选择标准。
3. **全套一起做** —— 目录重构（含 facade 逻辑）+ codegen + 双范式 prompt，分 4 个 PR 有序推进。

## 二、当前诊断

### 2.1 目录：框架和业务混在哪

| 层 | 现在散落在 | 问题 |
|---|---|---|
| **框架适配**（import deepagents/langgraph） | `runtime/`（llm/checkpoint/trim/ctx/reasoning）、`streaming.py`、各 `agents/*.py` 的 `create_deep_agent(...)` | `runtime/` 命名含糊；构建逻辑在 6 个 agent 文件里重复 |
| **agent 业务定义**（prompt + 配置） | `agents/*.py`（和框架调用**焊在同一文件**）、`agents/prompts/` | spec（业务）和 factory（框架）未分 |
| **业务工具** | `tools/native/*`、`tools/sandbox.py`、`browser/*` | `browser/` 顶层独立；`tools/` 混了 native(direct) + code-mode 执行 + http_client |
| **传输 HTTP/SSE** | `routes/*`、`streaming.py` | `routes/history.py` 直接 `aget_state`、`chat.py` 直接 `astream_events` —— 传输层直接碰 deepagents 内部（违反 facade 铁律） |

### 2.2 工具：一个能力「三处定义」

```
/api/agent/*  (web/routes/agent/*)   ← 业务 SSOT(真正访问 DB)
     ├── chat/tools/native/*.py      ← 手写薄壳(http_client) → chat agent direct call
     └── packages/pinai_sdk/_client.py(895行,手写) → Code Mode 在 sandbox import
```
`regen_sdk.py` 已规划 `openapi-python-client` codegen 但**还没做**（现在 `--check` 只验证存在）；native 和 sdk 是两份独立手写。

### 2.3 Code Mode 现状（诚实校正：main/card 已有，不是从零加）

- `main_chat.py` / `card_execution.py` **都已 import `CODE_MODE_GUIDANCE` + `SANDBOX_PREAMBLE`**，`_INSTRUCTIONS` 已嵌；`backend` 是 Daytona thread sandbox。
- thread sandbox 镜像 **baked `pinai_sdk`**（`sandbox.py:246-251`：slim Python 3.12 + pinai_sdk preinstalled，`from pinai_sdk import client` 可用）。
- **结论：对话场景的 Code Mode 链路已完整可用**。当前 prompt 引导偏「批量/多源才用 Code Mode」（`tool_routing` 里 ">5 calls prefer Code Mode"）。本次诉求 = **把它明确成「模型自主在 native / code mode 间选择」+ 给清晰标准 + 延迟权衡**，不是新建能力。

## 三、业界对标（为什么这么做）

- **Code Mode 是前沿且 Anthropic 自己推**：Anthropic「Code execution with MCP」(2025-11) —— ① tool 定义按需 import 不全量进 context；② 中间结果在执行环境处理只回结论；③ 循环/条件用代码原生表达。Cloudflare Code Mode、smolagents CodeAgent 同方向。→ pinai 的 SDK Code Mode **范式正确**。
- **Claude Code 的目录 convention**：核心抽象顶层显眼（`query.ts`/`Tool.ts`/`context.ts`）；**每个工具自包含一目录**（impl + prompt + test 放一起）；`services/` 按能力分。但它**没有「框架 vs 业务」二分**（它本身是框架）。
- **pinai 独有约束**：trust boundary 把一个能力劈成两半 —— 「数据访问」(web route，持 DB 凭证) vs 「agent 接口」(native/sdk，chat 进程)。所以 pinai **没法像 Claude Code 那样把一个能力完全自包含在一个目录**（跨进程了）。这是接受的现实复杂度。

## 四、目标架构

### 4.1 目录（chat 侧四层 + 独立 sdk 包）

```
chat/
  app.py  asgi.py  trust_boundary.py        # 进程入口 + 安全(横切)
  auth/                                       # 鉴权

  harness/    ← 【框架适配层】唯一 import deepagents/langgraph(facade)
    __init__.py   对外: build_agent(spec) / stream_turn() / read_history()
    factory.py    create_deep_agent 封装(6 个 agent 抽出的构建逻辑)
    llm.py  reasoning.py  checkpoint.py  ctx.py
    context.py    trim(原 runtime/trim.py)
    events.py     langgraph event → 中立 AgentEvent(从 streaming.py 抽前半)

  agents/     ← 【业务定义】AgentSpec + prompt,不 import deepagents
    main_chat.py  card_execution.py  generator.py  dream.py  evolve.py  crystallize.py
    prompts/

  tools/      ← 【业务工具】两个范式分清
    direct/     native @tool(可 review,薄壳调 /api/agent/* 或 sdk)   [现 native/]
    code_mode/  Code Mode 执行器(sandbox.py / local_sandbox)+ SDK cheat sheet 注入
    browser/    浏览器工具(从顶层 chat/browser 并入)
    http_client.py

  transport/  ← 【HTTP/SSE】前端只认这层
    routes/   chat / generate / history / run + browser routes
    sse.py    中立 AgentEvent → SSE 帧(从 streaming.py 抽后半)

packages/pinai_sdk/   ← 独立 wheel,sandbox pip install(不进 chat/,位置不变;codegen 收敛在这)
```

一眼可见：**`harness/` 是框架（锁住 deepagents），`agents/`+`tools/`+`transport/` 是业务**。`pinai_sdk` 必须留 `packages/`（Daytona sandbox 装它，chat 进程不装）。

### 4.2 工具范式（模型自主选）

| 范式 | 适用 | 代价 |
|---|---|---|
| **native @tool**（direct） | 单步、可 review、低延迟（直接 HTTP）。日常单次查询/操作 | 多步要多轮 tool call |
| **Code Mode**（sandbox + sdk） | 多源聚合、批量、大中间结果需 filter/reduce、需循环/条件 | 起 sandbox 有冷启动延迟；用户看不到 sandbox 内部（可 review 弱） |

两者**同源** `/api/agent/*`；prompt 给模型清晰 heuristic 自选。

## 五、四个 PR 的方案

### PR-A：SDK 契约同步 + native 复用 sdk（修正：契约测试，不全 codegen）

> **为什么不全 codegen（review 推翻原方案）**：手写 sdk 是**对象式** `client.memory.list()`（8 resource / ~40 method），agent 的 Code Mode 脚本 + `SDK_CHEAT_SHEET` + `SANDBOX_PREAMBLE` 全依赖它。`openapi-python-client` 默认生成**函数式** API（`from pinai_sdk.api.memory import list_; await list_.asyncio(client)`），全 codegen 替换会破坏对象式 API（所有 code mode 脚本失效 + cheat sheet 重写 + LLM 不友好），改回对象式要重度 custom template = 反而 hacky。

- **改用契约测试守同步**（解决「三处漂移」这个真痛点，零形态破坏）：手写对象式 sdk **保留**；新增 CI 契约测试 —— 启 transient web（`uvicorn pinai_agents.web.asgi:app`）取 `/openapi.json`，校验每个 sdk 方法映射到真实 endpoint（path / method / 必填参数 / response 形状）；`/api/agent/*` 改了而 sdk 没跟 → CI 红。`regen_sdk.py` 从「codegen」改成「契约校验」。
- **`SDK_CHEAT_SHEET`** 保持手写，由 `test_sdk_cheat_sheet_sync` + 上面的契约测试共同守一致。
- **native @tool 复用 sdk（你拍板的方向）+ 修 auth 串号（P0-2）**：让 sdk `_Client` 支持 **per-call token 注入**（构造时传 token，默认 fallback `PAI_SANDBOX_TOKEN`/`PAI_RUN_JWT` env）。**必须**：sdk 现在「读进程 env 单 token」对 sandbox 单租户 OK，但 chat 是多用户并发、token 在 per-request ContextVar —— native 若用 env-token sdk 会**跨用户串号**。chat native 用 ContextVar token 构造 client；sandbox 仍用 env default。native @tool 退化成「sdk 调用 + LLM-facing description」，`http_client` 的手写 IO 由 sdk 取代。
- **chat 装 sdk**：`packages/pinai_sdk` 加进 chat 进程依赖（editable / path install）。增量依赖小（httpx + pydantic 已有）；但要确认不把 sandbox-only 的重依赖带进 chat。
- **风险**：契约测试要处理 endpoint 仍在动（drift 即红是预期）；per-call token 改造要覆盖 sdk 所有 `_Endpoint`。

### PR-B：目录重构 Step A（机械移动，低风险）
- `runtime/` → `harness/`；`browser/` → `tools/browser/`；`tools/native/` → `tools/direct/`；`tools/sandbox.py`+`local_sandbox.py` → `tools/code_mode/`；`routes/` → `transport/routes/`；`streaming.py` → `transport/sse.py`（**整体移动，内部不拆**）。
- **中立 AgentEvent 中间层暂不引入**（P1：当前单一 SSE + langgraph，新增事件类型层是 YAGNI）。`langgraph_to_sse` 保持现状移到 `transport/sse.py`；facade 的可替换性靠 `harness` 的接口边界保证，不靠新增事件类型。真要换 transport/runtime 时再抽中立层。
- **纯移动 + 改 import，不改逻辑**。CI（ruff/mypy/test）守等价；grep 确认无残留旧 import 路径。

### PR-C：facade 逻辑 Step B（= §13 Phase 2，有行为风险）
- `agents/*.py` 拆 **AgentSpec（业务：prompt 段 + tool 集 + subagent + context 策略）+ `harness/factory.py`（框架：`build_agent(spec)` 封 `create_deep_agent`）**。
  - **generator 特殊处理**（P2）：它是复杂编排（orchestrator + 4 CompiledSubAgent + 各自 response_format），不套简单 spec —— 只把 model/backend/checkpointer 的构建走 factory，编排逻辑（task 顺序、子 agent 组装）留在 `agents/generator.py`。
- **范围是 chat 侧 routes**（P2 澄清）：web 的 `/history`+exists 已由 PR #22 改成读 `pai_chat_messages`、不碰 `aget_state`；本 PR 处理 **chat 进程** 的 `transport/routes/chat.py`（`astream_events`）和 `history.py`（backfill 用的 `aget_state`），改调 `harness` 中立接口。
- 加 ruff `flake8-tidy-imports.banned-api`：**`agents/` / `tools/` / `transport/` 禁止 import `deepagents` / `langgraph` 内部**（仿 web↔chat trust boundary 守法）。
- **风险**：行为变化（state 读取、流式翻译挪位）；充分跑 chat 测试套件 + dev 端到端。

### PR-D：双范式 prompt 更新（依赖 PR-A 的 sdk）
- 现状：main/card 已有 Code Mode，但引导偏「批量才用」。改成**模型自主选 native vs code mode**，给清晰 heuristic（见 §六）。
- **延迟 nuance（P2 校正）**：thread sandbox 是 **per-thread 复用**的（LRU），只有首次冷启动有几秒延迟、后续复用很快 —— prompt 引导「简单查询用 native」主要是省那次冷启动 + 保可 review，不是「每次都慢」。
- 确认对话 sandbox 的 sdk 是 PR-A 改造后（per-call token）的版本。
- **可观测（可选）**：Code Mode 在对话场景把关键步骤回传成 tool event，缓解「用户看不到 sandbox 内部」（对应 Claude Code「工具服务于可 review」）。

## 六、prompt 更新方案（具体）

1. **新增「工具范式选择」段**（共享片段，main/card 都用，可并入或紧邻已有的 `TOOL_DISCIPLINE`）：
   > 你有两种工具范式，自己判断用哪个：
   > - **直接工具调用**（memory_search / signals_recent / Composio meta …）：单步、即时、用户能看到每一步。**默认用它** —— 日常查询、单次读写、需要用户审阅的操作。
   > - **Code Mode**（在 sandbox 写 Python，`from pinai_sdk import client`）：当一件事需要**多源聚合（3+ 来源）、批量处理、对大中间结果做 filter/reduce、或循环/条件逻辑**时用。一个脚本一次跑完，只把结论带回。
   > 取舍：Code Mode 起 sandbox 有几秒冷启动、且 sandbox 内部用户看不到 —— **简单的事别用 Code Mode**，能一两个直接工具搞定就别写脚本。
2. **更新 `CODE_MODE_GUIDANCE`**：从「批量才用」改为上面的「模型自主选 + 延迟/可见性权衡」。
3. **更新 `tool_routing`**：把 ">5 calls prefer Code Mode" 这类硬阈值换成「按上面的范式选择段判断」。
4. 和已落地的 `TOOL_DISCIPLINE`（并行读 / 结果反思 / write_todos）协调，不重复。

## 十、安全：跨用户隔离不变量（重构必须保持）

本次重构（目录移动 + facade + 双范式）**不能削弱**下列隔离防线；facade 反而让边界更清晰、更易审计。

**现有防线**：
- RLS（20 张 pai_ 表，含 `pai_chat_messages`）+ `user_scoped_tx(pool, user_id)` set `app.user_id`。**注意：RLS 靠纪律 —— 漏 `user_scoped_tx` → service_role catch-all 裸奔（跨用户全权）。用户数据访问必走 `user_scoped_tx`。**
- run JWT（HS256 验签，含 `user_id`，**不含 session_key**）；ContextVar per-task 隔离（chat 多用户并发）；sandbox phantom token 绑 user + 防提权。
- `session_key` 形如 `main-<user_id>-<rand>` / `card-thread-<card_id>`，user_id 编码在 main session_key 里。

**🔴 已知 P0（重构前应修，独立小安全 PR，不 over engineer）**：
- `chat_send` / `chat_history` **不校验 session_key 归属**（`_classify_session_key` 只在 `chat_init` 调）；langgraph checkpoint **无 RLS**；`/history` backfill 从 checkpoint 读再写进调用者库 → **绕过 RLS 的跨用户泄露链**（A 传 B 的 session_key 可读 B 历史 / 对话）。
- 修复（复用已有机制，不造权限框架）：① web `send`/`history` 加 `_assert_thread_owned` —— `user_scoped_tx` 查 `pai_chat_threads` 归属（RLS 自动隔离），不属于 → 403；② chat 层纵深：`session_key` 前缀 user_id == `principal.user_id`（main thread）。

**重构落地约束**：
- facade（PR-C）搬 `user_scoped_tx` / ContextVar / RLS 链路时不能断；harness 收敛 deepagents 后，**session_key 归属校验在 `harness` 唯一入口统一做**（比散在各 route 更易审计）。
- sdk per-call token（PR-A）是**防 chat 多用户串号的安全必需**，非可选优化。
- service_role 绕 RLS 的点（`embeddings` / `devices` / payment webhook / `jwt_revoke`）需逐一确认是合理用途（catalog / webhook / admin），不在重构中误扩散。
