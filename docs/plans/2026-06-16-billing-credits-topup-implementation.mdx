**与本计划的差异(已验证更优):**
- 三个 repository 落在 `web/payment/`(free-function,对齐 `subscriptions.py`),非原计划的 `db/repositories/` class-style——它们是 webhook/scheduler 跨用户**服务侧写入**,reconcile 要一次 claim 多用户窗口,class-style 绑单 user 不合适。
- `sync_litellm_budget_for_plan` 保留为委托 `recompute_litellm_budget` 的**薄壳**(不碰 Phase 1 代码及其测试),而非删除重接。
- 新增 migration **102**(`max_budget_cents_at_open`)原为对账安全网而加;新用户在 `litellm_provisioning` 首开窗口(100 backfill 只覆盖迁移时已存在用户)。
- **invoice.paid 改为 `recompute(reset_spend=False) + set_period_end(NOW())`**:把 spend reset 的归属交给对账(否则 invoice.paid 直接 reset 会丢掉旧窗口的消费归因)。比设计原文「invoice.paid 直接 reset」更正确。

**对账用量来源修正(2026-06-17,验证后):** 原 SSOT 的「读 `budget_reset_at` 跳变 → 保守按上限扣」安全网在稳态会**误伤**:LiteLLM 的月度 auto-reset 锚在自然月 1 号、与对账窗口不对齐,每个账期都在窗口中途把 `key.spend` 清零,于是 `(closing − opening)` 计数器差值不可靠、安全网几乎每个账期触发,按上限满扣 → 把用户已购 credits 全额清空(零使用也清)。**修复:窗口 LLM 用量改从 `LiteLLM SpendLogs`(append-only、按请求留痕、不受重置影响)按 `[period_start, period_end)` 求和**(`client.sum_spend_for_key_window` 走 `/spend/logs`,日聚合、end 日期 EXCLUSIVE,相邻窗口干净切分)。`reset_detected` / 保守满扣分支已删;窗口收尾仍 `recompute(reset_spend=True)`,但只服务实时 `max_budget` 拦截、不再参与计费归属。`max_budget_cents_at_open` / `last_seen_reset_at` / `opening_litellm_spend` 列因此退化为审计/历史字段(reconcile 不再读),可后续迁移清理。回归测试:`test_reconcile_low_usage_keeps_credits`(零使用保住 credits)。

**浏览器 / 沙箱算力进 credits(2026-06-17 新增):** Browserbase 浏览器会话 + Daytona 沙箱算力之前不计 credits,现已接入(走和 ASR 同一条 `pai_provider_usage_events` → 对账 → credits 的路)。计量口径 = **按活跃使用时长 × 单价**:chat 进程把时长 fire-and-forget 上报到新端点 `POST /api/agent/usage/record`(`current_chat_principal` 鉴权,只上报时长、不报金额),web 侧用 `estimate_compute_charge` 按单价折成 cost 写 provider_usage(端点对时长做 6h 上限防滥用)。**两条路都覆盖了**(Mengli 拍板:用户用了多少就计多少):
- **交互式**(用户聊天里 agent 主动用):`browser_tool` 动作 / `LazyThreadSandbox.aexecute` 的 `finally` 上报,JWT 走 `current_run_jwt` ContextVar。
- **后台任务**(dream / crystallize / evolve,平台自动跑):one-shot 沙箱走的是另一条路(不经 LazyThreadSandbox),所以在各 agent 的 create→delete `finally` 里按沙箱生命周期上报。**这些跑在 `/agent/run/*`、不在 `run_context` 里,所以 JWT 必须显式传**(`report_compute_usage(run_jwt=...)` → `http_client.post_with_jwt`);crystallize 之前没接 run_jwt,这次从路由 `_verify` 取出来透传(仅用于计费归属,**不**传给 `create_oneshot_sandbox`,以免改动它的 phantom token 行为)。

**单价已按真实厂商价定**(2026-06-17 查实:Browserbase ~$0.12/browser-hr、Daytona 2vCPU/4GB ≈ $0.166/run-hr),`provider_usage.py` 的 `COMPUTE_USD_PER_MINUTE` 取约 2× 成本加成:**browser $0.004/min、daytona $0.005/min**(改 margin 只改这一处)。长期靠「精确计量每用户用量 × 我方单价,再用月度厂商发票做总账校准」收口,不靠推测。口径说明:计的是「活跃使用时长」(动作/exec 墙钟 + one-shot 沙箱 create→delete),不是整会话墙钟——交互式会话空闲(浏览器开着没操作、沙箱 auto-stop 前的 60min 空转)不计;one-shot 跑完即删、无空转尾巴,活跃≈运行。

**挂死兜底(2026-06-17):** one-shot run(dream/crystallize/evolve)的 `agent.ainvoke` 套 `asyncio.wait_for(timeout=ONESHOT_AGENT_RUN_TIMEOUT_SEC)`(默认 10min,env 可调,在 `sandbox.py`)。若某次 run 卡死(如沙箱回连不上 web,in-sandbox SDK 调用阻塞),超时即取消 → `finally` 强删沙箱 + 上报计量 + 返回降级结果,**不再无限挂着烧算力到厂商 60min auto_stop**。回归测试:`tests/chat/agents/test_dream_timeout.py`。端到端验证(本地真栈):用量→credits 扣费、实时端点真签 JWT 落行计价、chat 容器内真实 reporter→web、真起 Daytona 沙箱 + dream finally 真上报,均验通;真机自然触发(需 ngrok 让沙箱回连)未在本地跑。

**本期未做(范围决策 + 设计 out-of-scope):** 方案 B 的 ASR 实时进 LiteLLM(ASR 仍在 `pai_provider_usage_events`,对账已汇入窗口总额,计费不丢,故 `/usage` 仍保留 provider_usage 求和);整会话墙钟计费(当前是活跃使用时长);自动续充;阶梯折扣;EU/UK 退款。

**前端补齐(2026-06-18):** Subscription 面板已接入一次性充值 UI(预设 20/50/100 + 自填)、top-up 成功后 billing history 可展示 `pai_credit_grants` 充值记录、payment method 可展示 Checkout 使用过的 Link / card、plan credits 与 extra credits 分桶展示。其中 plan credits 不由前端硬编码,而是读 `/api/payment/usage.planAllowanceCredits`(DB open budget window 的 `allowance_cents`)。

## 范围决策(2026-06-16,Mengli 拍板)

**本期只做 credits 充值核心;ByteDance ASR 暂留 `pai_provider_usage_events`。** 理由:对账 job 本来就把 provider_usage 的 ASR 花费汇入窗口总额(SSOT 第 171 行),所以 ASR 计费不丢,只是少了「实时按 max_budget 拦 ASR」这一层(ASR 很便宜,两次对账间最多多花几分钱)。

- **不做(本期 out of scope):** 方案 B 的 ASR 实时口径(自定义 LiteLLM 回调把 ASR 按时长进 key.spend)。因此 **`/usage` 继续保留「加 pai_provider_usage_events」那段**(SSOT 第 162 行说落地方案 B 后才去掉——本期不去)。
- **充值前端 UI** 已在 2026-06-18 补齐(桌面本地 Vite 粗看,真机验收仍按 proactive frontend 流程由用户验证)。

**Architecture:** 新增 3 张表(`pai_credit_grants` / `pai_budget_periods` / `pai_credit_consumption_events`)+ 3 个 repository;新增唯一预算写入口 `recompute_litellm_budget`,收编现有 5 处 max_budget 写法;新增脱 Redis 的 `budget_reconcile` loop;新增 `POST /api/payment/topup` + webhook topup 分支;修 webhook claim 独立事务洞;接线升级/降级/取消/过期。

**Tech Stack:** Python / FastAPI / psycopg async / Stripe SDK / LiteLLM REST / yoyo SQL migration / pytest。
