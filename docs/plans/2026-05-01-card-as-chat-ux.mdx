# 执行层 Plan 2:Card-as-Chat UX 深化

> **状态**:brainstorm 草稿,**等 [Plan 1(chat-driven 执行 + Tier 工具政策)](./2026-05-01-execution-chat-driven) 上线稳定后再开**。
>
> **关系**:Plan 1 在执行层把 state machine 砍了,chat agent 自由度恢复。Plan 2 在 UI 层把"卡片"和"chat"统一成同一个 thread。两个 plan 解决的是不同的问题 —— Plan 1 解决工具滥用,Plan 2 解决用户体验。

## 一句话

`Card Detail = Chat Thread`。今天用户点卡 → 进 CardChat 页面;Plan 2 之后用户点卡 → 直接进入这张卡的对话 thread,所有交互(看进度、起草修改、选项确认、browser 接管、复杂多轮对话)都以"消息"形态发生在同一个 thread 里。Feed 里的卡片是 thread 的精简预览。

## 产品定位

卡片定位是 **"已经做完一半、等你审批的半成品"**:agent 在卡片 thread 里已经做完所有可逆的准备(查邮箱 / 查日历 / 查 memory / 起草内容),用户审批后再调不可逆的写动作。thread UI 把"做了什么"和"等什么"以 message 形态自然铺开 — 用户不需要先读 metadata 再去 chat 里看 agent 在干嘛。

跟传统 agent 卡片(Naro 模式)的差异:Naro 把 plan / trajectory / draft 设计成卡片元信息字段,用户在静态 UI 里读;PIN AI 用 thread 单一容器,所有 metadata 是 message,用户对话即修改。

## 为什么要做

Plan 1 上线后执行回到 chat-driven,但 UI 层会暴露一个不一致:

- chat 是开放对话 surface,任何工具调用 / 副作用确认都在对话流里完成。
- 卡片 detail 还是 v2 那种"上方卡片元信息 + 下方工具栏 + 下方进 CardChat 按钮"的形态,不像一个对话容器。
- 用户体验上的认知负担:"这张卡的状态是不是要从卡片上看?还是 chat 里看?同一个事在两边显示有冲突怎么办?"

Plan 2 的目标是让卡片本身**就是 chat thread**(card 视为 thread 的"精简元信息条 + 完整对话区"),消除两个 surface 的歧义。

## 边界与所有权

| 数据 / 决策 | 真源 | 本计划怎么改 |
|---|---|---|
| `intent_cards` (Generation) | Generation | 不改。 |
| chat session(`chat:card:<intent_card_id>`) | Execution | **成为 card 的执行真源**。card 状态不再独立存,从 thread 末尾消息推断。 |
| 卡片在 feed 里的形态 | Frontend | 改:加状态徽标(active / awaiting_user / done / dismissed),从 thread 状态推断。 |
| 卡片 detail UI | Frontend | 改:detail = thread 视图,顶部精简元信息条不消失。 |
| chat agent / 工具政策 | Execution(Plan 1) | 不改。Plan 1 的 chat agent 直接复用。 |
| Browser tool / browser SSE | Execution | 不改实现;改 UI 把 browser 面板内嵌进 thread 作为 message 类型。 |

**硬边界**:本计划只动 UI 层。不改 chat agent / 工具政策 / pin CLI / browser tool 实现。

## 关键决策(待 Plan 1 上线后细化)

### 1. Feed 形态:卡片预览 + 状态徽标

feed 里每张卡仍然是当前形态(title / why now / summary / sources)。**新增**:

- 状态徽标(基于 thread 末尾消息):
  - `agent_thinking` — agent 在跑工具,流式输出中(蓝色 spinner)
  - `awaiting_user` — agent 起草了内容/选项等待用户回应(黄色 ⚠️)
  - `done` — 用户确认完成 / 用户标记已读(绿色 ✓)
  - `failed` — agent run 异常 / chat:error(红色 + 重试入口,点徽标 inject 一条 user message "请重试")
  - `idle` — 卡片刚进 feed,没人点过(灰色,无徽标)
- preview 增加"agent 起手语"一行(thread 第一条 agent 消息的前 60 字符,如果存在)。

### 2. Card Detail = Thread 视图

### 3. Rich Message 类型(在 thread 里以特殊 UI 渲染)

| 类型 | 触发条件 | 长什么样 |
|---|---|---|
| **`text`** | 普通 agent / user 文本 | 现有形态(MainChatView 已支持) |
| **`tool_call`** | agent 调任何 pin / browser / web fetch | 折叠的灰色卡:"Ran `pin raw gmail recent`",点击展开看 args + envelope |
| **`draft_preview`** | agent 起草邮件 / 日程 / Slack 消息 | 内嵌可编辑的 preview 卡,带 [Edit] [Confirm-and-Send] [Discard] 按钮 |
| **`option_chips`** | agent 显式抛出二选/多选问题(如"周二 / 周三 / 周四 哪天?") | 一行可点击的 chip;点击后等同于用户文本回复(把 chip label 当 user message 提交) |
| **`browser_embed`** | agent 调 browser tool | 内嵌 browser 面板 + control mode 切换(像现在 `/browser/events` 的 panel,但作为消息存在 thread 里) |
| **`completion`** | agent 完成副作用动作(发了邮件、建了日程) | 绿色 ✓ 卡:"Sent email to sarah@... at 14:32",带原始 draft 链接 |

#### draft_preview 修改强约束(写进 chat agent prompt)

用户在 thread 里说"语气改正式点 / 把日期换成周五 / 加一句 X" 时,agent 应该输出
新的 `draft_preview` message 替换上一条。这一行为容易出问题:agent 顺手"优化"
未提到的字段、补全用户没要的内容、或在不确定时乱猜着改。Plan 2 把 4 条规则
写进 chat agent system prompt(跟 Plan 1 的 Tier policy 同一个 stable prefix):

1. **只改用户明确提到的字段**。其他字段绝对不动 — 不"顺手优化"、不"补充更
   全面"、不"重新润色已经定稿的部分"。
2. **不擅自添加内容**。用户说"语气改正式点",只改语气,不能再加一句"另外
   要不要问问对方周末方不方便"。
3. **不确定时输出澄清问题**(普通 `text` message),不要乱猜着改。
4. **如果改动涉及任务参数**(收件人 / 日期 / 范围 / 目标),agent 应该重新跑
   Tier 1/2 拉新数据再改 draft,不直接基于旧 draft 字段改。用户指令在新一轮
   中是最高优先级,覆盖原 draft 的任何继承字段。

这 4 条规则跟 Plan 1 的 `<side_effect_rules>`(draft → user OK → send)互补 —
Plan 1 管 "送出前必须 OK",这 4 条管"修改 draft 时 agent 行为收敛"。
高风险副作用(`*_DELETE_*` / `*_TRANSFER_*` 等)的 UI 层 modal 兜底见
§5 §高风险副作用 段。

### 4. 状态推断:thread 末尾消息 → card 状态

不存独立 `card_executions.state`,直接从 chat session 末尾消息推断:

| Thread 末尾 | Card 状态 |
|---|---|
| 流式输出中(`chat:done` 还没发) | `agent_thinking` |
| `tool_call` 等待中 | `agent_thinking` |
| `text` 由 agent 发,且包含问号或 `option_chips` / `draft_preview` 待操作 | `awaiting_user` |
| `text` 由 agent 发,无明确询问 | `idle`(用户可继续聊或离开) |
| `completion` message | `done` |
| 用户主动 dismiss / snooze | `dismissed` / `snoozed`(走现有 feedback 路径) |

实现方式:后端推 chat SSE 时附加一个 `card_status_hint` 字段,前端 reducer 收到后更新 feed 列表上的卡状态。

### 5. 复杂场景

#### Browser captcha / OAuth

- agent 调 `browser open` → 在 thread 里渲染 `browser_embed` 消息
- 用户在 embed 里直接操作 browser(完成 captcha / 登录 / 多步交互)
- 用户操作完后点 embed 里的"我搞定了"按钮 → 后端 emit `browser:user_done` → agent 续跑

#### 多轮对话(用户在草稿上反复修改)

- 自然走 thread:agent 出 draft → user 回"再短点" → agent 改 draft → user 回"OK 发吧" → agent 调 SEND
- 不需要新 UI,普通 chat 流程

#### 高风险副作用(`*_DELETE_*` / `STRIPE_CHARGE_*` / `*_TRANSFER_*`)

- agent 在 prompt 引导下先停下问用户(Plan 1 已落地)
- UI 层 Plan 2 加一道:这类工具调用前弹一个 modal,要求用户**显式键入**确认词("DELETE THIS EVENT" / "CONFIRM TRANSFER")才放行
- modal 不替代 agent 的 prompt 引导,是兜底

#### Mid-execution agent 卡住("我不知道下一步该怎么办")

- agent 输出 `option_chips` 让用户选(常规)
- 用户选完 → chip label 当 user message 推回 thread → agent 续跑
- 需要复杂回答时用户直接在文本输入框回

### 6. Feed 的"已读"/"未读"语义

- 用户点开 card 进 thread 视为"已读"(card 状态从 `idle` 变 `active` 或 `awaiting_user`)
- 用户在 thread 里发任何消息或点过任何 chip → 视为"engaged"
- thread 末尾 `completion` message 出现 → 视为"done"
- feed 排序优先 `awaiting_user` > `agent_thinking` > `idle`(新)> `done`(已完成,沉到底)

## 附属:Tier 4 工具合并(架构层,与 UI 主线独立)

**背景**:Plan 1 落地后实测(2026-05-02)暴露 Tier 4 内 web vs browser 的选择问题 —— prompt 软约束把"先 web fetch 再 browser"的规则化升级到 chat agent prompt + `routes/chat.ts` 拦截 hook(commit `5f4ce449`,Tier 4 two-step 规则)后,case 覆盖率显著提升,但**判断仍然由 LLM 做**。任何 prompt + 拦截规则都不是 100% 命中,边角 case 总会绕过去。

**真正消除 LLM 判断的方案**:把 `pin web fetch` 和 `browser` 合并成单一工具 `read_web`,内部走 fallback chain:

```text
read_web(url, intent?)
  1. fetch URL via existing pin web fetch path (cheap, ~3s)
  2. classify response:
       - 200 OK + text/html / text/plain / json / markdown + body 充实  → 返回 fetch 结果(textOrPreview + meta)
       - 401 / 403 / login redirect / WWW-Authenticate                   → 升级 browser
       - 200 OK + body 几乎空(JS-only SPA shell,< 200 chars 实质内容)→ 升级 browser
       - 415 / blocked content-type                                       → 升级 browser
       - response 含 "captcha" / "cf-challenge" 标记                       → 升级 browser
  3. when 升级 browser,自动 open + snapshot,返回跟 fetch 同 schema 的结果(text 字段统一,
     是 fetch body 还是 a11y snapshot 由 meta.upgraded 字段标识)
  4. 后续交互动作(click / type / wait / etc.)仍走原 browser tool;`read_web` 只接管"打开 + 拿首屏内容"这一阶段
```

**为什么放在 Plan 2(UI 层)旁边**:Plan 2 的 thread UI 渲染 tool_call 时,`read_web` + 升级 browser 的链路最自然嵌进同一个 message — 一条 tool_call message 显示"read_web https://... → upgraded to browser (login wall)",用户视图清晰、agent 视图统一。如果先做 `read_web` 再做 thread UI,工具事件的渲染会过两次重写。所以两件事一起做。

- **2-X.2**:新工具 `read_web` 注册 + 内部 fallback chain 实现。`agents/chat.ts` Tier 4 改写。`pin SKILL.md` 同步。删 `shouldInterceptBrowserFirstCall` Rule 2。
- **2-X.3**:前端 `ToolActivityCard` 渲染 `read_web` 升级链路。跟 Plan 2 主线 2-A 合并实施。

### 风险 / 决策

| 风险 | 缓解 |
|---|---|
| classification 误判("body 充实"判错把 SPA shell 当作 ok)| 加保守阈值(< 500 char 实质内容算 sparse);加 `--force-browser` flag 让 agent 显式覆盖 |
| `read_web` 屏蔽 browser open 后,需要"打开 dashboard 进行交互"的 case 被强制走 fetch 失败再升级,白绕一圈 | agent prompt 提示:已知是 dashboard / 私人页面 / 已知需要登录的场景,可以**直接**带 `intent='interactive'` flag 调 `read_web`,跳过 fetch 一步直升 browser |
| browser tool 仍然存在(interactive 阶段),Tier 4 政策又复杂化(read_web vs browser actions)| 文档 + prompt 必须清晰:"打开页面 = `read_web`;打开后的 click / type / fill 等 = `browser` actions"。SKILL.md 配两个反例 |
| 现有 `shouldInterceptBrowserFirstCall` Rule 2 删后,如果 `read_web` 链路失败,agent 直接调 browser open 的 case 回归 | 保留 Rule 1(zero pin grounding 拦);Rule 2 不需要,因为 fetch 阶段失败本身就是 inline reminder |

### 关键决策

| 决策 | 选什么 | 原因 |
|---|---|---|
| 单工具(`read_web`)vs 两工具(`pin web fetch` + `browser`)+ rule | **单工具** | rule 永远靠 LLM 自律 90%+ 命中;单工具消除"选择"这一步,100% 命中 |
| `read_web` 包揽 click / type 等 vs 只接管"打开 + 拿首屏" | **只接管打开 + 拿首屏** | interactive actions 形态完全不同(snapshot ref + click ref);不要把"读"和"操作"塞进一个工具,否则 description 又开始膨胀 |
| 何时做 | **跟 Plan 2 主线 2-A 合并实施** | UI 渲染逻辑(tool_call message)跟 `read_web` 升级链路天然配对,分两次做会过两次 |
