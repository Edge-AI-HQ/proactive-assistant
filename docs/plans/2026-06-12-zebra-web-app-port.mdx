## 实施结果与偏差（2026-06-12）

- M0-M5 按计划完成；用户中途拍板把「纯复制」改回「下沉共享」，最终形态 = `packages/ui-web`（~40 个模块下沉，frontend 全部留 shim 旧路径不变）+ `apps/web`（zebra 壳）。
- **注册点模式**（composition root 注入，替代 props 改造）：`registerSignOutCleanup`（devices 清理）/ `registerFeedbackOutbox`（离线 outbox）/ `registerLocalThreadStore`（本地同步 history/notify）/ `registerExternalMicAcquirer`（ambient 麦克风互斥）。frontend main.tsx 注册 native 实现，apps/web 不注册 = 纯网络路径。
- **实施偏差（均按「frontend 为真源」仲裁）**：
  - CONNECT / MIRROR / SETTING 用 production 全功能件（ControlPanel / GoalsView / settings sections + 从 AccountPanel 抽出的 SubscriptionPanel）装进 zebra 阅读列；zebra 原型的桌面 grid/并排重排留给视觉迭代轮。
  - zebra 的 paywall 面板（Apple Pay mock）没有移植——真实订阅 = SubscriptionPanel（Stripe checkout/portal/cancel/invoices）。`Intent.locked` 真卡不会置位，paywall 路径自然不触发。
  - zebra 的 reflection 卡分支是 mock 设计（真实 IntentCard 无此 kind），不移植。
  - AMBIENT 只读 = consent 状态卡 + `DeviceConnections`（设备 registry + 云端 timeline，与 CONNECT 同源组件）；不下沉 AmbientView（深耦合 native 采集链）。
  - TASKS 右 pane 自治：在 /tasks 上下文 approve/chat 落在右 pane（onOpenChat 路由），其余场景全局 560px slide-over。
- **测试迁移**：源码断言测试（readFileSync）路径已指向 ui-web 真实文件；ui-web 自带 vitest 配置（jsdom + frontend 同款 setup）。

## 背景与端形态战略

- **web 端**：本计划的产物 `apps/web`，zebra 桌面设计 + 真实功能，长期保留。
- **iOS**：当下继续走 Capacitor（`proactive-ai-frontend`）；等 React Native 方案（`apps/mobile`，PR#127 一线）成熟后下线 Capacitor。
- **macOS**：`apps/desktop`（Electron）目前 renderer 复用 proactive-ai-frontend；未来切到以 apps/web 为基础，**本计划不做**。
- zebra 设计稿在独立原型仓 `proactive-pin-ai-c7be7ecc`（Lovable 导出，Vite + React 18 + shadcn/ui），全部数据是 mock。本计划只取它的**视觉与布局**，功能行为一律以 proactive-ai-frontend 现有实现为真源。

## 已拍板决策（2026-06-12，用户确认）

1. **共享策略 = 下沉到独立共享包**：新建 `packages/ui-web`（`@pin-ai/ui-web`），存放 Capacitor iOS（proactive-ai-frontend）与 apps/web 双端共享的 React DOM 组件和平台 hooks。**独立 folder，不与 core/state 混放**；core/state 维持纯协议层/纯 query 层定位不变。两端尽可能复用能复用的模块。
2. **下沉方式 = move 不是 copy**：模块从 `proactive-ai-frontend/src/` 移入 `packages/ui-web/src/`，frontend 改 import 路径。按里程碑按需下沉，不搞一次性大迁移。
3. **v1 范围裁剪**：AMBIENT 只读（看云端已上传的 timeline，web 不采集）、voice 声纹砍掉、push 不做。onboarding 砍掉，登录直接进主界面。
4. **部署 = 新 fly app 并存**：`proactive-ai-web-dev` 与 `proactive-ai-frontend-dev` 并存；以后再把 web 流量入口切到 apps/web，时点另定。
5. **设计基线 = 原型仓 main `19c2f9f`**（含 ZebraLogin / ZebraBackdrop / ZebraGoals）；设计后续迭代按视觉 diff 跟进。
6. **路由模型 = URL 路由**（react-router，zebra 的模式），替代 production 移动端的 state-based `activeView` 导航；桌面 web 需要 deep-link。
7. **冲突仲裁 = proactive-ai-frontend 为准**：zebra 设计与 frontend 现有实现在 UI 语义或功能行为上冲突时，一律以 proactive-ai-frontend 为准。zebra 只供视觉/布局；不为贴合设计稿发明新功能、改变现有行为或数据语义。

### 共享包现状

- `@pin-ai/core`：纯 TS 协议层——`transport/`（http + SSE + config）、`api/` 17 个域（cards / conversation / payment / composio / ambient / profile / memory / devices / agent-runs / …）、`domain/`（卡片状态机，带测试）、`machines/`、`sync/`。平台无关。

## 目标架构

```
packages/
  core      （不动）纯协议层：transport / api / domain
  state     （不动）react-query hooks + stores
  design    （不动）design tokens
  ui-web    （新增）web 介质共享层：React DOM 组件 + 平台 hooks，双端消费
proactive-ai-frontend   Capacitor iOS 壳 + 移动端皮肤（AppLayout/ViewRouter/手势）
apps/
  web       （新增）zebra 桌面壳 + 桌面皮肤（ZebraShell/panels/⌘K/路由）
  mobile    （不动）RN 线
  desktop   （不动）Electron，未来另行切到 apps/web
```

依赖方向：`apps/web` 与 `proactive-ai-frontend` 都依赖 `ui-web + core + state + design`；`ui-web` 只依赖 `core/state/design`，**禁止反向 import 两个 app**。

### packages/ui-web 设计

- **定位**：双端共享的 React DOM 层。放「与壳无关」的功能组件和 hooks：聊天栈、球面、卡详情内容区、card actions、auth hook、connect/profile/settings 的功能区块。**壳留在各 app**：移动壳（AppLayout / ViewRouter / SwipeBackLayer / 手势）留 frontend，桌面壳（ZebraShell / panel 体系 / ZebraCommandPalette / ZebraBackdrop）留 apps/web。
- **目录**：按域分目录 `src/{auth,conversation,now,card,tasks,connect,profile,account,ambient}/`，子路径 export。
- **依赖规则**：硬标准 =「纯 web 环境可运行」。`@capacitor/core` 的 platform 检测（web 上 `isNativePlatform()` 返回 false）和带 web-stub 的自家插件**允许保留**——frontend 本来就以 web 形态跑，现有代码全部满足该标准。重 native 模块（ambient 采集、push、voice 录制）不进 ui-web。下沉某模块时若有 native 触点且无 web stub，触点通过 props 注入，native 实现留 frontend。
- **样式**：组件用 Tailwind 类 + 设计 token。两个消费 app 的 `tailwind.config` content glob 必须加 `../packages/ui-web/src/**/*.{ts,tsx}`（frontend 的相对路径按实际层级），preset 挂 `@pin-ai/design`。aurora / 玻璃等共享 keyframes/classes 收进 `ui-web/styles.css`，两 app import。
- **包内 import**：去掉 `@/` alias（那是 app 内 alias），包内用相对路径；对外子路径导出。
- **测试随行**：模块的 `*.test.ts(x)` 一起 move。注意 frontend 有**源码断言测试**（readFileSync + 正则锁组件结构，如 `ChatDetailView.source.test.ts`），文件 move 后断言里的路径/结构引用必须同步迁，否则 CI 红。
- **下沉操作模板**（每次相同）：move 文件 → 修包内相对 import → frontend 改 import 指向 `@pin-ai/ui-web/<域>` → 跑 frontend `npm run type-check` + `npm test` → 本地 dev 手点回归。

## 风险与对策

1. **ZebraConversation 的 mock 状态机 ≠ 真实帧协议**：功能行为以 production `ConversationView` 为真源，zebra 只取布局/视觉；不要按 zebra 的 mock 行为实现任何逻辑。
2. **卡状态域不齐**：zebra 只画了 new/normal/processing/done 四态，production 有七态（多 needs_input/ready/failed）。缺的三态沿 production 现有形态补设计，不阻塞接入。
3. **源码断言测试失配**：frontend 的 readFileSync+正则测试锁组件结构，下沉 move 必须同迁测试并改路径；每个下沉 commit 后必跑 frontend vitest（type-check 抓不到这类失配）。
4. **React 18→19 与依赖版本**：zebra 代码生在 React 18 + framer-motion 11；搬入后统一对齐 workspace（root overrides @types/react 19）与 frontend 的依赖版本；Sphere3DCards 用 production 带测试的版本（已适配真数据），zebra 的视觉参数（cardWidth/cardHeight/cacheKey）作 props 传入。
5. **Tailwind content 扫描**：ui-web 的类名必须被两个 app 的 content glob 覆盖，否则样式静默丢失；M0 配好并在两端各渲染一个 ui-web 组件验证。
6. **下沉造成 frontend 回归**：import 路径改动是机械的，但每次下沉后跑 frontend type-check + vitest + dev 手点该模块；Capacitor iOS 不受 bundle 形态影响（仍是同一份 web 产物）。
7. **视频资产**：3.87MB mp4 打包偏大但可接受；保留 aurora 兜底 + fade-in，后续可压缩或转 CDN。
8. **web 缺原生能力的降级**：push/voice/ambient 采集在 web 端 UI 上不留死按钮——相关入口隐藏或改只读文案。
