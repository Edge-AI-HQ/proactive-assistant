# V2 → V3 功能迁移计划

## 结论

- 分叉点:`c63f56f7`(2026-05-04 18:25 UTC,`chore: update OPENCLAW_IMAGE digest`)。
- V2 在分叉点之后 **63 commits**,V3 在分叉点之后 **46 commits**。V3 的 46 commits 是后端大重构(`apis/` + `pinai-openclaw/` + `miniapp/` 三个老仓搬进 `pinai-agents/`,Python / FastAPI / LangChain + DeepAgents,web/chat 双进程 + 强 trust boundary)。
- V2 的 63 commits 集中在 **两块**(原以为三块,proactive-engine 那块需要剔除):
  1. Capacitor 插件统一为 `@pin/capacitor-ambient-ai` + 补 iOS native;
  2. 前端 ambient ingest 链路 + 调试面板 + 健康观测 metric-scoped replace。
  3. ~~iOS `ProactiveEngine` 包~~ — V2 自己在 `e8803aee`(2026-05-10)已删除整个 `capacitor-plugins/proactive-engine/`,facade 化为 `@pin/capacitor-ambient-ai`。**不迁移,不复活历史 commit**。
- 迁移按用户拍板砍掉两块:**Data Studio feature(`features/data-studio/` + mini app builder UI)** 完全不要;**单独的 health 视图不做**。注意:V3 当前 health 观测策略是 `raw_only`(`policies.py:245`)只写 `pai_raw_device_health_observations`,**`DeviceTimeline` 只 fetch `personal_signals`,健康数据现在压根不会展示**——D-4 落地方案是**让 `DeviceTimeline` 加一路 `/api/raw/device-health` fetch + client merge sort**;**不**走"health policy 改 dual",因为 health 观测频率高,per-observation 写 signal 会让 `pai_personal_signals` 表灌爆(reviewer 高优指出)。
- 迁移工作量:**Capacitor 插件 + iOS native = 文件级 cp + 一堆 frontend deps + 工作区配置 + iOS Info.plist 隐私权 + patches/**(不只是 cp 目录,见 C 段);**前端 `services/ambient/` ingest 链路 = cp + 改 API base URL + 加 lifecycle wiring + outbox/server status 对齐**(V3 frontend 没有 `services/`);**后端 health policy + replace 修正 + ingest 签名修正 = Python 重写 ~150 行**(详见 D 段,不只是 metric scope)。
- **契约先行 + 几个真 V3 bug**:V3 `/api/devices/ingest` 当前签名 `body: dict`(`devices.py:237`)会让 V2 那种 array body 直接返回 422,**`is_array = isinstance(body, list)` 是 dead code**;`Header(..., alias=...)` 缺头也是 422 不是 401;`replace_health`(`raw_device.py:176`)无条件 DELETE,丢失 V2 的 `reference_count = 0` 保护;`results[i].status` 当前只 `inserted | duplicate`,把"真重复 / 0-row insert / 服务端写入异常"折叠成同一个值,outbox 没法可靠区分。**关键**:服务端写入异常必须返回独立的 `retryable_failed`,不能折叠到 `rejected`,否则 DB 一抽风就让用户事件被永久删除(reviewer 高优 #2 review 指出)。Status 共 5 态:`inserted | duplicate | rejected | parse_failed | retryable_failed`。这些**全部在 step 1 修完**,然后 step 3 前端才有契约依据。
- **Privacy invariant(reviewer 第三轮高优指出)**:V2 `startAmbientUpload()` 默认 autoStart 启动 sound_classifier / visit / activity / location 等 source,登录即采集是隐私回归。V3 必须在 step 1 加 `ambient_sources` user settings,step 3 让 `AmbientSourcesPanel` 成为 opt-in 开关,登录后只对 enabled source 调 `runtime.startSource(<key>)`,绝不调 `autoStart()`。Step 4 真机验证里这条单独列出来,验不过 plan 不算完成。
- **Web build 守护**:Capacitor 插件平移后,V3 web build 必须不挂——V2 commit `893df821` 就是修这个的。所有触碰 native plugin 的代码要 `isNative` 短路,UI 组件用 `React.lazy`。Step 2 + step 3 的 build 验证清单**强制要求** `npm run build`(web)+ `make ios`(iOS)都过,只跑一个不算 land。
- CORS、CI workflow、iOS bundle id 这些边角项视具体情况单独处理,在 V3 上多半已经不适用或已经覆盖。

9. **Outbox 成功判定**:**不要**直接拿 `results[i].status === "inserted"`,当前 server 把"真 duplicate / 0-row 写 / 内部异常吞 logger.warning"三种情况都返回 `duplicate`,outbox 把 duplicate 当失败会无限 retry,当成功会丢真错误。Step 1 已经把 server status 扩成 5 态 `inserted | duplicate | rejected | parse_failed | retryable_failed`,outbox 在 step 3 cp 之后**按 5 态判**:

### D. 需要迁移到 V3 — 后端:health 观测 metric-scoped replace + 真 V3 bug 修正

**比原计划大**——除了平移 V2 `089e1f94` 的 metric scope,V3 当前还有三处独立 bug 必须一起修,否则 step 3 前端 cp 之后会撞上:

#### D-1. health full replace 加 metric scope **+ `reference_count = 0` 过滤**

V2 `replaceDeviceHealthObservations`(`raw-db.ts:1934`)的 SQL 头是:
```sql
DELETE FROM device_health_observations WHERE device_id = ? AND reference_count = 0
```
注释明说"Full health sync refreshes only the unreferenced current slice; referenced rows are immutable raw evidence"。V3 `raw_device.py:176-198` 的 `replace_health` 当前**无条件 DELETE 整个 scope**,会把 memory / signal 已经引用的 raw evidence 一起干掉,这是 silent 数据丢失。

实施:
1. `DeviceHealthReplaceScope` 加可选 `metric: str | None`。
2. `health_full_replace_scope` 在所有 observations 共享同一 `metric` 时返回三键 scope。
3. `RawDeviceRepository.replace_health` 重写 DELETE SQL,**强制带 `AND reference_count = 0`**,scope 含 metric 时再加 `AND metric = %s`。
4. 平移 V2 commit `089e1f94` 的 5 个 contract test 到 `tests/web/devices/test_health_replace.py`,**额外加一个测试**:replace 不能删 `reference_count > 0` 的行。

#### D-2. `/api/devices/ingest` 签名修正(让 array body 真能进 handler)

V3 `devices.py:237` 当前 `body: dict`,FastAPI/pydantic 在 array body 上直接 422。下面 `is_array = isinstance(body, list)`(`devices.py:252`)是 dead code。V2 前端 `ingestSignals` 发的就是 array(`devices.ts:295`)。

修法二选一:
- (推荐)签名改成 `body: list | dict`(Python 3.10+ syntax)或显式 `Union`,handler 的 `is_array` 分支立刻生效。
- 用 `Request` 拿原始 body 自己 json.loads。

加 HTTP 端到端测试覆盖 array 和 wrapper 两种 shape。

#### D-3. `results[i].status` 扩展(从 2 态扩到 5 态)

`devices.py:435-441` 当前:
```python
ok = raw_inserted.get(n.id, False) or signal_inserted.get(n.id, False)
results.append({..., "status": "inserted" if ok else "duplicate"})
```
"duplicate" 实际把三种情况合在一起:
1. 真 dedupe(server 已有同 key,正确"no-op success")
2. raw insert 返回 0 但无 exception(也是 success-like)
3. signal `ingest_one` 抛异常被 `logger.warning` 吞掉(真失败,client 无感)—— **第二轮 review 高优指出:这种 transient failure 绝不能折叠成 client 永久失败**

outbox 无法区分这三种 → 没法决定 retry 还是 abandon。

实施 5 态:
- `inserted`:raw 或 signal 至少一处实写入。
- `duplicate`:server 已有同 dedupe_key,**由 ON CONFLICT 触发**(必须能从 INSERT 的 `RETURNING xmax = 0` 或类似机制区分,不允许用"0 rows affected"启发式——那会和 raw insert 写 0 行的情况混)。真 idempotent no-op。
- `rejected`:**只放确定性的语义校验失败**——missing kind / cross-device dispatch / unsupported_full_sync / 跨 device 静默丢弃。client side 永久 bug,outbox 移除。
- `parse_failed`:`IngestItemIn.model_validate` 抛异常那条 item(当前直接 continue 不返回 result,修)。client schema bug,outbox 移除。
- `retryable_failed`:**服务端写入抛异常**——`raw_repo` / `signals_repo` 的 transaction 抛了异常被 `logger.warning` 吞掉的那条 item。本质 transient,outbox **必须保留并 retry**。
- 当前代码里两处 `try/except` + `logger.warning` 的地方(`devices.py:395-397` 的 raw transaction,`devices.py:430-431` 的 signal_ingest)改成:把异常类型放进 result 的 `reason`,`status` 设为 `retryable_failed`,**不再闷掉**。

加 HTTP 端到端测试覆盖 5 态——尤其测一个 fault-injection 用例:repository mock 抛异常,verify response `status="retryable_failed"` 而不是 `rejected` 或 `inserted`。

#### D-4. **`DeviceTimeline` 加 `/api/raw/device-health` 合并展示**(不改 policy)

用户拍板"健康数据在 device data 里能显示就行,不要单独 health 视图",但 V3 现状是:
- `policies.py:245` `_HEALTH_POLICY` mode = `raw_only`,**只写 `pai_raw_device_health_observations`,不写 `pai_personal_signals`**。
- `DeviceTimeline.tsx:57` 只调 `fetchSignals(...)`,**根本不 fetch `/api/raw/device-health`**。
- 结果:health 上传成功也不会出现在 `DeviceTimeline`。

**~~曾经考虑改 `_HEALTH_POLICY` 为 `dual`~~**——直接放弃。Health 观测频率天然高(steps / heart rate 分钟级,sleep / activity 小时级),per-observation 写一条 signal 会:
- `pai_personal_signals` 行数膨胀几个数量级,影响 timeline query / memory pipeline / 下游 signal processing(generator / dream 都按 signal 计费 + 选卡)。
- 噪声把真信号(message / event / 用户动作)淹没。
- 后期再想往回收(去 dual)代价更大——已经写下去的 signal 行还得迁。

**两条候选路线,任选一条**(reviewer 高优指出之前的"PAGE_SIZE 各取 + merge top N + 两边推进"是错的——一边流量大就会让另一边没渲染的行被 cursor 推进吞掉):

**路线 A:server-side merged timeline endpoint(推荐)**

- 新增 `GET /api/devices/{deviceId}/timeline`,server 端 union signals + raw health,按 `occurred_at DESC` 合并 + keyset cursor。
- 返回统一 envelope:`{ items: [{ type: "signal" | "health", row: {...} }], next_cursor, has_more }`。
- 前端 `DeviceTimeline` 只调一个 endpoint,游标干干净净。
- 工作量:~80 行 Python 实现 + ~60 行测试;frontend ~30 行 UI(`HealthObservationCard` + 把 `fetchSignals` 换成 `fetchDeviceTimeline`)。
- 风险:server 端 UNION 跨表 query,加索引,但 V3 schema 已经在两张表都有 `(user_id, device_id, occurred_at)` 索引。

**路线 B:frontend k-way merge with per-source buffers**

- 各自 keyset cursor,每路维护一个 buffer。
- 渲染时从两个 buffer 头部取 `occurred_at` 较大者,**只对实际消费掉的那一路推进 cursor**,没消费的 buffer 留着下次合并。
- buffer 见底时再拉一页。
- 工作量:frontend ~150 行 + 测试覆盖偏斜流(只有 signals / 只有 health / 两边交错 / 一边空了 / cursor=null 终止),后端 ~30 行(补 `since` / `until` / `before` query param)。
- 风险:复杂度更高,边界条件更多;V3 `fetchSignals` 返回 `next_cursor: null`(单页)和 raw health 当前**没有 `before` cursor 也没有任何 cursor 字段**,这两个 endpoint 都需要先补 cursor 才能做。

**默认路线 A**——后端工作量差不多但 frontend 不用碰复杂 k-way merge;另外把"是 signal 还是 health"的判断收回到 server,前端只渲染 item type,后续要再加 device-state / device-apps timeline item 都很自然。

**工作量**(按路线 A):Python 端 D-1 ~80 + D-2 ~10 + D-3 ~50 + D-4 ~80(新 timeline endpoint)= 共 ~220 行实现 + ~350 行测试;Frontend 端 D-4 part = ~30 行 UI(进 step 3 做)。

### `/ingest` 契约细节(前端 ambient 上传链路的唯一入口)

> ⚠️ 下面带 **【V3 当前 bug,step 1 修】** 标记的项是 V3 实际行为,**和正确目标行为不同**。Step 1(D 段)落地后,这些 bug 消失,契约变成"目标行为"。

- **Auth headers**:`X-Device-Id` + `X-Device-Token` 必带。
  - 任一**缺**(header 不存在)→ **【V3 当前 bug】FastAPI `Header(...)` 默认返回 `422 Unprocessable Entity`,不是 401**。前端 outbox 把 422 当永久失败可能也行,但和 V2 行为(401 时清缓存重 register)不一致。step 1 用 `Header(None, ...)` + handler 内显式校验,改成统一返回 401 `missing device credentials`。
  - 任一**错**(header 存在但值不匹配)→ 401 `invalid device credentials`(handler 里 `find_device_by_token` 抛 `DeviceTokenInvalid` 转 401,这条没问题)。
- **JWT**:**不需要**。Service-role 直查 `pai_devices` 拿 `user_id`,RLS 走 service_role fallback。前端可以走 proactive API client 顺手带 JWT,但服务端不读它。
- **Body shape**:目标接受两种 shape(plugin 1:1):
  - Array: `[{...item}, ...]`(每个 item 可带 `source: "device:<id>"`)
  - Wrapper: `{ deviceId: "...", items: [...] }`(wrapper deviceId 作为 fallback)
  - **【V3 当前 bug】** handler 签名 `body: dict`(`devices.py:237`)让 array body 直接 422,下游 `is_array = isinstance(body, list)` 是 dead code。V2 前端 `ingestSignals`(`devices.ts:295`)发的就是 array,如果不修,step 3 cp 完 100% 跑不通。step 1 改签名为 `body: list | dict`(或用 `Request` 拿原始 body)。
- **跨 device 限制**:item `source: "device:<id>"` 若不等于 token-verified 的 `deviceId`,**该 item 静默丢弃**(`devices.py:279-281` 只 `continue`)。MVP 只允许 self,不支持 fan-out。step 1 把这种 item 在 `results[]` 里返回 `status: "rejected"` + reason,而不是从 result 数组里消失。
- **错误码**(step 1 后的目标):
  - 400 `items must be an array` — items 字段不是 array
  - 400 `deviceId or signal source required` — 既没 wrapper deviceId 也没任何带 source 的 item
  - 401 device credential 不对(包括缺 header)
- **成功 response shape**(step 1 后的目标):
  ```json
  {
    "ok": true,
    "accepted": <int>,       // 收到的 raw_items 数
    "inserted": <int>,       // 真写库的(raw 或 signal 至少一处实写入)
    "ignored": <int>,        // accepted - inserted
    "results": [
      {
        "id": "<item.id>",
        "dedupeKey": "<server-resolved>",
        "status": "inserted" | "duplicate" | "rejected" | "parse_failed" | "retryable_failed",
        "reason": "<string,可选,非 inserted/duplicate 时给>"
      }
    ]
  }
  ```
  - `inserted`:raw 或 signal 至少一处实写入。**outbox 视为 success,从队列移除。**
  - `duplicate`:server 已有同 dedupe_key,真 idempotent no-op(由 ON CONFLICT 触发,**不依赖** "0 rows affected" 启发式判断)。**outbox 视为 success,从队列移除。**
  - `rejected`:**确定性的语义校验失败**——missing required field / cross-device dispatch / unsupported_full_sync / 跨 device 静默丢弃 等,重传也不会变好。**outbox 视为永久失败,移除并记日志,不要 retry。**
  - `parse_failed`:`IngestItemIn.model_validate` 抛异常,本地客户端 schema bug。**outbox 视为永久失败,移除并记日志。**
  - `retryable_failed`:**服务端写入抛异常**——DB 连接断、SAVEPOINT 失败、repository bug、Supabase Storage 一时不可用、等。本质是 transient,重试有机会成功。**outbox 视为可重试失败,保留在队列里按指数退避 retry**,不要因为 200 OK 就把它当成功移除。
  - 网络错误 / 5xx / 4xx(非 200 整体):**outbox 视为可重试失败,按指数退避 retry。**
  - **【V3 当前 bug】** 现状只有 `inserted | duplicate` 两态,把"真 dedupe / 0-row insert / signal_ingest 抛异常被 logger.warning 吞"折叠成同一个 `duplicate`,outbox 没法可靠区分。step 1 不修这个,**禁止开始 step 3**。
  - **关键区分(reviewer 高优指出):** 不要把"服务端写入异常"折叠到 `rejected`。`rejected` 只放确定性 client-side bug;服务端抛异常必须走 `retryable_failed`,否则一次 DB 抽风会让用户事件被永久删除而 client 完全无感(200 OK + outbox 移除)。

### Replace / dedupe 语义

- **Dedupe key**:server 端会保底生成。**outbox 的本地 key 必须等于 server 看到的 key**——客户端如果显式发 `dedupeKey`,就用自己的;如果不发,outbox 也得用 `device:<deviceId>:<item.id>` 作本地 key,否则重传判定会错位。
- **sync_mode**:
  - `incremental`(默认):append-style ingest
  - `full`:按 policy 走 replace_scope。
    - `device_health_observations`:**【V3 两个 bug】** (a) 当前只 `(device_id, local_date)` 缺 metric tightening,step 1 D-1 加;(b) 当前 `replace_health` 无条件 DELETE,**V2 是只删 `reference_count = 0` 的行**(`raw-db.ts:1934`),保护已被 memory / signal 引用的 raw evidence。step 1 D-1 也修这个,SQL 强制带 `AND reference_count = 0`。
    - `device_apps_snapshot` / `device_contacts_snapshot`:走全 device 替换。
- **part-success**:per-item 各自 SAVEPOINT(`devices.py:391-393`),单条坏行不污染整批。step 1 D-3 后,outbox 按 `results[i].status` **5 态**处理。

## 风险 / 待确认

契约相关的(endpoint shape / auth / body / response status / replace 语义)都已经在上面契约 section + D 段拍死并进入 step 1。剩余事项已经按用户拍板收口:

1. **Outbox 持久化用 `@capacitor-community/sqlite`**(拍板)。V2 `outbox.ts` 只实装了 `MemoryOutboxStore`,`OutboxKind = "memory" | "sqlite"` 里的 `"sqlite"` 是 placeholder——内存 outbox 后台被杀就丢数据,mobile 场景下不可接受。最佳实践 = SQLite 真持久化跨重启。Step 3 实施时:
   - frontend deps 加 `@capacitor-community/sqlite`(C 段 deps 清单加一条)。
   - 在 `services/ambient/outbox.ts` 补 `SqliteOutboxStore implements OutboxStore` 类(`OutboxStore` interface 已经定义好,字段名 `dedupeKey` 已定,直接实装即可)。
   - `getAmbientRuntime()` 工厂在 `isNative` 时默认用 sqlite store,否则 fallback memory(web build 兼容)。
   - 表 schema:`(id PRIMARY KEY, item TEXT JSON, dedupe_key TEXT UNIQUE, status TEXT, attempt_count INTEGER, last_error TEXT, next_retry_at INTEGER, inserted_at INTEGER, synced_at INTEGER)`。Index on `(status, next_retry_at)`。
   - 测试至少覆盖:enqueue 去重(dedupe_key UNIQUE 触发)、pending 按 retry time 排序、`markSynced` / `markFailed`、prune TTL、app 重启后还能读到。
2. **`/api/raw/device-health` pagination**:D-4 走 server-side UNION timeline endpoint(`GET /api/devices/{deviceId}/timeline`),不再需要单独给 `/raw/device-health` 补 cursor——timeline endpoint 自己有 keyset cursor。`/raw/device-health` 保留现状用于 debug / direct query,不强求 cursor。这一项**等价于已解决**。
3. **`reference_count` 列**:✅ V3 schema 已经有(`019_pai_raw_device.sql`),D-1 不用新加 migration,只动 `replace_health` 的 DELETE SQL 即可。V3 当前**没有任何代码会把 reference_count 增到 > 0**——memory / signal 引用 raw 时的"+1"逻辑在 V3 还没实装,意味着 D-1 加的过滤短期内不会真正保护任何行。但 raw 引用机制后续会上,**现在就把 DELETE 限制带 `AND reference_count = 0` 是为了将来引用机制上线时不需要再回头改 SQL**。前置防御,不紧迫。
