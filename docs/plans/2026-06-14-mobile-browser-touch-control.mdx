# 手机端远端浏览器的原生触摸操控

状态:已定稿(待实施)。本文是该 feature 的设计 SSOT。承接 PR#139(browser view 重构:split/drawer + 远端跟随容器 + client_hints 接通)。

## 问题(为什么)

手机上操控远端浏览器现在体验差,三个现象:打字要先点一个"召唤键盘"按钮、旁边还有个含义不明的"Enter"键、**网页滑不动**。

三个现象同一个根因:**我们现在依赖 Browserbase 交互式 Live View iframe 来接收输入,而它是桌面鼠标模型**(拖拽≠滚动、靠鼠标滚轮滚动、桌面键盘聚焦)。触摸手势(滑动滚动、点输入框自动唤键盘、捏合)它都不映射。现有的 keyboard / Enter / 角落 drag-pad 三个控件都是给这个错配打的补丁,既不可发现也不原生。

## 架构决策:方案 C(混合)

**Browserbase 只负责"看",我们负责"操作"。**

- **帧**:Live View iframe 设成**只读**(`pointer-events:none`),纯渲染。帧仍由 Browserbase 的 CDP screencast **直连客户端**(不经我们后端,不耗我们带宽)。
- **输入**:在 iframe 之上盖一层**全屏、同源的手势捕获层**;手势翻译成裸 **CDP `Input.*` 触摸/手势事件**,经我们现有 `/input` 通道 → 后端持有的 CDP 连接 → 远端浏览器。

成熟度:这就是 **remote framebuffer(VNC/RDP,25+ 年)** 模式的浏览器特化。浏览器领域的参考实现是 **Chrome DevTools 的 screencast**(`Page.startScreencast` + `Input.dispatch*`,Browserbase Live View 即从其 `ScreencastView` 派生);手机触摸转发的直接商业先例是 **BrowserStack / Sauce Labs Live**(网页手势→真机触摸)。每一半都成熟;我们只是沿"带宽边界"把帧(用 vendor)和输入(自己做)切开。

为什么不是另两种:
- **全用 vendor 交互 iframe(现状)**:桌面鼠标模型,触摸天花板就在这,做不到原生。
- **DIY 全套(自己截屏流 + 输入)**:最被验证,但帧流(~1.5MB/s/会话)全过我们后端,成本/延迟/扩展性差,等于重造 vendor 免费给的东西。留作升级路径(见末节)。

## 边界

- **只针对触摸场景**。web(鼠标)端**完全不动**——继续走它现在已经"体验很好"的路(直接操作 Live View iframe)。两条输入路并存,互不干扰。
- **gate 按真实触摸能力,不按屏宽**:用 `pointer:coarse` / `navigator.maxTouchPoints>0` / `isNative` 决定是否启用手势 overlay。**不要**用 `device_kind==mobile` 或窗口宽度——桌面用户把窗口拖窄会拿到 mobile 会话(可以,预览手机版),但他手里是鼠标,必须继续走鼠标直接操作,不能被塞触摸层。
  - "会话是不是 mobile"(mobile UA/viewport)→ 按 client_hints/屏宽定(已有)。
  - "要不要触摸 overlay"(本 feature)→ 按真实触摸能力定。
- **不引入 Browserbase fingerprint**(本轮已拍板)。调研结论:`fingerprint.devices:["mobile"]` 只给 UA/headers/随机 screen,**不给 touch、不给可控 viewport、不给 DPR**,fingerprint-only 会反过来破坏本方案。stealth 需求出现再加,且只替换 UA override,绝不替换 touch/viewport/DPR 的 CDP 调用。
- 帧仍来自 Browserbase 只读 Live View iframe;不改 split/drawer 布局、header、控制模型(均来自 PR#139)。

## 设计

### 1. 会话设备档:保持 self-CDP(不动)
现有 `manager._create` 对 mobile/tablet 已经做了正确的地基,**保留**:
- `Emulation.setDeviceMetricsOverride{mobile:true, deviceScaleFactor:preset(iPhone=3), width:W, height:H, screenWidth:W, screenHeight:H}` —— 唯一能 **pin viewport + 控 DPR + 置 mobile 布局**的途径。
- `Emulation.setTouchEmulationEnabled{enabled:true, maxTouchPoints:5}` —— **唯一**让页面 `navigator.maxTouchPoints>0` / `@media(pointer:coarse)` 命中、从而认我们注入的触摸事件的开关(fingerprint 不做这件事)。
- `Network.setUserAgentOverride(iPhone UA)` —— 保留(无 fingerprint 时由它给 mobile UA)。
- W×H 取 client_hints 的 viewport(手机上 = 手机屏 CSS 尺寸),让远端 viewport ≈ 显示面板 → 坐标映射近 1:1。

### 2. 后端:常驻 CDP session + 触摸 Input 协议
- **manager 持有一个常驻 `CDPSession`**(`internal.cdp = await context.new_cdp_session(page)`,创建时建、随会话存活),专供 `Input.*` 派发。替换现在"创建时临时建、emulation 完就 detach"的用法。导航时同 target 的 CDP session 存活;新 target/tab 需重新 attach(边界处理)。
- 输入只在 **user 控制模式**派发(AI 模式忽略,沿用现有 control gating)。
- **`apply_user_input` 从 Playwright 鼠标(`page.mouse.click/wheel`)改为裸 CDP `Input.*` 触摸**(Playwright `page.tap`/`page.touchscreen` 在 connectOverCDP 上用不了——hasTouch 不能在已连接 context 上设,maintainer 明说 out of scope;所以必须裸 CDP)。

`/input` body 按 `type` 区分(坐标均为**远端 CSS px**;CDP Input 用 CSS px,DPR 只影响帧清晰度不影响坐标):

| type | 字段 | CDP 调用 |
|---|---|---|
| `tap` | x, y | `Input.dispatchTouchEvent` touchStart@(x,y) + touchEnd;**返回 `{editableFocused: bool}`**(tap 后 `Runtime.evaluate` 查 `document.activeElement` 可编辑性,告诉前端要不要唤键盘)|
| `scroll` | x, y, dx, dy, speed? | `Input.synthesizeScrollGesture{x,y,xDistance:-dx,yDistance:-dy,speed,gestureSourceType:"touch"}`(touch 源 → 原生惯性)|
| `text` | text | `Input.insertText{text}`(IME 安全,提交合成文本)|
| `key` | key | `Input.dispatchKeyEvent` keyDown/keyUp(Enter/Backspace/Tab/Arrow…)|
| `pinch` [P2] | x, y, scale | `Input.synthesizePinchGesture{x,y,scaleFactor,gestureSourceType:"touch"}` |
| `long_press` [P2] | x, y | touchStart → 延时 → touchEnd |
| `navigate`/`back`/`forward`/`reload` | url? | 沿用现有 `page.goto`/`go_back`/… + 隐式接管(已有)|

- chat routes `/agent/browser/sessions/{key}/input` 扩词汇;web `/api/browser/...` proxy 已通用,透传即可。

### 3. 前端:手势 overlay + 状态机
全屏透明 overlay(同源,覆盖 live view box),仅在 **触摸设备 + user 模式** 激活。用 Pointer Events 分类手势:
- **down**:记录起点 + 时间,标记 pending。
- **move**:位移 > TAP_SLOP(~8px)→ 进入 pan;throttle(rAF)累积 dy/dx → `scroll`。
- **up**:仍 pending 且短时小位移 → `tap`;否则 pan 结束(可按末速度补一个 fling `scroll`)。
- **hold(定时无位移)** → `long_press` [P2]。
- **双指** → `pinch`(距离比 → scale)[P2]。

### 4. 坐标映射
remote CSS viewport = 我们 pin 的 W×H;overlay 显示尺寸 = 面板 Pw×Ph;`remote = overlay × (W/Pw, H/Ph)`。手机全屏 drawer 下 remote≈面板 → scale≈1 无 letterbox。面板与 remote 宽高比不一致时按 fit 偏移修正(让 remote 宽高比≈面板可消除)。每次手势按当前 overlay rect 重算 scale(面板 resize 后远端**不**重建,只重算 scale)。

### 5. 键盘自动唤起(去掉手动按钮的关键)
1. tap → 后端 touch tap → 返回 `editableFocused`。
2. 为 true → 前端聚焦一个本地隐藏 `<input>` → 手机键盘升起。
3. 击键 → `key`(特殊键)/ `text`(普通+IME 合成,`compositionend` 提交)→ 远端。Enter = 键盘自带回车 → `key:Enter`。
4. 复用现有 BrowserView 隐藏 input 的 composition 逻辑,只是改成**命中输入框自动唤起**,删掉 keyboard/Enter 两个手动按钮。

### 6. 控制模型集成
- AI 模式:overlay 表现为"点击接管"层(沿用 PR#139 隐式接管)——首个触摸切 user,之后 overlay 转为手势层。
- user 模式:overlay = 活动手势层。
- 交还 AI:沿用现有按钮。

### 7. 滚动延迟与手感(诚实的 tradeoff)
混合方案里**帧像素不归我们**(vendor 跨域 iframe),所以**做不了客户端滚动预测**;滚动反馈延迟 = 一次往返(client→web→chat→CDP)+ 下一帧。这是远端操控的固有延迟(BrowserStack live 同样有)。MVP 接受它:
- `synthesizeScrollGesture`(touch 源 + speed)给原生惯性,**每次滑动基本一条命令**,延迟容忍。
- 真要"丝滑跟手"需要 DIY 帧(自己 canvas → 本地预测/位移),见升级路径,本期不做。
- 唯一延迟敏感的边缘场景 = 连续拖拽(slider/画图)需 stream touchMove,P2 再优化。

## 分阶段

- **Phase 1(MVP,正好修三个痛点)**:`tap`(touch)+ `scroll`(滑动滚动)+ **自动唤键盘** + `text/key`(含 IME)。后端常驻 CDP + Input 协议;前端 overlay + 手势 SM;删 keyboard/Enter/drag-pad 三个手动控件。
- **Phase 2**:`pinch` 缩放、`long_press`(上下文/选词)、拖拽 stream 优化、跟手滚动打磨。
- **Phase 3(可选/远期)**:DIY 帧 canvas(脱离 Browserbase / 需要控帧率质量 / 要丝滑预测时)。

## 不变量(本期不动)
- web/桌面(鼠标):直接操作 Live View iframe,零改动。
- 帧来源:Browserbase 只读 Live View iframe(直连客户端)。
- split/drawer 布局、header、控制模型:PR#139 现状。
- 会话设备档:self-CDP mobile emulation(不引入 fingerprint)。

## 风险 / 待验证 / 开放问题
- **滚动延迟**(混合无客户端预测)——MVP 接受;丝滑需 Phase 3。
- **自动唤键盘**靠 tap 后 `activeElement` 可编辑性判断(一次往返)——真机真站点验证可靠性 + 远端 blur 时键盘收起的检测。
- **坐标 letterbox**(非 1:1 边缘场景)——偏移修正。
- **iOS WebView 渲染 Live View iframe 的可靠性**——保留 PR#139 的 foreground 重连/重挂 key。
- **常驻 CDP session 的健壮性**——top-level 导航存活;新 tab 重 attach;输入串行化。
- 无本地 Browserbase E2E,必须真机验。

## 验证方式
真机(`make ios` 在本 worktree 起 → 本地后端 + Browserbase):滑长页、点链接、点搜索框→键盘自动起→打字(含中文)→提交、(P2)捏合缩放;对比原生手感。后端 ruff/mypy/pytest;前端 type-check/test + check:packages。

## 升级路径(留给未来)
"输入→CDP"这半在混合与 DIY 全套里**完全一样**。将来若脱离 Browserbase 或要控帧,只需把"帧"那半从"vendor iframe"换成"自己 canvas + `Page.startScreencast` 中继",**输入侧零改动**——所以现在走混合不赌死,退路干净。
