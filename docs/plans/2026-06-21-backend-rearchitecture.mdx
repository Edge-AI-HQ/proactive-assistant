# 后端重构：领域垂直化 + 三 service 物理拆分

> 状态：**brainstorm 草稿（设计讨论阶段，未实施）**。综合 2026-06-21 多轮讨论 + 一轮基于代码的 5-agent 验证（§十一）。
> 前序：[Agent Core 控制平面](./2026-06-04-agentrun-control-plane)（actor kernel，本次保留不动）。

## 结论（先读）

1. **水平切分已做完、且做得好**。web/chat 早已是两个 app、两进程、HTTP+SSE+EdDSA JWT 网络边界、配置分离、import 墙；chat 不碰业务库，业务数据全走 `http_client` 回调 `/api/agent/*`。actor kernel + harness 三处 facade 是亮点，**本次不动**。
2. **真正的债在 web 内部：按技术层平铺、缺领域边界**。要做**垂直切分**（按 bounded context 重组），不是再拆 web/chat。
3. **trust boundary 在 fly 上没真生效**。根因在 `fly.dev.toml:11`：单 fly app 无法给两个 process group 发不同 secret。**拆成独立 fly app 是唯一正解。**
4. **终态 = 三平面 + 一底座，物理走 monorepo uv workspace，三个独立 service**：`api`（受信任）/ `agent-engine`（无信任 LLM 执行）/ `reward-dashboard`（内部只读工具，不持 master credentials）。各自独立 pyproject + Dockerfile + fly app + per-app secret。
5. **trust boundary 命门已验证（§十一）**：agent-engine 对 `web/` 的 import = 0，只依赖 `contracts` + 自带 config → `libs` 只需 `contracts`，trust boundary 靠依赖图物理强制。
6. **reward-dashboard 彻底拎出产品架构**：内部 review 工具不是产品 `api` 的 domain，而是独立 service，只读产品 DB 做分析、零产品代码依赖、不被产品依赖、不持 master credentials。

## 一、为什么重构（诊断）

agent app 后端 = **三个平面 + 一个底座**：

```
   Human (前端) ─┐
                 ├──►  ① API Edge ───────────────────────────────────┐
   Agent (LLM)  ─┘      ui 路由 = 人类 API ; agent 路由 = Tool Plane    │
                                                                        ▼
   ┌────────────────────────────────────────────────────────────────────┐
   │ ② Domain Plane (产品 bounded contexts) — 本次主战场                  │
   │   identity · user_model · connector · billing · generation ·         │
   │   feedback · chat_history · browser     ← 不含 reward-dashboard       │
   └────────────────────────────────────────────────────────────────────┘
        ▲ 向下调                                       │ 只能依赖底座
   ┌────┴──────────────────┐          ┌────────────────▼───────────────────┐
   │ ③ Orchestration        │          │ ④ Platform / Infra 底座             │
   │   scheduler+dispatcher │          │   db · auth(deps/user_service/User) │
   │   account_lifecycle    │          │   llm · storage · notification ·    │
   │   phase1_seed          │          │   speech · embeddings               │
   └────────────────────────┘          └─────────────────────────────────────┘

   ┌──────────── Agent Runtime ─────────────┐   ┌──── 内部工具（独立 service）────┐
   │ Control(api) ─HTTP+SSE→ Execution       │   │ reward-dashboard                │
   │ kernel/worker/conversation/recorder     │   │ 只读产品 DB + langsmith         │
   │      agent-engine: harness/agents/tools │   │ 无 master credentials           │
   └─────────────────────────────────────────┘   └─────────────────────────────────┘
```

三个 agent app 本质判断（显式化）：**agent 是领域的一等 consumer**（agent 路由=tool plane，与 ui 对称）；**control / execution 分离**；**工具层是 agent 触达世界的窄接口**。

## 二、目标架构与依赖铁律

依赖方向（Clean / Hexagonal），用 **import-linter** 强制：

```
deployment(api/agent-engine/reward-dashboard asgi)
  api:    orchestration → control → domains → platform   (domains 互不 import；唯一例外单向依赖 billing)
  agent-engine: → libs/contracts（纯协议，无 credentials）+ 自带底座
  reward-dashboard: → 产品 DB（只读）+ langsmith ；零 import 产品代码
libs/contracts → 叶子
```

- **`agent-engine` 禁止依赖 api 内部**（domains/platform/control）——trust boundary 的代码层实现，依赖图物理强制。
- **`reward-dashboard` 禁止 import 产品任何 service/domain 代码**——它和产品只有"共享 DB schema"的数据级耦合（只读），无代码耦合。

## 三、物理形态：monorepo uv workspace，三 service ✅

一个 repo，三个独立 deployable（`services/{api, agent-engine, reward-dashboard}`）+ 共享 `libs/contracts`。uv `[tool.uv.workspace]`，path 依赖，改协议即时生效（dev 不发版）。三个独立 fly app + per-app secret。

| service | 信任档 | 持有 | 不持 |
|---|---|---|---|
| `api` | 受信任 | master credentials + DB(读写) | — |
| `agent-engine` | 无信任 | contracts + 执行环境凭证(daytona/browserbase/tavily/litellm vk)；DB=langgraph scoped DSN | master credentials、产品 DB 可见性 |
| `reward-dashboard` | 内部只读 | 只读 DB role + langsmith + reviewer 鉴权(`internal_operator_subs`) | master credentials、写产品数据的能力 |

---

## 四、trust boundary 四道防线（拆 app 后全部立起来）

1. **依赖图物理隔离**：`agent-engine` 的 `pyproject.toml` 只依赖 `libs/contracts`，列不到 api 的任何代码 → `import` 不到。`reward-dashboard` 同理不依赖产品代码。
2. **镜像隔离**：各 service 的 Dockerfile 只 COPY 自己 + 所需 lib，凭据/领域代码不进别的镜像。
3. **部署隔离**：三个 fly app，`agent-engine` 与 `reward-dashboard` app 都**不下发** master credentials（单 app 做不到的那步）。
4. **运行时 fail-fast**：`agent-engine/asgi.py` 启动检查 `FORBIDDEN_ENVS`（重启用）。

> **§十一 硬施工项**：`agent-engine` 的 `DATABASE_URL` 换 `pai_chat` scoped DSN（只见 langgraph schema）；`reward-dashboard` 用只读 DB role。否则即使代码隔离，运行时仍能看/动 `pai_*`。

1. 统一语言优先。2. 按概念命名不按供应商（`payments` 不叫 `stripe`）。3. 包名 ≠ 模块名（`user_model/memory.py`）。4. 同组子模块同维度互斥（`apps/device/world`）。5. 边界靠 import-linter（`ingest/` 不用 `_ingest/`）。6. 领域名单数、表名复数。

## 十一、基于代码的 final review（2026-06-21，5-agent 验证）

5 个 agent 逐模块对照真实代码。**总判断：领域骨架成立，无 ❌（无不可行项），trust boundary 命门通过；一批 ⚠️ 是边界细节按代码事实校准。**

### 11.1 两条必须做的硬动作

1. **control 裸 `SELECT … FROM users`（worker.py:749）→ platform/auth 公开接口**（如 `get_run_credentials(user_id)`）。control 唯一一处 reach 进 users 实现。
2. **agent-engine `DATABASE_URL` → `pai_chat` scoped DSN**。现用 superuser DSN 能看 `pai_*`；024_pai_chat_role.sql role split 从没 wire。不补则 trust boundary 只到"代码隔离"未到"运行时隔离"。

### 11.2 域归属修正（含本轮 reward-dashboard 调整）

- **reward-dashboard 提升为独立 service**（非产品 domain）：reward/casebook/trace/pattern_extractor/pattern_health/personal_data_snapshot 全归它，只读产品 DB、零产品代码依赖、无 master credentials。产品 `api` 从此与内部工具物理无关。
- **patterns 整块是 card/reward 链路**（verify-usermodel 纠正，推翻初版 fingerprint→user_model）：读 casebook/evaluations/reward_events、无 user-facing 入口。归位：`matcher`+`fingerprint`→generation（生成用）、`extractor`/`health`→reward-dashboard（curate）。`pai_card_patterns` 是共享表（产品只读、reward-dashboard curate）。**user_model 核心 = 6 表**。
- **conversation.py + chat_turn_recorder 归 control**（执行入口/SSE 累加器，非历史）。chat_history 缩为 sync+repos+/history。
- **feedback 拆出 reward-dashboard 后彻底干净**（纯用户反馈）；evolution 移出 feedback→user_model（memory 进化记账）；补漏列的 `ui/dreaming.py`。
- **auth 整体（deps/user_service/User）下沉 platform/auth**（`deps` 被 44 route 依赖）；identity 瘦身为 token 生命周期 + impersonation（impersonation 需 master cred 留 api）。
- **dispatcher / phase1_seed / account_lifecycle 归 orchestration**；generation 是被 dispatcher 逆向驱动的 service 集合。

### 11.3 跨域接口要显式（边界契约）

- **provisioning（browserbase + litellm）= 被 control/identity 反向依赖的公共层**，定为域公开接口（worker 里的 browserbase 兜底是 smell，记一笔）。
- **personal_signals**：connector 写、user_model 拥有 → user_model 暴露 ingest 接口，connector 单向调。
