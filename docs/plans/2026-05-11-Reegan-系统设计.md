## 1. Executive Summary（执行摘要）

### 1.1 一句话方向

构建一个 proactive(主动)、privacy-aware(隐私感知)、context-aware(上下文感知) 的 voice-to-action 系统：只有在系统理解用户需求、能可靠执行、判断这是 personal hit(对用户个人有价值)、confidence 已校准、且 timing 合适时,才进行介入。

### 1.2 五条不可妥协的架构决策

| Decision | 含义 | 为什么重要 |
|---|---|---|
| **D1. ASR 不负责理解** | ASR 只输出 transcript、timestamps、language、confidence、latency。不要让 ASR 判断 intent 或 recommendation。 | 避免把 acoustic error 和 semantic decision 混在一起；ASR 错误会向 downstream NLU 传播,需要清晰边界与错误定位。 |
| **D2. Context Segmentation 独立** | 先切 context/session/topic,再进入 semantic understanding。 | 长对话、多任务、多 topic 会造成 context pollution；无关 memory 会 distract LLM 并降低 response quality。 |
| **D3. Personal Hit 独立 gate** | personal_hit_score 不是 action ranking 的副产品,而是独立判断:这件事对这个用户是否真的有价值。 | 推荐系统不能只看 accuracy；engagement/satisfaction 受 beyond-accuracy 目标影响 [R13]。 |
| **D4. Timing 独立 policy** | 推荐内容正确 ≠ 应该现在打扰。Timing module 决定 now / later / silent / channel / intensity。 | 人机交互研究明确强调 time services based on context；context-aware prompts 可降低打扰感。 |
| **D5. Confidence + Action Effects 闭环** | 每一层都输出 confidence,Evaluation 层校准它；Action Effects 把 helpful/workable/user liked 回流。 | 现代模型 confidence 常不校准；production ML 需要 testing、monitoring、feedback loop。 |

### 1.3 成功的样子

- **用户层面**：系统少打扰,但在合适时机给出"刚好有用"的帮助；用户不需要频繁纠正。
- **产品层面**：从被动 voice command 扩展为 proactive personal assistant,但用 gate 和 timing 控制风险。
- **工程层面**：每个 team 有明确的 module ownership、输入输出、metrics、failure attribution 和 dashboard。
- **评测层面**：不仅看 accuracy,还看 task success、personal hit、false intervention、correction、repeat acceptance。

### 1.4 North-star Metrics（北极星指标）

| Metric | 定义 | Primary Owner | 为什么重要 |
|---|---|---|---|
| **End-to-end Task Success Rate** | 有效用户目标中,最终被正确完成或推进的比例。 | | 证明系统真正完成任务,而不是只生成看似合理的回复。 |
| **Personal Hit Rate** | 个性化建议被接受、复用或被后续反馈证实有用的比例。 | | 衡量是否击中个人需求,而不是 generic helpful。 |
| **False Intervention Rate** | 用户不需要 / 不欢迎 / 时机不对的系统介入比例。 | | 主动系统最大的风险是 annoying。 |
| **User Correction Rate** | 用户纠正 transcript、intent、slots、action、timing 的频率。 | | 系统是否经常误解或脑补。 |
| **Repeat Acceptance Rate** | 用户在后续相似场景继续接受同类建议的比例。 | | 衡量长期 trust 和 habit formation。 |

## 2. Research-backed Rationale（研究支撑的设计依据）

下面的 research / evidence 并不是为了做文献综述,而是为架构决策提供支撑：哪些模块必须独立、哪些指标必须追踪、哪些风险不能忽略。

| Design Claim | 支撑材料 / 证据 | 对本系统的含义 |
|---|---|---|
| **On-device / local-first 是语音入口的默认方向** | Google 曾将 speech recognition + language understanding 模型压缩到手机本地运行,实现实时、无网 transcription 与更低 latency [R1]；Apple 的 foundation model 原则也强调 on-device processing、privacy 和 user feedback [R2]。 | Voice Perception 默认端侧；复杂语义可 hybrid / offload,但必须保留 privacy / risk metadata。 |
| **ASR 与 NLU 要分离,但要承认错误传播** | 标准 SLU pipeline 通常是 ASR -> NLU；decoupled design 便于迭代,但 ASR error 会传播并放大到 downstream NLU [R4]。 | ASR 不做 intent；NLU 需要 ASR confidence、n-best / semantic-error signal,Eval 要能做 failure attribution。 |
| **WER 不够,需要 semantic ASR error** | NIST 以 WER 作为 ASR 标准指标 [R5]；Amazon Alexa 研究指出 WER 不一定反映语义差异,语义重大的 ASR error 会导致 voice assistant downstream failure [R6]。 | Voice metrics 同时看 WER/CER、entity WER、semantic-ASR-error rate、ASR confidence calibration。 |
| **Context segmentation 是 memory 和 NLU 的基础** | 开放域长对话会跨多个 task / topic,需要新的 tracking tools [R7]；无关 memory / context 会 distract LLM 并降低 response quality [R8]。 | Context Segmentation 独立,先做 session / topic boundary、relevance scoring、memory retention。 |
| **Human-AI system 要支持纠错、解释、反馈、谨慎学习** | Microsoft HAX / HAI guidelines 是 evidence-based,强调 time services based on context、support correction、scope services when in doubt、learn / adapt cautiously、granular feedback [R9][R10]。 | Self-correction detection、low-confidence clarification、feedback collection 和 cautious preference update 是产品基本能力。 |
| **Timing 必须成为 dedicated policy** | 移动打断研究显示,在 activity transition 时发送 prompt 可能降低 perceived burden [R11]；interruptibility-aware 系统需要独立建模当前 / 未来 context [R12]。 | Timing 不只是 action 的参数,而是独立 module：should prompt now、best time、channel、intensity、cooldown。 |
| **Recommendation 不能只优化准确率** | 推荐系统研究强调 beyond-accuracy 目标(diversity、serendipity、fairness)会影响 engagement 和 satisfaction [R13]；offline evaluation 需结合 online A/B [R14]。 | Personal Hit 是独立 gate；评测要包括 acceptance、repeat acceptance、annoyance、long-term retention。 |
| **Emotion estimation 只能做 probabilistic signal** | 情绪 / 表情研究指出 facial movement 不应被当作 universal diagnostic emotional state [R15]；speech emotion recognition 在噪声、OOD、label ambiguity 下不确定性高,需要 UQ [R16]。 | Scenario & Emotion 输出 emotion_confidence / frustration_level,不做强断言；低置信度时用 neutral response。 |
| **Confidence 必须校准** | Guo et al. 发现现代 neural networks 往往 poorly calibrated；0.8 confidence 应该接近 80% accuracy,temperature scaling 是实用的校准方法 [R17]。 | 每个 module 的 confidence 都要 calibration dashboard：ECE、Brier、reliability plot、threshold tuning。 |
| **Evaluation / monitoring 是系统基础设施** | NIST AI RMF 强调 AI risk 与 context、lifecycle、impact、measurement 相关；Google ML Test Score 强调 production ML 需要 testing / monitoring / data / schema checks [R18][R19]。 | Team H 不只是做 A/B,而是做 full-stack observability、risk management、failure attribution、calibration。 |

## 3. Target Architecture（目标架构）

目标系统不是"一个模型给答案",而是一条有清晰责任边界的数据链路。每个模块都必须能独立评测、独立调试、独立归因。

> **Figure 1.** 9-module architecture with confidence / risk / privacy spine

### 3.1 End-to-end Flow（端到端链路）

```
Audio Signal
  -> Voice Perception
  -> Context Segmentation
  -> Semantic Understanding
  -> Scenario & Emotion Estimation
  -> Opportunity / Personal Hit Scoring
  -> Action Strategy
  -> Timing & Prompting Policy
  -> Action Execution & Effects
  -> Evaluation / Learning Loop
```

### 3.2 Common Data Contract（通用数据契约）

每个 module 输出业务字段之外,都必须带上 common envelope。否则 Evaluation 无法做 failure attribution,Timing 无法做 suppression,Personal Hit 无法做 learning。

| 字段 | 含义 | 示例 |
|---|---|---|
| `trace_id` | 一次 end-to-end 请求的全链路 ID | `tr_20260511_abc` |
| `context_id` | 当前 utterance / session / topic 的上下文 ID | `ctx_789` |
| `timestamp / start_ts / end_ts` | 时间戳,用于排序、latency、session boundary | `123.4 / 128.9` |
| `source_module` | 生成该 output 的模块 | `semantic_understanding` |
| `confidence` | 该模块对输出的校准置信度 | `0.86` |
| `risk_level` | low / medium / high / blocked | `medium` |
| `evidence_signals` | 该判断依据的关键 signals,可用于解释和 debug | `ASR conf=0.87, pause=1.2s` |
| `privacy_class` | none / personal / sensitive / highly_sensitive | `personal` |
| `consent_scope` | 当前是否允许记忆、个性化、跨 app action | `memory_opt_in=true` |
| `calibration_version` | confidence calibration 的模型 / 版本 | `cal_v3` |

### 3.3 Operating Modes（运行模式）

| Mode | 何时使用 | 期望行为 |
|---|---|---|
| **Mode 0: Silent Observe** | 低 need、低 hit、低 confidence、或 timing 不合适 | 不提示用户；只记录 allowed telemetry,用于后续校准。 |
| **Mode 1: Clarify** | need / could 有一定信心,但存在 missing slot 或 semantic ambiguity | 只问一个最小必要问题,不直接行动。 |
| **Mode 2: Confirmed Action** | 高 need、高 could、高 hit,但有中等 risk 或用户未授权 | 简短确认后执行,例如"要我帮你设 9 点提醒吗?" |
| **Mode 3: Direct Action** | 明确的用户命令 + 高 confidence + 低 risk + 权限已授权 | 直接执行并给用户轻量反馈。 |
| **Mode 4: Proactive Suggestion** | 用户未明确命令,但 need / could / personal hit / timing 均通过 | 使用低打扰方式提示；必须支持 dismiss / cooldown。 |

## 4. Module Specifications（模块规格）

以下 9 个模块是 recommended dedicated modules。每个模块都列出 owner、职责、输入输出、不可做事项、metrics 和 MVP scope。

### 1. Voice Perception / 端侧语音感知

| 项目 | 规格 |
|---|---|
| **Owner** | Team A: On-device Speech Team |
| **Purpose（目的）** | 把真实世界的声音稳定转为可用的 transcript + speech events。它是 perception,不是 understanding。 |
| **Submodules（子模块）** | Audio Enhancement; VAD; Wake / Trigger Detection; Local ASR; ASR Confidence; Noise Robustness |
| **Inputs（输入）** | mic 音频流；device state；噪声环境；语言提示 |
| **Outputs（输出）** | `speech_detected`, `start_ts/end_ts`, `transcript`, `language`, `vad_confidence`, `asr_confidence`, `latency_ms`, `energy_cost` |
| **Must NOT Do（不可做）** | 不要判断 intent；不要生成 recommendation；不要把低置信 transcript 当作确定事实。 |
| **Core Metrics（核心指标）** | VAD precision / recall；false trigger rate；missed speech rate；ASR WER / CER；entity WER；semantic-ASR-error rate；latency；battery / CPU / memory；confidence calibration |
| **MVP Scope** | 端侧 VAD + ASR + confidence；能输出 n-best 或 significant-ASR-error signal；所有 downstream 必须可读取 ASR confidence。 |
| **Evidence / Rationale** | ASR / NLU pipeline 存在错误传播；WER 是必要但不充分,应增加 semantic error 判断 [R4][R5][R6]。 |

### 2. Context Segmentation / 上下文切分

| 项目 | 规格 |
|---|---|
| **Owner** | Team B: Context & NLU Team |
| **Purpose** | 判断一句话属于哪个 session / topic / task,哪些信息相关,哪些需要保留为 short-term / long-term memory。 |
| **Submodules** | Utterance Segmentation; Session Boundary; Topic Boundary; Short-term Context Buffer; Context Summary; Relevance Scoring; Memory Retention Decision |
| **Inputs** | ASR transcript；timestamps；停顿；先前的对话；app / device / location signals；最近的用户操作 |
| **Outputs** | `context_id`, `segment_type`, `topic`, `summary`, `relevance_score`, `should_keep_in_memory`, `boundary_confidence` |
| **Must NOT Do** | 不要直接判断 recommendation；不要把所有 transcript 无脑塞进 memory；不要让 old context 污染 current task。 |
| **Core Metrics** | boundary accuracy；topic segmentation accuracy；wrong-context rate；context relevance precision；memory retention precision / recall；context pollution rate |
| **MVP Scope** | 支持 task-related / chitchat / correction / noise 四类 segment；对每段生成 summary + relevance_score。 |
| **Evidence / Rationale** | 长对话跨任务 / 跨 topic,需要 dedicated tracking；无关 context 会降低 personalized dialogue quality [R7][R8]。 |

### 3. Semantic Understanding / 语义结构化

| 项目 | 规格 |
|---|---|
| **Owner** | Team B: Context & NLU Team |
| **Purpose** | 把 context segment 转成 structured semantic frame：用户说了什么、想要什么、关键 slots 是什么、哪里不确定。 |
| **Submodules** | Intent Detection; Entity / Slot Extraction; Goal Detection; Constraint Extraction; Missing Slot; Ambiguity; Need / Urgency Detection |
| **Inputs** | context segment；transcript；ASR confidence；previous user context；domain schemas |
| **Outputs** | `intent`, `user_goal`, `entities`, `constraints`, `missing_info`, `urgency`, `semantic_confidence`, `ambiguity_flags` |
| **Must NOT Do** | 不要决定是否推荐；不要决定 timing；不要在缺 slot 时脑补。 |
| **Core Metrics** | intent accuracy；entity extraction F1；missing slot detection；ambiguity detection；semantic confidence calibration；user correction rate |
| **MVP Scope** | 先覆盖 reminders / calendar / messages / notes / search 四类 high-frequency domains；所有 slot 必须有 source evidence。 |
| **Evidence / Rationale** | SLU 通常包含 intent 和 slots；ASR 错误会改变 intent / slots,semantic layer 需要显式处理 uncertainty [R4][R6]。 |

### 4. Scenario & Emotion Estimation / 场景与情绪估计

| 项目 | 规格 |
|---|---|
| **Owner** | Team C: Situation Intelligence Team |
| **Purpose** | 判断用户当前处境、活动、可用性和可能的情绪信号；尤其要识别 self-correction。 |
| **Submodules** | Scene Understanding; Activity Estimation; Environmental Context; Emotional State Signal; Frustration / Stress Signal; Self-correction Detection; State Revision |
| **Inputs** | semantic frame；context segment；tone / prosody features；device / app signals；历史；行为信号 |
| **Outputs** | `scene`, `activity`, `emotion_signal`, `frustration_level`, `self_correction_detected`, `corrected_field`, `scenario_confidence` |
| **Must NOT Do** | 不要把 emotion 当作确定事实；不要用单一 modality 做强判断；不要在低 confidence 时调整用户画像。 |
| **Core Metrics** | scenario classification accuracy；self-correction recall；correction field accuracy；false emotion detection rate；frustration precision；state revision accuracy |
| **MVP Scope** | 先做 scene / activity + self-correction；emotion 只输出 low / neutral / high uncertainty signal。 |
| **Evidence / Rationale** | 情绪识别在真实场景存在 ambiguity / OOD / noise；应输出 uncertainty,必要时宁可 neutral [R15][R16]。 |

### 5. Opportunity / Personal Hit Scoring / 推荐门控与个人击中

| **MVP Scope** | 先做 deterministic + lightweight model 的 hybrid gate；输出 reason codes,便于 PM / UX review。 |

## 5. Decision Policy（决策策略）：Gate + Action + Timing

核心策略：不要让单个 module 决定是否打扰用户。最终行为必须由 gate、action strategy、timing policy 串联决定。

### 5.1 Recommendation Gate（推荐门控）

| Gate | 问题 | 默认 Threshold | 不通过时的动作 |
|---|---|---|---|
| **Need to Address** | 用户是否真的表达了需求 / 风险 / 机会? | >= 0.70 | 不介入；记录 missed-opportunity sample 用于 review。 |
| **Could Address** | 系统是否有能力、权限、工具、信息完成? | >= 0.65 | 说明不能做,或 ask for permission / info。 |
| **Personal Hit** | 这件事对这个用户个人是否有价值? | MVP >= 0.60；proactive >= 0.70 | 不做 proactive；可在明确命令时继续。 |
| **Chain Confidence** | ASR / semantic / scenario / gate / action 综合是否可信? | direct >= 0.70；clarify 0.45–0.70 | 低 confidence -> ask clarification / suppress。 |
| **Risk** | 错误行动会不会带来高成本、隐私、财务、安全风险? | low / medium 允许；high 需要 confirmation；blocked 禁止 | 高 risk 必须确认或阻断。 |
| **Timing** | 现在提示是否合适? | >= 0.65 或 urgency=high | 延后、silent notification、或 suppress。 |

### 5.2 Suggested Policy Logic（建议的策略逻辑）

MVP 阶段的伪代码:

```python
if risk_level == 'blocked':
    suppress_and_log(reason='blocked_risk')
elif semantic_confidence < 0.45 or asr_confidence < 0.50:
    ask_clarification_or_repeat()
elif missing_info and need_to_address_score >= 0.70:
    ask_minimal_clarification()
elif need_to_address_score < 0.70:
    silent_observe()
elif could_address_score < 0.65:
    explain_limitation_or_request_permission()
elif personal_hit_score < 0.60 and not explicit_user_command:
    suppress(reason='low_personal_hit')
elif risk_level == 'high':
    ask_confirmation()
elif timing_score < 0.65 and urgency != 'high':
    defer_or_silent_notification()
else:
    execute_or_prompt(action_strategy)
```

## 6. Evaluation & Learning Loop（评测与学习闭环）

Evaluation 不是最后上线前的一次测试,而是系统每天运行的基础设施。每个 module 需要独立评测,同时需要 end-to-end attribution。

### 6.1 Dashboard Stack（仪表盘体系）

| Dashboard | Owner | 核心视图 |
|---|---|---|
| **Voice Quality** | Team A + H | VAD PR curve；false triggers；missed speech；WER / CER；entity WER；latency；battery；noisy environment slices |
| **NLU & Context** | Team B + H | intent accuracy；slot F1；missing slot；ambiguity；wrong-context rate；context retention；correction-driven errors |
| **Situation & Correction** | Team C + H | scene accuracy；self-correction recall；emotion uncertainty；false emotion labels；scenario drift |
| **Personal Hit & Gate** | Team D + H | need / could / hit distributions；false interventions；missed opportunities；按 user segment 的 acceptance；threshold sweeps |
| **Action & Execution** | Team E / G + H | candidate ranking；wrong action；tool failure；task completion；undo / rollback；helpful / workable / liked |
| **Timing & UX** | Team F + H | prompt acceptance；dismiss；ignore；complaint；cooldown；timing success；notification fatigue |
| **Calibration & Risk** | Team H | ECE；Brier；reliability diagrams；按 module 的 confidence vs accuracy；risk incident review；privacy-safe logging coverage |

### 6.2 Labeling Taxonomy（标注分类体系）

| Label Category | 示例 | 使用方 |
|---|---|---|
| **ASR / Voice** | correct transcript；semantic-ASR-error；wake false positive；noisy environment | Team A, H |
| **Context** | session boundary；topic boundary；relevant / irrelevant memory；should_keep | Team B, H |
| **Semantic** | intent；entities；slots；missing_info；ambiguity；urgency | Team B, E |
| **Scenario** | working / driving / meeting；availability；self-correction；corrected field | Team C, F |
| **Personal Hit** | accepted because personal；generic useful；irrelevant；annoying | Team D, H |
| **Timing** | good timing；too early；too late；interruptive；channel wrong | Team F, H |
| **Action Effects** | helpful；workable；liked；repeated；undone；caused correction | Team G, D, H |

### 6.3 Confidence Calibration Plan（置信度校准方案）

- **Per-module reliability plots**：ASR confidence vs transcript correctness；semantic_confidence vs intent / slot correctness；personal_hit_confidence vs acceptance。
- **Metrics**：Expected Calibration Error (ECE)、Brier score、NLL、threshold-specific precision / recall。
- **Action policy**：High confidence + low risk 才能 direct action；medium confidence 进入 clarification；low confidence 则 suppress。
- **Calibration cadence**：每周看 threshold drift；每次模型更新前后必须比较 calibration,不只比较 accuracy。

### 6.4 Offline + Online Evaluation（离线 + 在线评测）

| Stage | 目标 | 示例测试 |
|---|---|---|
| **Offline eval** | 快速发现明显错误和 threshold trade-off | module benchmarks；ablation；counterfactual gate replay；edge-case sets；按噪声 / 语言 / 口音的 robustness |
| **Shadow mode** | 不打扰用户,只评估系统是否会想介入 | would_prompt logging；false positive review；missed opportunity labeling |
| **Limited beta** | 小流量验证 user value 和 annoyance | 先做 explicit commands；proactive 只在 low-risk 场景；每日 failure review |
| **A/B test** | 确认 online behavior 和 long-term signals | acceptance；repeat acceptance；correction；false intervention；retention；support tickets |
| **Post-launch monitoring** | 持续发现 drift、feedback loop、风险 | training-serving skew；calibration drift；user segment regressions；tool / API failures |

- **周五 release check**：没有 confidence、risk、rollback、dashboard 就绪,不允许发布任何模型 / 策略变更。

## 8. Risks, Guardrails & Open Questions（风险、护栏与待决项）

### 8.1 Core Risks（核心风险）

| 风险 | 症状 | Guardrail（护栏） |
|---|---|---|
| **Over-intervention（过度介入）** | 用户觉得系统烦、乱推荐、打断工作流 | 专门的 personal hit + timing gate；cooldown；dismiss learning；false intervention dashboard |
| **Over-personalization（过度个性化）** | 系统把偶然行为当成偏好,越学越偏 | preference update 需要重复证据；cautious adaptation；用户可控 |
| **ASR / NLU error cascade（错误级联）** | 听错导致 wrong action | ASR confidence；semantic-ASR-error detection；低 confidence 时 clarification |
| **Context pollution（上下文污染)** | 旧话题 / 无关 memory 影响当前建议 | context segmentation；memory relevance score；retention policy；retrieval precision eval |
| **Emotion overclaiming（情绪过度断言）** | 系统武断判断用户情绪 | emotion 仅作 uncertainty signal；neutral phrasing；不基于 emotion 做 high-stakes 决策 |
| **Risky direct action（高风险直接执行）** | 未确认就执行高成本动作 | risk taxonomy；必须 confirmation；undo / rollback；blocked categories |
| **Metric gaming（指标博弈）** | 优化 acceptance 但降低 trust | 与 false intervention、correction、repeat acceptance、satisfaction、risk incidents 一起平衡 |
| **Training-serving skew（训练 / 服务差异）** | offline 好、online 差 | serve-time feature logging；shadow mode；online A/B；monitoring |

### 8.2 Open Questions for Team Discussion（待团队讨论的问题）

1. **Personal Hit 的 first-party data scope**：哪些 user history / preferences / recent behavior 可以使用?是否需要 explicit opt-in?
2. **Proactive beta 的 allowed domains**：只做 reminders / calendar / follow-up,还是包含 content / recommendation?
3. **Timing policy 的 user controls**：全局开关、category cooldown、quiet hours、meeting / driving suppression 如何设计?
4. **Risk taxonomy**：哪些 action 必须 confirmation?哪些 action 永远不能 proactive?
5. **Evaluation labels 的成本**：哪些 label 由 human review,哪些由 implicit feedback,哪些用 weak labels?
6. **Cloud / off-device fallback**：哪些模块可以走 cloud?触发条件、隐私保护、用户透明度如何定义?
