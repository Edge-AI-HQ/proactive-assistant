# Preference Consolidation Agent（偏好整理 · Goal 驱动）

> 本文是 **goal 驱动实现规格**，给自动实现循环（Claude Code go）用。结构：一个总目标 → 若干有序 goal → 每个 goal 有「验证门（自动，循环退出条件）」和「人工验收（循环外，不进门）」。
> **循环规则**：实现一个 goal，跑它的验证门命令，全绿才算这个 goal 完成；任何门红就继续改同一个 goal。**LLM 行为类（整理得对不对、塌得合不合理）不可确定性断言，绝不作为循环门**——只在人工验收里列。验证门只断言 plumbing（route 存在、SDK 有方法、prompt 含某段、dispatcher 路由某 kind、DB 落某行）。

## 背景（为什么要这个）

`057_pai_preference_lifetime.sql` 之后，偏好的「懒/读时」整理已经有了：临时偏好 `expires_at` 自动过期、generator 在读取时「冲突跟最新那条、notes 记冲突」。但这只是按住急症，**批量/主动整理仍然缺**：

- active 持久偏好**只进不理**——`supersede` / `archive` 至今没有批量调用者。攒一年 `list(active)` 返回几十条，generation **每一批都要把同一堆矛盾重新读进来、重新在读时解一遍**，结论生成完就丢。
- generator prompt 自己承认「persistent 应该和 `profile.preferences` 一致，冲突就取较新的并标记 mismatch」——等于系统**预期两层会漂开**，却没有任何东西定期对齐。

consolidation 把「懒路径做不了的四件事」做掉、落库、之后大家省事：①矛盾偏好塌成当前事实（supersede 到现存赢家）+ 退役死偏好；②与 `profile.preferences` **双向对齐**（偏好→profile merge，且反向修正/清掉 profile 里过期矛盾的 key）；③outcome 调权重（某主题老被 dismiss → 降该偏好 `weight`/`confidence`，带 floor）；④仲裁时把 outcome 当弱信号辅助破平/判死。

> 上游讨论见本文末「相关」。本 plan 做**偏好层 + profile.preferences 双向对齐 + outcome reweight**；memory 层级压缩、强 outcome 归因（preference-id 级）推后。

## 总目标

新增第四个 evolution 值班场景 **consolidation**，跑在 chat 进程 code-mode sandbox（复用 dream/evolve harness），**每天凌晨 3 点（按用户时区）**把某用户**累积的 active 持久偏好**整理成「当前事实」的干净集合，让下一次生成读到的是已沉淀的结论，而不是每批现解的矛盾堆：

- **矛盾塌成一条**：同 `(scope, 主题)` 下对立/重复的偏好，按 recency 选**最近那条现存 active 偏好**当赢家，把败者 `supersede` 到**它的 id**（N 条 → 1 条）。**不新建合成行**——保留赢家原始 `source`，避免机器编的偏好冒充用户原话（见现状锚点 `_resolve_source`）。
- **死偏好退役**：陈旧、无后继、近期零互动且过了年龄 floor 的孤儿偏好，`archive`。
- **profile 双向对齐**：耐久且验证过的赢家 `profile.merge_preference` 进 `pai_profile.preferences` 桶（复用现有 key）；**反向**——profile 桶里和当前 active 偏好集矛盾/已过期的 key，修正（覆盖成当前 stance）或清掉（整桶 read-merge-write 保 siblings）。
- **outcome 调权重**：某主题卡近期老被 dismiss → 用 `preferences.reweight` 降对应偏好的 `weight`/`confidence`（**带 floor，不清零**）；并辅助 recency 破平 / 判定孤儿是否真死。**但 outcome 永不驱动 `supersede`/`archive`**——结构变更只由 recency + 显式陈述决定（归因弱，见不变约束 3）。

per-user；每个动作走 `pai_evolution_runs`（`trigger_kind='consolidation'`）审计；supersede 链保留 → 全可逆。

## 不变约束（循环任何时候都不能违反）

1. **不动 057 的读时行为**：`preferences.list(active)` 的 `expires_at` 过滤、generator「本批跟最新」的 prompt 措辞**一行不改**。consolidation 是把读时结论**固化**，不是替换读时逻辑。
2. **不需要 migration**：`consolidation` 已在 `pai_evolution_runs.trigger_kind` 的 CHECK 里（`013_pai_evolution.sql`）；`pai_scheduled_tasks.kind` 是开放枚举无 CHECK（`021_pai_scheduler.sql`）。**禁止**为本 plan 新增 migration；若发现需要新列，停下来报告，不要擅自加表。
3. **outcome 只能改权重，永不驱动结构变更**：卡片 `sources[]` 只引 memory/signal/gmail/profile/world id，**不引 preference id**；偏好影响只散在 `PlanOutput.notes`（落 `pai_pipeline_runs.iterations`）。所以 outcome 只按 scope/topic 粗匹配，能做的只是 `preferences.reweight` 调 `weight`/`confidence`（**带 floor，不清零**）+ 辅助 recency 破平/判死；`supersede`/`archive` 永远由 recency + 显式陈述决定，**outcome 不得删任何偏好**。preference-id 级强归因（让 outcome 驱动结构）推后。
4. **trust boundary + 不冒充用户**：consolidation 跑在 chat 进程，经 `/api/agent/*` + per-run JWT 调用，不碰 master credential。`source` 由服务端按 principal 决定（`_resolve_source` 普通 run 恒 `user`，无 `agent` 路径），不信 agent 自报。**因此 v1 禁止 `preferences.add` 合成新偏好行**——否则机器合成会被盖 `source='user'` 冒充用户原话；塌矛盾一律 `supersede` 到现存 active 赢家。合成行（需 `source='agent'`）推后。
5. **安全护栏**：① 年龄 floor——新于 N 天（默认 14）的偏好不许 `archive`；② reweight 有 floor——单次 dismiss-burst 不能把 `weight`/`confidence` 清零（设下限，如 0.1）；③ profile 反向清 key 必须 read-merge-write **只删目标 key、保 siblings**，禁止整桶盲写；④ 每个写动作（supersede / archive / reweight / merge）必须可在 `pai_evolution_runs` 审计行查到；⑤ 整理可逆（靠 supersede 链 + archived 状态，不做物理删除）。
6. **不主动 kick 重生成**：整理即时落库，等下一次自然生成读到干净集合。
7. **v1 范围**：偏好层 + `profile.preferences` 双向对齐 + outcome reweight。临时偏好不归它管（已被 057 过期接管）；memory 层级压缩、preference-id 级强归因、合成新偏好行、用户可见开关全部推后（见末尾「推后」）。
8. 遵守仓库编码原则：无 `as any` / `# type: ignore` / `eslint-disable` / `# noqa`（除非注释说明唯一选项）；改动最小化；复用 dream/evolve/memory-archive 已有 pattern，不发明新写法。

## Goal 1 — 偏好 archive + reweight 通路（无依赖）

**目标**：补齐 consolidation 写偏好需要的两个 endpoint：①把现成的 `PreferenceRepository.archive(id)` 暴露成 agent route + SDK（退役无后继的死偏好）；②**新增** `set_weight` 方法 + route + SDK（让 outcome 调 `weight`/`confidence`）。两者都 additive，无 migration（weight/confidence 列已存在）。

**交付物**：

- `web/db/repositories/preferences.py`：新增 `async def set_weight(self, id, *, weight=None, confidence=None) -> PreferenceRow | None`——只 UPDATE 该 user 该 id 的 `weight`/`confidence`（传入哪个改哪个，COALESCE 保留另一个），不存在返回 None。
- `web/routes/agent/preferences.py`：
  - `@router.post("/archive/{preference_id}")` → `repo.archive(...)`，404 if missing/already archived。**完全镜像** `web/routes/agent/memory.py:archive_memory`。
  - `@router.post("/reweight")`（body `{id, weight?, confidence?}`）→ `repo.set_weight(...)`，404 if missing。鉴权 `current_agent_run` + `user_scoped_tx`。
- `packages/pinai_sdk/src/pinai_sdk/_client.py`：`Preferences` 类加 `archive(self, id)` → `_post(f"/archive/{id}", {})`（镜像 `Memory.archive`）、`reweight(self, id, *, weight=None, confidence=None)` → `_post("/reweight", {...})`。同步更新顶部 docstring endpoint 清单。

## Goal 2 — consolidation agent + chat run 路由（依赖 Goal 1）

**目标**：新增 `chat/agents/consolidate.py`（code-mode，照 dream/evolve harness）+ chat run 路由 `/agent/run/consolidate`。system prompt 把「输入 + 仲裁规则 + 写操作策略 + 输出契约」写死。

**交付物**：

- `src/pinai_agents/chat/agents/consolidate.py`：`run_consolidate(*, virtual_key, user_id, run_id, run_jwt=None, model=None) -> dict`，结构镜像 `dream.py`（`create_oneshot_sandbox(run_jwt=..., scope_label="consolidate")` → `create_deep_agent(...)` → `ainvoke` → `delete_sandbox_now` → 返回 `{"summary": ...}`）。system prompt 顺序同其它 agent：identity → trigger → goal → `SANDBOX_PREAMBLE` → `CODE_MODE_GUIDANCE` → `GROUNDING_POLICY` → hard_rules → output_contract。
- `src/pinai_agents/chat/routes/run.py`：新增 `@router.post("/agent/run/consolidate")` → `run_consolidate(...)`，鉴权/参数解析镜像 `post_run_dream`。

**system prompt 必须包含的语义（hard_rules 段落）**：

输入（首次 gather，parallel）：
- `client.preferences.list(status="active", limit=500)` —— 整理对象，**只处理 `durability='persistent'`**（临时的已被 057 过期接管，不碰）。
- `client.profile.get()` —— 拿 `profile.preferences` 桶 + goals 做跨层对齐参照。**merge 前必读现有 key**，用来复用 main chat 已写的 key、避免重复 sibling（见写操作映射）。
- `client.preferences.list(status="superseded", limit=100)` —— 已废弃历史（有界），**防止复活用户已放弃的 stance / 反复重判同一矛盾**。
- `client.feedback.list(kind="card_action", since=<上次 consolidation run>)` + `client.cards.recent(limit=50)` —— outcome 弱信号，**按 scope/topic 粗匹配**。

仲裁规则（确定性优先级，写进 prompt）：
1. 按 `(scope, 主题)` 分组，组内找 polarity 对立或重复表述。
2. 组内裁决优先级：**(a) 显式 recency 赢**（最近那条现存 active 偏好 = 当前 stance，胜者不变）→ (b) outcome 用来辅助：recency 平手时破平、判定孤儿是否真死（某主题近期零互动/全 dismiss）、以及决定要不要 reweight（见下），**但不翻转 recency、不删任何偏好** → (c) 同日平手按 `weight` 破平。
3. 写操作映射（**只用 supersede / archive / reweight / merge_preference / profile.upsert，不调 `preferences.add` 合成新行**）：
   - **塌矛盾/去重**：真矛盾或同 stance 重复 → 选最近那条现存 active 偏好当赢家，把败者 `preferences.supersede(old_id=败者, new_id=赢家)`（赢家本就 active 满足断言；保留其原始 `source`）。
   - **退役死偏好**：陈旧、无后继、近期零互动、**年龄 ≥ floor 14 天** → `preferences.archive(id)`。
   - **outcome reweight**：赢家/留存偏好对应主题近期老被 dismiss → `preferences.reweight(id, weight=降后值)`（**带 floor 0.1，不清零**）；表现好可适度回调。
   - **profile 正向**：赢家若耐久且验证过 → `profile.merge_preference(key, value)`：**先在已 gather 的 `profile.preferences` 桶里找覆盖同 scope/主题的现有 key，命中就复用那个 key merge**（`merge_profile_preference` 浅合并：同 key 覆盖、异 key 加 sibling——复用现有 key 才不会和 main chat 写的重复），没命中才用确定性 slug `pref_<scope>_<subject-slug>` 新建。
   - **profile 反向对齐**：profile 桶里和当前 active 偏好集**矛盾**的 key → 用 `merge_preference` **覆盖**成当前 stance；**已过期/已无对应 active 偏好**的 key → read（`profile.get`）→ 内存删该 key → `profile.upsert(preferences=整桶)`，**只删目标 key、保 siblings**。
   - **严禁新建合成偏好行**（consolidation run 的 source 会被盖成 `user`，机器合成会冒充用户原话）。
4. 护栏：年龄 floor；reweight floor（不清零）；profile 反向清 key 只动目标 key 保 siblings；empty 是诚实的（没矛盾就别动）；outcome 永不 supersede/archive。

输出契约（末尾 assistant message 仅 JSON）：

```json
{"preferencesSuperseded": int,
 "preferencesArchived": int,
 "preferencesReweighted": [{"id": "str", "from": 0.0, "to": 0.0, "reason": "str"}],
 "profileKeysMerged": ["str"],
 "profileKeysCorrected": ["str"],
 "profileKeysRemoved": ["str"],
 "conflictsResolved": [{"scope": "str", "winner": "str", "losers": ["str"]}],
 "summary": "str"}
```

## Goal 3 — scheduler 接线 + lifecycle + 空转护栏（依赖 Goal 2）

**目标**：dispatcher 能派 `consolidation` kind，按 `_dispatch_dream` 模板包 evolution lifecycle；加进长跑 kind；**每天凌晨 3 点（按用户时区）触发** + 便宜的「没东西可整就 no-op」护栏（daily 大多数天会 skip，护栏是控成本关键）。

**交付物**：

- `web/scheduler/dispatcher.py`：
  - kind 路由加 `elif kind == "consolidation": await self._dispatch_consolidate(task, run_id)`。
  - `_dispatch_consolidate`：**镜像 `_dispatch_dream`**——`EvolutionRepository.create(trigger_kind="consolidation", context_summary=f"Consolidation run {run_id}", run_id=run_id)`（status running）→ `_call_chat("/agent/run/consolidate", task, run_id)` → 异常 `fail()` / 成功 `complete()`。
  - **空转护栏**（在 create/调 chat 之前，**不新增 repo 方法，复用现有 list**）：`EvolutionRepository.list(trigger_kind='consolidation', limit=1)` 取上次 run 的 `started_at`（首次为 None）；`PreferenceRepository.list(status='active', limit=500)` 取回后在 Python 里 filter `durability=='persistent'` 且（`started_at` 为 None 或 `created_at > started_at`），计数；< 阈值 N（默认 5）则 log skip 直接 return，不建 evolution 行、不调 chat。
  - `_LONG_RUNNING_KINDS` 加 `"consolidation"`。
- schedule 播种（**确定触发点，daily-local 镜像 dream**）：在首次 `GET /api/profile` 的 `_ensure_auto_generate_schedule` 旁边新增 `_ensure_consolidation_schedule`：若该 user 没有 `kind='consolidation'` 的 schedule 行就 upsert 一行，`trigger_kind='schedule'`，`next_run_at` 用**镜像 `_next_auto_dreaming_fire` 的 `_next_consolidation_fire(timezone, hour=3)`** 算出用户时区当天/次日 03:00 → UTC（cron 语义 `"0 3 * * *"`），task id `consolidate.auto.{user_id}`（沿用 `_auto_dreaming_task_id` 风格）。跑完后下一次 fire 同样按 daily-local 重算（dispatcher/tick 已有 recurring 续期逻辑，沿用，不另写）。**v1 不加用户可见开关**：always-on daily 3am，靠空转护栏控成本（决策见风险表）。

## 推后（本规格不实现，循环不要碰）

- **memory 层级压缩**：把碎片化 `pai_memory` 归并成更高阶图式（schema）。同一 harness 可扩，但输入/规则不同，单独 phase。
- **合成合并偏好（`source='agent'`）**：要让 consolidation 写一条新的「当前事实」偏好（而非 supersede 到现存赢家），需要 `_resolve_source` 支持把 consolidation run 盖成 `source='agent'`（现在只有 user / internal_operator），否则机器合成行冒充用户原话。v1 一律 supersede 到现存赢家。
- **preference-id 级强归因**：v1 的 outcome reweight 只能按 scope/topic 粗匹配（卡片 `sources[]` 不引 preference id）。要让 outcome 精确到单条偏好、甚至驱动 supersede，需要生成在 card `sources[]` 里引 preference id（现在不引）。
- **事件/阈值触发升级**：v1 是 daily 3am + 计数护栏；「检测到矛盾就立即触发」「dismiss 率飙升触发」需要新 producer，推后。
- **用户可见开关 / dreaming panel 展示**：consolidation run 默认不进 dreaming-history panel（panel 只 filter `daily_dream`/`manual`）；要展示和加 settings 开关另说。

## 风险和决策

| 风险 | 决策 |
|---|---|
| daily 触发空跑烧 LLM/sandbox 钱 | daily 3am 触发，但调 chat 前查「距上次 run 新增 active persistent 偏好数 < N 则 skip」——大多数天会 skip，便宜护栏挡住空转。 |
| outcome 归因弱却拿来删偏好，误杀用户真实意图 | 硬约束：outcome **只能 reweight（带 floor 不清零）+ 辅助破平/判死**，**永不 supersede/archive**；结构变更只由 recency + 显式陈述决定（不变约束 3）。 |
| profile 反向清 key 整桶 wholesale 替换误删 siblings | read-merge-write：`profile.get` 读全桶 → 内存只删目标 key → `profile.upsert(preferences=整桶)`；改其它现有 key 一律走 `merge_preference` 覆盖，不整桶盲写（不变约束 5③）。 |
| 机器合成偏好冒充用户原话 | `_resolve_source` 只有 user / internal_operator 无 agent；v1 **不合成新行**，只 supersede 到现存 active 赢家（保留其原始 source）。合成 + agent source 推后。 |
| `profile.preferences` 桶 key 撞 main chat 的 ad-hoc key 产生重复 sibling | **已修**：consolidation merge 前先读现有 `profile.preferences` key，命中同 scope/主题就复用、不命中才用确定性 slug `pref_<scope>_<subject-slug>`。`merge_profile_preference` 按 top-level key 浅合并，复用现有 key 即覆盖不重复。统一 main-chat 侧 keying 推后。 |
| 整理误删，用户找不回 | 不物理删除：`supersede` 留链、`archive` 留状态；全程 `pai_evolution_runs` 审计，可回查可逆。 |
| 把刚说的偏好当矛盾删掉 | 年龄 floor（默认 14 天）：新偏好不许 archive，给它证明自己的机会。 |
| 和 057 读时逻辑打架 | consolidation 只固化读时结论，不改 `list` 过滤和 generator prompt（不变约束 1）。 |
| 擅自加 migration | `consolidation` 和新 kind 都不需要 schema 变更（不变约束 2）；发现要加列先停下报告。 |
| 循环在 LLM 行为门空转 | 验证门只断言 plumbing（route/SDK/prompt 锚点/dispatcher 路由/DB 行）；整理质量进人工验收。 |
