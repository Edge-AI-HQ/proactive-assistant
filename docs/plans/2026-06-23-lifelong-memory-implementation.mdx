> **状态**：实施方案（2026-06-23）。配套设计 SSOT [Lifelong Memory 系统](./2026-06-23-lifelong-memory-system)（架构 why）；本份是 **how to land**。消费侧见 [Proactive + 卡片生成](./2026-06-23-proactive-card-generation)。
> **依据**：2026-06-23 对 `backend/` memory 实现的命名 inventory（代码核实，origin/main `e5876040`）。落 backend 三 service 重构 [§信任边界](./2026-06-21-backend-rearchitecture)。
> **分支**：`feat/lifelong-memory`（基于 origin/main）。

## 〇、总策略：expand-contract，且"可重抽"省掉最难的一环

用户拍板**全面重构、不迁移历史数据**（产品测试中，dev 可重抽）。这把通常最痛的"双写迁移历史数据"直接删掉。所以是干净的三段：

1. **Expand（P1–P4）** — 新架构（L0/L1/L2 + 3 工具 + evolve 三合一）与老架构**并存建起来**，新链路独立可端到端验证；老链路这期间不动，dev 仍能用。
2. **验证关口（P5）** — 一个用户走**完整**链路（connector ingest → `pai_raw` → `pai_events` → evolve → markdown 画像 → agent 用 `events_search` + 画像出卡/对话），确认**有效**——不是"表建起来"就算，是 agent 真的用上了。
3. **Contract（P6–P7）** — 消费侧切到新链路，老表/API/工具/agents **整体删**（不迁移）。

**三段式信任边界纪律（贯穿）**：engine 看不到 memory 表（scoped DSN，#197）。每个新工具 = **api endpoint（agent 面 JWT）+ SDK 方法 + engine direct tool** 三段，真 CRUD/预算/威胁扫描只在 api 侧 `domains/user_model/`。

**RLS 纪律**：新表（`pai_raw`/`pai_events`/`pai_user_strings`）都带 RLS policy（RLS 现在真生效，#202–204），走 `user_scoped_tx` 的 `SET LOCAL ROLE pai_app`。

### 6.3 Final review 发现的实现细节（与设计 doc 字面差异，2026-06-24）

独立对照审查（9 维度全建对，符合度高）记录 3 处实现 vs 设计 doc 的字面差异，均代码自洽、非 bug，列此备查：

1. **`pai_events.curation_status` 取值 = `pending`/`active`/`filtered_out`/`archived`**（`111_pai_events.sql` CHECK + `events.py`）；设计 doc 早期文字写 `curated`——实现用 `active` 表「留用」、`archived` 表 supersede 后的旧行。以代码为准，设计 doc 文字待顺手对齐。

3. **检索默认只见 `active`，pending 不可见**（`events.py` `search_semantic` 硬滤 active、`search_structured` 默认 status=active）：projector 投影的新事件是 `pending`，须等 evolve（on_event/daily）CURATE promote 到 `active` 才被 `events_search` 召回；agent 主动 `event_append` 的事件直接 `active` 立即可见。**这是有意的 quality gate（evolve 做语义判定、避免噪音 raw 直接进语义检索），但意味着「connector ingest 完 → chat 能语义搜到」之间夹一次 evolve。运维/eval 须保证 evolve 调度在线，否则新 connector 事件语义检索为空。** generation 侧不受影响——它另有 connected_raw 全量新鲜 raw（透明读 pai_raw）+ events 的 importance 背景，双路互补。
