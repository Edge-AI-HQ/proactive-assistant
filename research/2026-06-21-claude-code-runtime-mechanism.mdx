# Claude Code 运行机制剖析(2026-06-21)

> 目的:为「自建一个强度对标 Claude Code 的 agent」做 step-1 调研 —— 先把 Claude Code 的运行机制吃透。
>
> 方法:不看官方文档、不靠记忆,而是直接逆向一段真实 session 的落盘 transcript。Claude Code 把每个 session 以 append-only JSONL 事件流存在 `~/.claude/projects/<project>/<session-uuid>.jsonl`,子 agent 与大结果另存同名目录下。用 `jq` 对事件做结构化聚合,再读代表性记录还原机制。本文所有结论均有 transcript 字段佐证。
>
> 标本:一次 session(uuid `d36a4747…`)主 transcript 1759 行 / 5.8 MB,726 个 assistant 回合、30 个 subagent transcript、2 个卸载的大工具结果。这段 session 几乎触发了 Claude Code 所有高级机制,是理想标本。本文剖析的是 Claude Code 这个 harness 本身,与被重构的 PIN AI 后端代码无关。

## 0. 标本背景:它在干什么

这是一次 **~3.7 小时、66.3 万 output token 的自主后端重构**(`goal_status.durationMs=13314471, tokens=663138, iterations=2`)。25 条真人 prompt 驱动,流程是:**架构讨论 → 按模块对照代码做可行性验证 → 自主分阶段执行重构 → 提 PR**。主 agent 扮演 orchestrator(自称 `team-lead`),分阶段并行派出 30 个 subagent,把后端拆成 contracts / engine / api / libs-db / reward-dashboard 多 service。

理解这个背景很重要:下面每一个机制,都是在「一句话目标 → 无人值守跑数小时 → 真正完成」这个压力场景下被同时调用起来的。

---

## 1. 持久化模型:一切都是 append-only JSONL 事件流

Claude Code 不存「对话数组」,存**事件日志**。一个 session = 一个主 `.jsonl`,每行一条 JSON 事件。目录布局:

```
<session-uuid>.jsonl                       # 主对话事件流(唯一真源)
<session-uuid>/
  ├── subagents/
  │     ├── agent-<name|hash>.jsonl        # 每个 subagent 独立的事件流
  │     └── agent-<name|hash>.meta.json    # subagent 元信息(类型/团队/模型/权限)
  └── tool-results/<id>.txt                # 超大工具结果「卸载」到磁盘
/private/tmp/claude-501/<session>/tasks/<task-id>.output   # 后台任务输出落盘
```

主 transcript 的事件 `type` 分布,就是 Claude Code 的「运行时事件总线」:

| type | 数量 | 作用 |
|---|---|---|
| `assistant` | 726 | 模型回合(含 thinking / text / tool_use) |
| `user` | 329 | 真人输入 + 工具结果 + 合成注入(共 7 个变体) |
| `worktree-state` / `permission-mode` / `mode` / `ai-title` | 各 113 | 每轮 UI / session 状态快照 |
| `last-prompt` | 112 | 最近 prompt 缓存 |
| `attachment` | 59 | **上下文动态注入**(各类 system-reminder) |
| `queue-operation` | 33 | **消息队列**(异步唤醒的核心) |
| `file-history-snapshot` | 28 | **文件 checkpoint**(rewind / undo) |
| `system` | 26 | hook 输出 / 计时 / 压缩分界 |

`user` 记录有 7 个结构变体,靠不同字段区分来源:带 `toolUseResult + sourceToolAssistantUUID` 的是工具结果(269 条,与 269 个 tool_use 严格 1:1);带 `origin + permissionMode + promptSource` 的是真人输入;`isCompactSummary` 是压缩摘要;`interruptedMessageId` 是一次 ESC 中断;`isMeta` 是系统注入。

> **启示**:用 append-only 事件流而非可变对话数组做真源,天然支持 resume / rewind / 审计 / 子进程分文件。状态(mode / permission / title)与消息**同流但分 type**,UI 可独立投影。

## 2. 核心 agent loop:thinking → tool_use → tool_result 的 ReAct 循环

一条 `assistant` 记录的 `message.content` 是块数组,三种块共存(全 session 计数):

- `thinking`(240 块)—— **extended thinking,重度使用**,几乎每个回合先想再做。
- `text`(225 块)—— 给用户看的话。
- `tool_use`(269 块)—— 工具调用,带 `id` / `name` / `input`。

每个 `tool_use` 严格对应后续一条 `user` 记录里的 `tool_result`(269 ↔ 269),通过 `sourceToolAssistantUUID` 回链,并用 `toolUseResult` 字段承载**结构化原始结果**(不只是给模型的文本)。

`message.usage` 暴露了计费与缓存模型:

```json
{"input_tokens":6530, "cache_creation_input_tokens":39142, "cache_read_input_tokens":16088,
 "output_tokens":2290,
 "cache_creation":{"ephemeral_1h_input_tokens":39142,"ephemeral_5m_input_tokens":0},
 "iterations":[…], "service_tier":"standard", "speed":"standard"}
```

要点:**prompt caching 有 1h / 5m 两档 TTL**。长 system prompt + 工具定义 + 历史前缀走 `cache_read`,只有增量进 `cache_creation`。这是长 session 成本可控的关键。

> **启示**:loop 本身是教科书 ReAct;工程量在 ①把 thinking 作为一等块持久化,②结果「结构化 + 文本」双形态,③缓存分层把前缀钉住。

## 3. 工具体系

### 3.1 实际调用频次(主 transcript)

```
128 Bash | 45 Edit | 39 Read | 21 Agent | 11 TaskUpdate
  9 Write |  8 TaskCreate | 4 AskUserQuestion | 3 ToolSearch | 1 SendMessage
```

六类:**执行**(Bash)、**文件**(Read / Edit / Write)、**多 agent**(Agent / SendMessage)、**任务台账**(TaskCreate / TaskUpdate)、**问人**(AskUserQuestion)、**工具发现**(ToolSearch)。

### 3.2 `toolUseResult` 的结构化形态(每类工具一套 schema)

| 工具 | toolUseResult 结构 |
|---|---|
| Bash | `{stdout, stderr, interrupted, isImage, noOutputExpected, staleReadFileStateHint?}` |
| Edit | `{filePath, oldString, newString, originalFile, replaceAll, structuredPatch, userModified}` |
| Read | `{file, type}` |
| **Agent** | `{agent_id, agent_type, name, team_name, teammate_id, model, status, is_splitpane, tmux_pane_id, tmux_session_name, tmux_window_name, plan_mode_required, color, prompt}` |
| TaskCreate | `{task:{id, subject}}` |
| TaskUpdate | `{taskId, statusChange, updatedFields, success}` |
| ToolSearch | `{query, matches, total_deferred_tools}` |

Edit / Write 都带 `structuredPatch` 和 `userModified` —— 支撑文件 checkpoint 与「用户手改检测」。

### 3.3 延迟工具 + ToolSearch(关键扩展性机制)

`ToolSearch` 结果显示 `total_deferred_tools: 137`。**137 个工具默认不进 system prompt**,只留名字;用 `select:TaskCreate,TaskUpdate,TaskList` 这类查询按需把 schema 拉进上下文才可调用。连 `TaskCreate` / `SendMessage` 这种核心工具都是延迟加载的。变化以 `attachment.type: deferred_tools_delta` 增量注入(`added / removed / readded / pendingMcpServers`)。

> **启示**:工具一多(MCP server 一接就几十上百),全量塞 system prompt 会爆 token 且降准。正解是**两段式**:延迟工具只暴露名字 → 模型按需 search 加载 schema。这是 1000+ 工具规模下的必备设计,也是最容易被低估的一项。

## 4. 多 agent 编排:team-lead + 具名 teammate 的「团队」模型

### 4.1 两种 subagent

`Agent` 工具的 `input` 有无 `name` 决定两种形态(meta.json 印证):

**A. 具名 teammate(传 `name`)** —— 19 个,`taskKind: in_process_teammate`:

```json
{"agentType":"phase4-orchestration","name":"phase4-orchestration",
 "taskKind":"in_process_teammate","teamName":"session-d36a4747","color":"pink",
 "model":"claude-opus-4-8","permissionMode":"bypassPermissions","planModeRequired":false}
```

常驻、可被 `SendMessage` 寻址、归属同一 `teamName`、有颜色标识、自带 model 与权限模式。

**B. 匿名 task(不传 `name`)** —— 11 个,只有 `{agentType, description, toolUseId}`。一次性,`toolUseId` 回链派生它的 Agent 调用。

### 4.2 嵌套与拓扑

主 transcript 21 次 `Agent` 调用 = 19 具名 + 2 匿名;磁盘上却有 30 个 subagent → **9 个是 teammate 自己嵌套派生的**(subagent 内部也能调 Agent)。这次重构的编排拓扑:

```
team-lead(主 agent)
├─ domain-* ×7   (billing / usermodel / generation / connector-apps / connector-device / reward-dashboard / voice)  归位各领域
├─ verify-* ×5   (connector / usermodel / billing-control / browser-chat / engine-trust)                            对照代码验可行性
├─ phase4-* ×2   (control / orchestration)                                                                          归位控制 / 编排层
├─ phase5-* ×5   (contracts / engine / api / libsdb / rewarddash)                                                   物理拆 service
└─ 匿名 task ×11 (其中 9 个由上述 teammate 嵌套派生,如「验证 browser 域」「Extract endpoint paths」)
```

每个 teammate 自己也是完整 agent —— 例如 `phase5-contracts` 那个 transcript 跑了 158 行、38 Bash / 7 Edit。

### 4.3 执行底座:tmux 分屏

`Agent` 的 toolUseResult 带 `tmux_pane_id / tmux_session_name / tmux_window_name / is_splitpane` —— **并行 agent 实际跑在独立 tmux pane 里**(即 Claude Code 的 FleetView 分屏)。是真·OS 级并行进程,不是协程模拟。

### 4.4 通信协议

- **下行**:teammate 收到的第一条 `user` 是 `<teammate-message teammate_id="team-lead" summary="…">…</teammate-message>`。
- **上行 / 横向**:`SendMessage({to, recipient, summary, message/content, type:"message"})`。日志里 team-lead 中途给 `phase5-rewarddash` 发指令:批准其方案、划定边界(「只移这 2 个跨 service repo 进 pinai_db,别扩大」)、要求「全绿后 commit 报我」—— **这是对运行中 subagent 的实时双向操控**,不是 fire-and-forget。

> **启示**:强 agent 的多 agent 不是「开 N 个并行跑完收 join」,而是**有身份、可寻址、可中途纠偏、可嵌套**的团队。orchestrator 负责拆解 / 派活 / 划边界 / 收口,teammate 负责深执行。

## 5. 异步机制:teammate_spawned + task-notification 队列

这是「async agent」的核心,链路完整:

1. **派发即返回**:19 个 Agent 调用的结果全是 `status: "teammate_spawned"`(不是 `completed`)。调用瞬间返回,teammate 在后台 tmux pane 里跑,父 agent 继续干别的或派下一个。
2. **完成时入队**:teammate「come to rest」时,系统把一条 `<task-notification>` **`enqueue`** 进消息队列(`queue-operation` 记录,`operation:"enqueue"`):

   ```
   <task-notification>
     <task-id>aec25a9be1dd861a9</task-id>
     <tool-use-id>toolu_01G2…</tool-use-id>
     <output-file>/private/tmp/claude-501/…/tasks/aec25a9be1dd861a9.output</output-file>
     <status>completed</status>
     <summary>Agent "Extract direct tool endpoint paths" came to rest</summary>
     <note>每次该 agent 来到静止且无存活后台子任务时触发一次;可再发消息让它 resume,同 task-id 可能多次通知。</note>
     <result>…完整结果…</result>
   </task-notification>
   ```

3. **唤醒父 agent**:该通知以 `promptSource:"system"` 作为合成 user 回合注入主流,父 agent 据此继续。
4. **结果落盘**:完整输出写 `tasks/<task-id>.output`,通知里只带摘要 + result,避免父上下文被巨结果撑爆。
5. **排队输入**:用户在 agent 忙时输入,记成 `promptSource:"queued"`;`attachment.type:"queued_command"` 佐证 slash 命令也可排队。

**关键设计点**:

- 父子**不阻塞** —— 靠「派发返回 stub + 完成回调入队 + 队列项当合成 prompt 重入」解耦。
- 通知幂等可重入(同 task-id 可多次 notify,因为 agent 可被 resume)。
- 「无存活后台子任务才通知」—— 保证嵌套子树整体静止才回报父层。

## 6. 自主 goal 循环:`/goal` + Stop hook + sentinel 评估

这次能无人值守跑 3.7 小时,靠的是自主循环,transcript 把它的实现暴露得很清楚:

- 用户用 `/goal` 设了长任务条件(`goal_status.condition`):「先读取整个 doc,然后一个 phase 接一个 phase 执行,直到完全完成,每个 phase 完对照 doc 做测试…」
- **Stop hook 是引擎**:`system.subtype:"stop_hook_summary"` 的 `hookInfos[].command` 字段**就是那段 goal 文本**。即:agent 每次想停下时,Stop hook 触发,把 goal 当 prompt 重新注入,逼它继续。
- **sentinel 周期评估**:`attachment.type:"goal_status"` 记录带 `met:true/false` + `sentinel:true` + 评估 `reason`。系统周期性问「目标达成没?」,给出详细判断(例:「进度卡在 Phase 4 中途…用户主动说等 subagent 跑完暂停…当前未完成」→ `met:false`)。
- **达成才退出**:最终一条 `met:true` 带 `iterations:2, durationMs:13314471, tokens:663138`,reason 详述三层(代码层 33 commit 全绿 / 部署配置 ready-inactive / 改名 571 处)均落地才判完成。
- **可被人打断**:用户说「等下面两个 subagent 跑完,我们暂停一下」,sentinel 据此判 `met:false` 且尊重暂停;之后「continue」「please continue」再续。

> **启示**:自主性 = 一个「停止时重注入目标」的 hook + 一个「独立评估是否真达成」的 sentinel。关键是 sentinel 用**另一次 LLM 调用**判定,而非让执行 agent 自评,避免自我欺骗。这是把「一句话目标」变成「跑数小时直到真完成」的最小机制。

## 7. 上下文动态注入:`attachment` / system-reminder 家族

Claude Code 不是一次性塞死 system prompt,而是**每轮按需把变化的上下文以 `attachment` 增量注入**(即 `<system-reminder>`)。transcript 里的类型谱:

| attachment.type | 次数 | 注入了什么 |
|---|---|---|
| `task_reminder` | 39 | todo 列表状态提醒 |
| `goal_status` | 5 | 自主循环目标 / 达成判定(见 §6) |
| `agent_listing_delta` | 2 | 可用 agent 类型清单**增量** + `showConcurrencyNote`(并发派 agent 提示) |
| `deferred_tools_delta` | 2 | 延迟工具清单变化(见 §3.3) |
| `mcp_instructions_delta` | 2 | MCP server 指令变化 |
| `skill_listing` | 1 | 可用 skill 清单(`skillCount / names`) |
| `edited_text_file` | 3 | 被编辑文件的最新内容回填 |
| `compact_file_reference` / `file` | 4 | 压缩后 / 附加的文件引用 |
| `queued_command` | 1 | 排队的 slash 命令 |

注意大多是 **delta** —— 只注入变化量,不重发全量,既省 token 又让模型感知「刚发生了什么变化」(队友上线了、工具加载了、MCP 接上了)。

> **启示**:上下文工程的真相是「动态增量注入」而非「静态大 prompt」。把「环境变化」建模成可注入的 reminder 类型,模型才能对一个活的、变化的工作环境实时反应。

## 8. 状态、checkpoint 与压缩

- **文件 checkpoint**:`file-history-snapshot = {messageId, snapshot, isSnapshotUpdate}` —— 每次改文件按 messageId 存快照,支撑 rewind / undo(「回到某条消息前的文件状态」)。Edit / Write 的 `structuredPatch + originalFile + userModified` 配合它工作。
- **session 状态快照**:`mode` / `permission-mode` / `worktree-state` / `ai-title` / `last-prompt` 各 ~113 条,每轮快照一次,供 UI 投影 + resume。
- **上下文压缩**:`user.isCompactSummary:true`(+ `isVisibleInTranscriptOnly`)是一条压缩摘要回合;`system.subtype:"compact_boundary"` 标出压缩发生的分界点。长 session 到阈值就把旧历史压成摘要、钉住摘要继续,与缓存 TTL 配合。
- **中断**:`user.interruptedMessageId` 记录一次 ESC 打断(指向被打断的 assistant 消息)。
- **权限**:teammate meta 是 `permissionMode:"bypassPermissions"`(自主跑不弹窗);主流有独立 `permission-mode` 流,真人 prompt 带 `permissionMode` 字段。

---

## 9. Hooks 与可观测性

- **Hooks**:`system.subtype` 里有 `stop_hook_summary`(Stop hook,§6 的引擎),带 `hookCount / hookInfos`。Hook 是用户可配的、在生命周期点(如 Stop)执行命令并把输出回灌的扩展点。
- **可观测**:`turn_duration`(7,逐轮计时)、`away_summary`(15,用户离开期间的自然语言进度回顾,中英双语,「disable recaps in /config」)、每条 assistant 的 `usage.iterations[]`(单回合内多次推理的细分)。

## 10. 复刻蓝图:要造「同款 agent」,按这个顺序搭

把上面拆出的机制按依赖排序,给出可落地清单:

1. **事件流持久化**(地基):append-only JSONL,消息 / 状态 / 附件同流分 `type`;子 agent 分文件。先有它,resume / rewind / 审计 / 分进程才有依托。
2. **ReAct 执行核**:`thinking + text + tool_use` 多块输出;`tool_use ↔ tool_result` 1:1 回链;结果「结构化 + 文本」双形态。
3. **Prompt 缓存分层**:固定前缀(system + 工具 + 早期历史)走长 TTL cache,增量进短 TTL。没有它长任务烧不起。
4. **工具层**:每工具一套结构化 result schema;**延迟工具 + 按需 search 加载**(规模化必备);Edit / Write 带 patch + userModified 喂给 checkpoint。
5. **上下文动态注入**:把「环境变化」建模成 delta 型 reminder(待办 / 可用 agent / 工具 / skill / MCP / 被改文件),每轮只注入变化量。
6. **多 agent 团队**:Agent 工具产出有身份的 teammate(team / name / color / model / permission);独立进程(tmux 或等价)并行;`SendMessage` 双向通信 + 中途纠偏;允许嵌套。
7. **异步队列**:派发返回 stub(`spawned`)→ 完成入队 `task-notification`(摘要 + 结果落盘)→ 当合成 prompt 重入父流;输入可 `queued`;通知幂等可 resume。
8. **自主 goal 循环**:`/goal` 存条件 → Stop hook 想停时重注入 → **独立 sentinel(另一次 LLM 调用)判 `met`** → 达成才退;尊重人为暂停。
9. **状态 / 压缩 / 中断**:逐轮状态快照、文件快照(rewind)、到阈值压缩 + boundary 标记、ESC 中断记录。
10. **Hooks + 可观测**:生命周期 hook(至少 Stop)、逐轮计时、token / cache 计量、away recap。

**最容易被低估、却决定「强不强」的三点**:延迟工具加载(§3.3)、异步 task-notification 队列(§5)、goal + sentinel 自主循环(§6)。普通 agent 缺的正是这三样 —— 它们让 agent 能在大工具集、长时间、无人值守下稳定干活。
