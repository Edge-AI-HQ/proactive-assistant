# 前端分层架构方案（2026-06-10 起草，2026-06-11 更新三端格局）

> **状态**：方案已评审，关键决策全部拍板（见 §1.1），实施未开始。本文是设计 SSOT，实施时按 Phase 拆 PR。

## 1. 背景与目标

当前用户产品前端是 `proactive-ai-frontend`（React SPA，Vite + Tailwind + Capacitor 打包 iOS）。产品规划三端：

- **web**：现 codebase 原地演进（Vite SPA）；
- **macOS**：Electron，renderer 直接复用 web 端的 React DOM UI；
- **iOS**：React Native（Expo CNG）重写，替代当前 Capacitor 方案，UI 独立实现。

三端 UI 之下，「与后端的交互 + 业务逻辑」最大限度共用。终态共用矩阵：

```
packages/core (纯 TS)  ───────┬─── web (Vite SPA)
packages/state (React hooks) ─┤      │  ← React DOM UI 整层共用 → Electron renderer (macOS)
                              │      └─ web adapter             └ electron adapter (IPC→main)
                              └─── iOS (Expo RN)：独立 RN UI + expo adapter
```

三端消费同一份 core+state；web 和 Electron 额外共用整个 UI 层；RN 端只重写 UI 和平台 adapter。

### 1.1 已拍板的决策

| 决策点 | 结论 | 日期 |
|---|---|---|
| 现 web 端命运 | **原地演进**成未来的 web 端；共用包在真实消费中打磨，不出现「抽了包没人用」的腐化 | 06-10 |
| 启动方式 | **现在渐进抽包**，小步 PR 与功能开发并行；新功能直接写在新分层里 | 06-10 |
| 状态/数据获取选型 | **TanStack Query + zustand**（两者同时支持 React DOM 和 React Native） | 06-10 |
| iOS 技术栈 | **Expo CNG（prebuild）**；自家原生采集插件的 Swift 核心包成 Expo Module | 06-10 |
| web 框架 | **Vite SPA，不用 Next.js**（理由见 §4.1）；Next.js 留给未来的营销站/公开分享页 | 06-11 |
| macOS 技术栈 | **Electron**，renderer 复用 web DOM UI；mac 端原生采集仍需 Swift（helper/native module） | 06-11 |

## 2. 现状扫描结论（事实基线）

全量扫描 `proactive-ai-frontend/src`（263 个 TS/TSX 文件，~59.5k 行）+ `capacitor-plugins/ambient-ai`，2026-06-10（main e3342688）。

> **复核**（2026-06-11，main 8874a5e6，+20 commits：custom MCP connector、chat 阅读优先滚动、TTFT 优化、卡片手势等）：本节结论与文件引用全部仍成立；正文数字为扫描日快照（现 272 文件 ~63.1k 行，±5% 漂移）；唯一实质变化是源码断言测试 5→6（见 §2.3）。

### 2.1 业务逻辑现在住在哪

**大 hooks 是主力（`src/hooks/` ~6.3k 行）**，且业务逻辑占比极高：

| Hook | 规模 | 内容 | 业务逻辑占比 |
|---|---|---|---|
| `components/chat/conversation/useConversationRuntime.ts` | 1119 行 | SSE 流运行时：envelope 分发（20+ 事件类型）、transcript 累积、HITL 暂停、重连游标、分页 | ~95% |
| `hooks/useCardExecutionRun.ts` | 29KB | 卡片执行适配：`chatHistoryToSnapshot()` history→snapshot 转换、状态合成（running/needs_input/pending_done/...）、1.5s 轮询 | ~70%（转换逻辑本就是纯函数） |
| `hooks/usePipeline.ts` | 17KB | 生成任务状态机（idle→connecting→running→complete/error）、sessionStorage F5 恢复、孤儿运行采纳 | ~50% |
| `hooks/useCardActions.ts` | 13KB | confirm/modify/dismiss/snooze 编排、Set-based 乐观更新、connector OAuth 短路 | ~30% 纯逻辑 |

**泄漏进组件**：14 个组件直接 import `lib/api`（占组件文件 16%）。最严重的 `profile/GoalsView.tsx`（2322 行）一半是数据编排：5 个并发 fetch + 15 个 useState。`ConversationView.tsx`（1424 行）里 `conversationInit` / `proxyPost("/feedback")` 直接在组件内调用。

### 2.2 对分层有利的事实

- **`lib/api.ts`（2063 行，~80 个函数）是纯函数集合**：按域注释分组（devices/payment/profile/raw/conversation/skills/memory/scheduled-generators），auth 注入集中在 `authHeaders()` → `pinaiFetch()` 一处，401 重试带并发去重（module-level promise cache）。抽包阻力小。
- **SSE 是 `fetch + ReadableStream + TextDecoder` 手工解析**（`proxySSE` / `proxyGetSSE`，没用 EventSource），支持 POST body、custom headers、`id:` 行 resumable cursor（PR#56 Redis Streams 链路）。解析逻辑是纯 TS。
- **`services/ambient/timeline/` 的 pipeline/normalize/envelope/narrative ~3k 行已经是零平台依赖的纯 TS**（数据合并、窗口聚合、narrative 生成）。
- **导航是状态驱动**：没用 URL 路由（MemoryRouter 只是容器），`useAppNavigation` 持有 `activeView` + overlay 状态、`navigateTo(MenuId)` 是唯一入口。导航意图天然平台无关。
- **React hooks 本身跨 web/RN 共用**：`react` 包不依赖 DOM（依赖 DOM 的是 `react-dom`）。共用层可以直接包含 hooks 层，不必把所有逻辑降级成框架无关 class——这是整个方案的核心杠杆。
- **域类型现在是手抄后端的**（`types/intent-card.ts` 注明从后端复制，无同步机制）。三端后若各端各抄一份会三处漂移；core/domain 收敛成唯一一份是顺带收益。
- root 已是 npm workspace（`proactive-ai-frontend` + `capacitor-plugins/*`），加 `packages/*` 顺势。

### 2.3 阻力与雷点

- **零状态管理库**：手写 `useEffect + useState + AbortController`，三套轮询节奏并存（`useCardExecutionRun` 1.5s / `useActiveAgentRuns` 4s/30s 自适应 / `useCards` 30s），F5 恢复策略多样（sessionStorage / server truth + retry / Supabase session），`useUserSettings` 手撸 module-level cache + listeners。共用层如何管状态是最大架构决策（已拍板 TQ + zustand）。
- **RN 内置 fetch 不支持 `ReadableStream`**：整条 SSE 链路（chat stream / resumable cursor）在 RN 上跑不通，需要 `expo/fetch`（WinterCG 兼容，支持流式）或传输层注入。这是最容易被忽略的硬雷。Electron renderer 是 Chromium，无此问题。
- **ambient 采集层是 Capacitor 强耦合**：`services/ambient/sources/*`（14 个数据源 ~1600 行，每个都是 `AmbientAi.addListener` 绑定）+ SQLite（`outbox.ts` ~700 行 + `timeline/store.ts` ~900 行，`@capacitor-community/sqlite`）。RN 端要重写采集绑定与 DB driver，但**数据模型与 normalize 逻辑可共用**；自家 plugin 的 iOS Swift 核心（HealthKit/CoreMotion/音频）大部分可换壳复用。
- **6 个「源码断言测试」**（readFileSync + 正则锁组件结构：`AppLayout.navigation.test.ts`、`AppLayout.menu.test.ts`、`ChatDetailView.source.test.ts`、`CardTimeline.copy.test.ts`、`AmbientModelsManifest.test.ts`、`useCardExecutionRun.source.test.ts`——最后一个 2026-06-11 入 main，锁的正是 Phase 3 要提纯的 hook）会在文件搬迁时失败，需同步迁移。
- 平台耦合点完整清单：推送（`usePushNotifications`，注意「先绑监听器再 register」的顺序约束）、auth deep-link（`useAuth` 的 `appUrlOpen` + PKCE code exchange）、OAuth surface（`oauth-popup.ts`：web `window.open` 轮询 vs native `@capacitor/browser`）、secure storage（`devices.ts`）、键盘处理（`main.tsx` 的 visualViewport hack）、语音录制（`pcm-recorder.ts` AudioContext，web-only）。
- web 构建的 native 隔离靠 Vite alias 把所有 Capacitor 包指到 `lib/native-plugin-stub.ts`（Proxy 抛错），运行时靠散弹式 `if (isNative)` 守卫——能用但不是结构性隔离，且二元 `isNative` 判断在三端格局下会腐化（见 §4.5）。

## 3. 目标架构

### 3.1 三层与硬边界

分层线不是「React vs 非 React」，而是三条依赖边界：

| 层 | 内容 | 禁止依赖 |
|---|---|---|
| **L0 `@pin-ai/core`**（纯 TS） | transport（含 SSE 解析）、API 域函数、域类型、纯状态机、平台接口（ports）定义 | react、capacitor、electron、`window` / `document` / `localStorage` 等浏览器 globals |
| **L1 `@pin-ai/state`**（React hooks，跨 DOM/RN） | TQ queries/mutations、zustand stores、业务编排 hooks、auth glue | react-dom、capacitor、electron、浏览器 API（存储走 core 的 port） |
| **L2 apps**（三端，两套 UI） | web+Electron 共用一套 React DOM UI；RN 一套；各端入口组装自己的平台 adapter | —— |

边界用工具强制而不是靠自觉（同后端 web↔chat trust boundary 的思路）：core/state 包的 ESLint `no-restricted-imports`（禁 react-dom / @capacitor/* / electron）+ `no-restricted-globals`（禁 window/document/localStorage/sessionStorage/navigator/location），进 CI `frontend-check` 硬 gate。

### 3.2 目录结构

```
packages/
  core/          # @pin-ai/core   纯 TS
    src/transport/    # pinaiFetch / proxySSE / proxyGetSSE，fetch 实现可注入
    src/api/          # 按域拆 api.ts：conversation/ cards/ devices/ payment/ memory/ skills/ ...
    src/domain/       # IntentCard、SSE envelope、Signal 等类型 + normalize（后端类型的唯一前端镜像）
    src/machines/     # conversation runtime / card snapshot / pipeline 纯状态机
    src/ports/        # KVStorage、SecureStorage、Database、Push、OAuthSurface 等接口
  state/         # @pin-ai/state  React（跨 DOM/RN）
    src/queries/      # TQ hooks（替代手写轮询的数据 hooks）
    src/stores/       # zustand（navigation intent、conversation transcript、乐观状态）
    src/auth/         # supabase client 注入式 glue
proactive-ai-frontend/   # web app：DOM UI + web/capacitor adapters（Capacitor 壳退役前继续兼任 iOS）
capacitor-plugins/       # 不变（RN 切换完成后随 Capacitor 壳一起退役）
apps/desktop/            # 未来 Electron：main process + adapters + 薄 renderer 壳（复用 DOM UI，见 §5 衔接）
apps/mobile/             # 未来 Expo RN：RN UI + expo adapters
```

**DOM UI 的复用形式**（web ↔ Electron）：目标是「一套 React DOM UI、两个壳」。具体形式（Electron renderer 直接 import `proactive-ai-frontend` 的根组件 vs 把 DOM UI 提成独立包）是 Electron 立项时的决策，现在不预建。**现在唯一要做的前置**是 §4.5 的组装纪律：平台能力在入口处注入，UI 不内嵌平台分支——做到这一点，两种复用形式都只是壳工程。

工程决策：**内部包不打包、源码直引**——vite alias 指到 `packages/*/src`，未来 Metro 走 Expo 官方 monorepo 支持（SDK 52+ 自动处理 workspace），Electron renderer 走 vite 同构。没有 build 步骤、HMR 直通。暂不需要 turborepo/nx：各端构建（vite / electron-builder / EAS）相互独立，没有交叉产物依赖；若将来 CI 时长成为问题再引入，决策点后置。每包独立 `tsc --noEmit` + vitest 进 CI。

## 4. 关键技术决策与理由

### 4.1 web 框架：Vite SPA，不用 Next.js

评审中曾考虑 web 端换 Next.js，**否决**（2026-06-11），理由三条：

1. **产品性质不匹配**：web 端是登录后的重客户端 app（SSE 流式 chat、全是私人数据、零公开内容）。Next.js 的核心收益（SSR/RSC 首屏与 SEO、服务端渲染公开内容）对 authenticated app 没有兑现场景；核心复杂度（SSE 流、状态机、乐观更新）全在客户端，RSC 帮不上。
2. **与 Electron 直接冲突**：Electron 的最大红利是 renderer 加载 web 端同一份静态 bundle。Next.js 一旦用了服务端特性（RSC/Server Actions/middleware）就无法 static export，Electron 只剩「内嵌 Node server」（重、非主流）或「loadURL 远程站」（离线不可用，桌面端退化成套壳浏览器）两条路。两个决策互相打架时，Electron 的收益更实。
3. **引入第二后端运行时 + 推翻原地演进**：用足 Next.js 意味着 fly 上多一个 Node server（Supabase auth 改 `@supabase/ssr` cookie session、secrets 流转多一环、与 FastAPI 形成双后端）；Vite→Next 是构建/路由层重写，不是原地演进。

**Next.js 的正确位置**：未来若做营销站/公开分享页（分享卡片、research 结果——proactive AI 的天然增长钩子），独立建 Next.js 小站。按站点性质拆（app=SPA、公开内容=Next.js）是业界标准形态（Linear/Notion 同构）。

### 4.2 SSE 传输：fetch 注入解决 RN 雷

现状 `proxySSE` / `proxyGetSSE` 用 `fetch().body.getReader()` 手工解析。web 与 Electron renderer（Chromium）原生支持；RN 内置 fetch 不支持流式 body，Expo 的 `expo/fetch` 原生支持。

正解是 core transport 暴露一个注入点：

```ts
configureTransport({ baseUrl, fetchImpl, getAuthHeaders })
```

web/Electron 传 `globalThis.fetch`，RN 传 `expo/fetch` 的 fetch。一个注入点解决，不需要更重的抽象。PR#56 的 resumable cursor 逻辑（`id:` 行 → `lastEventId`）是纯解析逻辑，原样进 core。

附带提醒：RN/Hermes 的 `TextDecoder` 支持在 RN 立项时验证，旧版本需 polyfill。Electron 桌面端常驻 + 可恢复 SSE 是天然组合（替代移动端推送的部分职责，见 §4.5 ports 表）。

### 4.3 auth：core 不 import supabase

现状 `api.ts` 直接调 `supabase.auth.getSession()`。改为 `getAuthHeaders` 注入后：

- supabase client 由各端入口创建：web 用现配置（SPA flow）；RN 用同一个 `@supabase/supabase-js` + AsyncStorage adapter + PKCE（官方支持）；Electron renderer 同 web，但 session 持久化建议接 SecureStorage port（main 进程 `safeStorage`，不落明文 localStorage），OAuth 回调走 `shell.openExternal` + 自定义 protocol handler。
- `dev-auth.ts`（`X-Dev-Auth` header）只是另一种 header provider；
- auth glue（`onAuthStateChange` → 状态）放 state 层，接受 client 注入。

### 4.4 TQ 消化三套手写轮询；conversation 流不归 TQ 管

映射关系：

- `useCards` / `useMemories` / `useSkills` / `useUserSettings` / `useActiveAgentRuns` / `useComposio` / `useWeather` → **TQ query**（`refetchInterval` 替代手写轮询 + focus refetch；RN 上 TQ 官方提供 AppState/focusManager 接入）。`useUserSettings` 手撸的 module cache + listeners 整个删掉——TQ cache 就是干这个的。
- 写操作（feedback、settings patch、card actions）→ **TQ mutation + optimistic updates**（替代 `useCardActions` 的 Set 手工乐观态）。
- sessionStorage F5 恢复 → TQ persist / zustand persist（storage 走 KVStorage port）。
- **`useConversationRuntime` 不是 server-state cache，是流式状态机，TQ 不适合**。正解：envelope 分发 + transcript 累积 + 重连游标提纯成 core 的纯 reducer（`(state, envelope) → state`），zustand store 持有状态，state 层一个薄 hook 绑定 SSE 生命周期。提纯的最大红利是**可测试性**：录制真实 SSE 流做 fixture 回放测试——现在这 1119 行几乎没法单测。

### 4.5 平台 ports：能力注入替代平台枚举，组装收敛到入口

两条纪律：

1. **UI 与业务代码不问平台，只问能力**。现状的二元 `isNative` 散弹式守卫在三端格局（web / electron / ios，还有 Capacitor 过渡期的组合）下必然腐化成多分支枚举。正解：每端入口（composition root，web `main.tsx` / Electron renderer 入口 / RN 入口）组装一份 ports 实现注入下去，组件和 hooks 拿到的是 `secureStorage.set(...)` 这样的能力对象，不存在 `if (platform === ...)`。平台差异全部消失在入口组装这一层。
2. **只在搬迁碰到时才建 port**。第二、三个实现出现之前，提前设计全套接口必然设计错（对照编码原则「低冗余不过度抽象」）。接口形状以现有 web/Capacitor 实现为准，Electron/RN 立项时按新实现校准。

扫描已知最终会出现的 ports 与三端实现：

| Port | web（现有，含 Capacitor 过渡） | Electron（未来） | Expo RN（未来） |
|---|---|---|---|
| KVStorage | localStorage / sessionStorage | localStorage（renderer 直用） | AsyncStorage |
| SecureStorage | @aparajita/capacitor-secure-storage | main `safeStorage`（IPC） | expo-secure-store |
| Database（ambient outbox/store） | @capacitor-community/sqlite | better-sqlite3（main，若做桌面采集） | expo-sqlite |
| Push / 触达 | @capacitor/push-notifications | 常驻 SSE + 系统 Notification（无 APNs） | expo-notifications |
| OAuth surface | window.open 轮询 / @capacitor/browser | `shell.openExternal` + protocol handler | expo-web-browser |
| DeepLink / AppLifecycle | @capacitor/app | protocol handler / app 事件 | expo-linking / AppState |
| Ambient 采集 | @pin/capacitor-ambient-ai（iOS Swift） | Swift helper / native node module（屏幕活动、日历等 mac 采集） | 同一套 Swift 包成 Expo Module |

> Database port 的主要消费者是本地-云端同步引擎（本地缓存 + cursor 增量 + outbox），`@pin-ai/core` 将新增 `sync/` 子系统——调研与方案见 [本地同步引擎](./2026-06-11-local-sync-engine.mdx)。

### 4.6 导航：状态驱动是隐藏红利

没用 URL 路由对 web 是缺陷（无 deep-link / 浏览器后退，web 端要补），但对分层是好事：导航意图（`navigateTo(MenuId)` + overlay 状态）已经平台无关。抽到 state 层 zustand store 后各端映射：web 真 URL 路由（react-router）、Electron 同套 UI（`file://` 下用 hash history，细节属壳工程）、RN react-navigation。

### 4.7 UI 共用边界

- **web ↔ Electron：共用整套 React DOM UI**（Tailwind、framer-motion、react-virtuoso、vaul 在 Chromium renderer 全部照常工作）。
- **RN：独立 UI**。对应物替换：Tailwind→RN 样式方案、framer-motion（26 个组件在用）→reanimated、react-virtuoso→FlashList、vaul→RN bottom sheet。
- `components/ui/` 现在只有 1 个 Drawer 原语，web UI 体系本身欠建设——那是 UI 演进的事，不在本方案范围。

### 4.8 Electron 安全模型（立项第一天的规矩）

`contextIsolation: true` + `nodeIntegration: false` + preload 只暴露白名单 IPC 通道；renderer 视为不可信，平台能力（safeStorage、文件、采集控制）全部走声明式 IPC——ports 的 electron adapter 就是这层 IPC 的类型化封装。这是后端 web↔chat trust boundary 的桌面版对应物：敏感能力只在 main，renderer 只拿到窄接口。

## 5. 渐进迁移路径

每个 phase 独立可 merge、CI 始终绿，与功能开发并行。核心机制是 **shim 兼容**：`lib/api.ts` 抽空后变成 `export * from "@pin-ai/core/api"` 转发壳，组件 import 路径零改动；之后按域逐步改 import、最后删壳。

| Phase | 内容 | 规模/风险 |
|---|---|---|
| **0 地基** | `packages/core` + `packages/state` 骨架、tsconfig、ESLint 边界规则、vitest、CI 接入 | 1 个 PR，小 |
| **1 API 层下沉** | `api.ts` 2063 行按域拆进 `core/api/*`，auth 改注入，`types/` 域类型随迁，旧路径 shim | 2-3 个 PR，中；**ROI 最高、风险最低**，完成后协议层即三端 ready |
| **2 TQ/zustand 立起来** | 引 Provider；7-8 个数据 hooks 逐个换成 `state/queries/*` 的 TQ 版；新旧并存无冲突。**React 19 升级作为本阶段独立 PR**（三端版本统一前提，TQ v5/zustand/react-router 7/framer-motion 12 均兼容，react-virtuoso、vaul 升级时验证） | 每 hook 一个 PR，各小；可穿插日常迭代 |
| **3 核心状态机提纯** | `useConversationRuntime` / `useCardExecutionRun`（`chatHistoryToSnapshot` 本就 ~70% 纯函数）/ `usePipeline` / `useCardActions` ≈ 2.7k 行 → core 纯状态机 + state 壳 | 3-4 个 PR，大；**风险集中区**，先写状态机回放测试再动手，每 PR 配 chat 主链路手动验证 |
| **4 组件去业务化 + 组装收敛** | 14 个直连 api 的组件改走 state hooks；`GoalsView`（2322 行）顺势拆；散弹式 `isNative` 分支收敛到入口组装（§4.5 纪律）；6 个源码断言测试同步更新（锁 `useCardExecutionRun` 的那个在 Phase 3 搬迁时即触发） | 持续性，跟 UI 迭代合并做 |
| **5 ambient 域** | `timeline/` 纯逻辑 ~3k 行平移进 core；outbox/store 的 SQL 逻辑与 driver 分离（Database port）；`sources/*` 采集绑定留 app 侧，normalize 进 core | 中，可滞后或与 3/4 并行 |

### 衔接：Electron macOS 立项时

依赖 Phase 1-2（拿到可注入的 core+state）即可起步，不必等 Phase 3-5：

1. `apps/desktop` 壳工程：main process（窗口、tray、protocol handler、auto-update、签名公证）+ preload IPC 白名单（§4.8）。
2. renderer 复用 DOM UI：拍板复用形式（直接 import app 根组件 vs 提独立 UI 包），入口组装 electron adapters（§4.5 ports 表第三列）。
3. 若做 mac 桌面采集：Swift helper / native module + Database port 的 better-sqlite3 实现，normalize 复用 core（与 iOS ambient 同构）。

### 衔接：RN iOS 立项时

依赖 Phase 1-3（协议层 + 状态机提纯完成，否则 conversation 链路要在 RN 上重写一遍）：

1. `apps/mobile` Expo CNG 壳 + `expo/fetch` 注入 transport + expo adapters。
2. 自家 plugin 的 iOS Swift 核心（HealthKit/CoreMotion/音频）换壳成 Expo Module。
3. RN UI 按屏重建；Capacitor 壳与 `capacitor-plugins/` 在切换完成后退役。

### 执行顺序建议

Phase 0+1 现在就排（风险低、独立成立，即使端规划再变也是纯收益）；Phase 2 穿插日常迭代（React 19 升级早做，它同时是 Electron/RN 的前提）；Phase 3 在 long-task UX / SSE 这波功能稳定后启动（避免与 in-flight 的 conversation 改动撞车）。Electron 衔接最早可在 Phase 2 完成后启动；RN 衔接等 Phase 3。

## 6. 收益与代价的诚实评估

### 分端共用率

| 端 | 共用 | 需新写 |
|---|---|---|
| **web** | —（共用层的孵化地与第一消费者） | 持续演进 |
| **Electron macOS** | core + state + **整套 DOM UI**（~90%+） | main process、preload/IPC、electron adapters、（可选）mac 采集原生模块 |
| **Expo RN iOS** | core + state（协议层 + 状态机，约占现 codebase 20-25%） | 整套 RN UI（现 DOM UI ~25k 行的对等物）、expo adapters、采集模块换壳 |

对 RN，20-25% 的数字不大但价值密度高：SSE 协议、重连游标、HITL、乐观更新、竞态处理——**每个功能里最难写对、bug 最贵的部分**。分层不会让 RN 重写变小，它保证的是 RN 端不用重写也不会写歪协议层和业务状态机，且三端行为天然一致。对 Electron，分层 + 不用 Next.js 的组合直接把桌面端变成壳工程。

### 主要风险与对策

1. **Phase 3 行为回归**（最大风险项）：SSE 重连、HITL、F5 恢复这些边界行为是踩坑打磨出来的。对策：先测试后重构（envelope 回放 fixture）、小 PR、chat 主链路手动回归。
2. **React 19 升级**（已从风险升格为 Phase 2 的明确迁移项）：Expo SDK 53+ 绑 React 19；state 包 peerDependencies 写 `react >=18` 过渡，三端统一到 19 后收紧。
3. **TQ 心智切换**：团队要适应「server state 不进 useState」。一次性学习成本，换掉三套手写轮询和多种 F5 恢复策略，值得。
4. **半途而废是最差结局**：分层做一半（部分 hooks 在 TQ、部分手写）比不做更乱。Phase 1-2 务必做完整闭环；Phase 3 可以按模块暂停，但不要半个模块。
5. **Electron 运维成本**（立项时）：签名公证（notarization）、auto-update 通道、崩溃上报是桌面端固定开销，纳入壳工程排期，不要当成「顺手就能发」。

### 不做的代价

RN/Electron 立项时面对的是 6.3k 行 React 强耦合 hooks + 14 处组件直连 API + 零测试的状态机：RN 端等于把 Phase 1-3 压缩到立项关键路径上做且没有回归基准；Electron 端虽然 UI 可整体复用，但散弹式 `isNative` 与直连 supabase/localStorage 的代码会在 renderer 里产生一批隐蔽的运行时差异。
